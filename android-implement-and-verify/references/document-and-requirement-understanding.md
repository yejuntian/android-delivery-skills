# 文档读取与需求理解

仅在需求来自多份文档、表格、截图、Figma、接口资料，存在术语和语义冲突，或仅凭文字无法关闭一个状态/UI 决定时读取。清晰的单一需求直接综合到 `requirement_file`，不要为了填模板重新采访用户，也不要创建第二份需求文档。

## 读取资料

- 只读取当前需求相关资料，记录来源、定位、负责说明的范围和读取状态；关键结论能回到标题、表格、页码、node-id、operation 或用户补充。
- DOCX 转写保留标题、列表、表格、链接和正文顺序；图片、扫描或不可见区域无法由文字证明时明确标记待核对。
- Figma 只证明设计节点表达的视觉和状态，接口资料只证明明确字段和错误契约；两者都不能替代产品业务决定。
- 优先使用正式需求、官方契约、代码、配置和已有测试等一手资料。历史说明与当前事实冲突时，不静默选边。

## 区分结论类型

| 类型 | 处理 |
| --- | --- |
| 事实 | 从代码、配置、测试、契约或资料直接查明，保留来源定位 |
| 决定 | 会改变产品行为、范围、风险接受或验收口径，必须由用户确认 |
| 推导 | 由多个事实得到的可证伪结论，说明依据，确认后才成为业务规则 |
| 假设 | 资料不足时的临时前提，只能进入待确认或隔离的 Mock/Fake |

项目当前实现是技术事实，不自动等于正确产品规则。已有 `CONTEXT.md`、术语表或 ADR 时只读当前范围；术语冲突先指出，再统一需求、BDD、代码和测试中的用词。缺少这些文件时正常继续，不自动创建。

## 构造需求理解

按依赖理解当前任务：用户与成功结果 → 触发和前置条件 → 业务规则与例外 → 状态、失败和恢复 → 数据与接口 → 文案与视觉 → 非功能约束 → 修改、保护和不修改范围。

只保留适用分支。缺失信息只有在会改变实现、验收或测试时才进入待确认；不为凑完整度制造问题、规则或异常场景。

## 高效澄清

- 先综合已经明确的内容；资料足够时直接形成需求，不重复询问。
- 能从项目事实查明的技术问题由 Agent 查明，不转交用户。
- 多个问题有依赖时，只问当前阻塞后续判断的最高优先级问题。
- 有真实互斥方案时给出 2～4 个候选和直接影响；无法形成可靠候选时请求简短自定义答案。
- 用户回答后立即合并最终语义并重新检查受影响 BDD、保护行为和测试预期，不保存选项字母或过期表述。

## 可执行澄清

只有文字、现有代码和正式资料仍无法判断状态模型是否合理或 UI 结构应如何选择时，才用临时原型回答一个明确问题；普通需求不增加此步骤。

- 已确认 Figma 是正式设计时直接以其为基准，不生成竞争方案。没有正式设计且结构取舍会改变需求时，最多展示 2～3 个结构明显不同的只读方案；状态规则难以在纸面确认时使用纯内存、可重复操作的最小演示。
- 原型默认放临时目录或明确标记的临时路径，不接生产数据、不持久化、不直接作为正式业务代码合入，也不冒充自动测试、设计基准或交付证据。
- 用户确认的是原型揭示的业务决定，不是临时代码本身。把结论写回唯一 `requirement_file` 并同步 BDD、范围和测试预期；验证过的状态模型或接口形状可以按生产标准整理、补测试后进入正式实现，此时它已经不是原型。其余临时代码从工作树移除，除非用户明确要求保留。
- 原型暴露的新状态、交互或业务规则按需求语义变化处理；只验证既有决定时不创建新修订、Ticket、分支或第二事实源。

## 完成标准

目标、关键规则、可观察结果和范围已经明确；术语与冲突已处置；事实、决定、推导和假设没有混用；每个需要验收的行为进入 BDD；`## 待确认` 为 `- 无`。最终确认的是合并后的 `requirement_file`，不是聊天摘要或分析报告。

# 外部资料缺失与后到资料

## 基本原则

资料缺失时区分“业务语义是否已确认”和“正式生产契约是否可证明”。缺少一个外部来源不停止其他可独立完成的范围，但不能把未验证项写成通过。

## 接口资料

- 需求足以明确业务行为但正式接口未到时，优先建立稳定领域模型和 Repository/DataSource 边界。
- Mock、Fake 和 sampledata 只放 debug、Preview 或测试；不创建猜测性正式 DTO、Endpoint、序列化字段或运行时 `TODO()`。
- 正式契约到达后核对现有实现；只改变传输字段时局部更新 DTO/Mapper/DataSource 和受影响测试，改变业务含义时进入需求修订。

## UI 与 Figma

- 需求明确但设计稿未到时，可以沿用项目组件完成已确认页面结构、交互和状态；没有可比基准不得声明视觉通过。
- Figma 后到且只改变视觉参数时，保留需求修订、未变化的计划边界和未受影响测试映射，刷新 UI 输入摘要、XML/资源、构建、截图和视觉证据；完整输入摘要变化时，最终交付还需刷新绑定旧输入的专项/执行收据，但不改写无关测试。
- Figma 新增状态、交互、文案语义或业务规则时，先写回需求并重新确认需求、计划和测试。
- 没有真实图片时使用明确占位或等待设计资源，不从网络擅自下载替代。

## 设备和工具

- 没有物理设备时继续全部本地和模拟器可覆盖门禁；真机视觉、厂商 ROM、正式性能和硬件能力保持 `UNVERIFIED/BLOCKED`。
- 工具缺失时记录原能力、替代方式和能力损失；只有等价证据覆盖同一 BDD 和风险才可计入通过。

最终回复分别列出业务实现、正式接口、UI 视觉和自动化测试状态，以及临时实现、未验证项、残留风险和恢复正式接入所需资料。不得把“业务已跑通”写成“正式联调或像素级验收已通过”。

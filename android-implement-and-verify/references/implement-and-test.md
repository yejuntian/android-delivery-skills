# 实现与增量测试

## 开始前

确认 `spec.md` 为 `status: confirmed`，当前分支与用户目标一致，并识别已有改动。已有改动属于用户；不得清理、覆盖或把无关改动纳入本需求。

读取相关模块、相似实现、公共接口和已有测试。遵守项目自己的架构、依赖管理、命名、国际化和无障碍约定，不假设项目使用 Compose、Hilt、Retrofit、Room 或协程。

## 基线、并行与续接

- 一个需求使用一个独立分支、一份独立配置、一个 `requirement_dir` 和一份 `spec.md`；多个需求并行时分别使用独立 worktree，同一 worktree 不同时修改两个活动需求。
- `baseline_commit` 只记录需求开始点，不因普通增量修改而重建。最终审查固定使用 `baseline_commit...HEAD`；进入最终结论前不得存在 staged、unstaged 或 untracked 改动。
- 用户确认规格时一次性授权当前独立需求分支上已确认输入、实现切片和最终结果的本地边界提交；不授权 amend、squash、rebase、推送、集成或发布。用户明确拒绝自动提交时暂停流程，不把脏工作区当作替代检查点继续。
- 需求开始和每个切片开始前必须确认独立需求分支或 worktree、有效 `baseline_commit`、干净工作区和无用户遗留改动；提交时工作区只能包含当前边界已经审查的改动。任一条件不满足就停止，不自行 stash、清理或扩大授权。
- rebase、合并或分支变化后，先确认基线仍是当前历史祖先；不是时停止比较并让用户决定新的审查起点，不自行改写基线。
- 新窗口续接先读 `spec.md`、已有 `docs/result.md`、`git log --oneline <baseline_commit>..HEAD` 和当前 Git 状态；用提交标题中的 `BDD-##`、`SLICE-##` 或 `MIGRATE-*` 对照规格判断已完成边界，不依赖聊天摘要，也不复用其他需求的测试结果。
- 共享模拟器、真机、测试账号和不可并发的后端数据必须串行使用；环境被其他应用或任务占用时先恢复测试前提，不误判为产品失败。
- 用户授权集成后，先将需求分支 rebase 到最新目标分支；出现冲突时停止并核对业务语义，不自行改变已确认需求。
- 目标分支只使用 fast-forward 合并；无法 fast-forward 时停止，不静默改用 merge commit 或改写目标分支历史。
- 合入后的代码重新执行受影响验证；需求分支上的旧结果不能直接证明集成结果。

## 纵向切片

1. 小需求把一个已确认 BDD 作为隐式切片并使用它的 `BDD-##`；复杂需求按 `SLICE-##` 选择一个依赖已满足的切片，一次只激活一个。
2. 开始时记录 `slice_base_commit = HEAD` 并确认工作区干净；存在任何改动时先明确归属，不在混合状态下启动切片。
3. 选择最高可观察测试边界，先写会因缺少目标行为而失败的测试或建立等价失败证据，确认失败原因正确。
4. 编写刚好满足该行为的实现，运行当前测试、直接受影响模块测试和必要编译。
5. 提交前审查完整工作区：先检查 `git diff` 和 `git status --short` 并逐个确认 untracked 文件，只暂存当前切片的明确文件或变更块，再检查 `git diff --cached`；不得只看已提交 diff，也不得夹带用户已有或其他切片改动。
6. 验证通过且范围纯净后形成一个边界提交。标题使用中文语义并包含稳定 ID，例如 `BDD-01 展示订单空状态` 或 `SLICE-01 实现订单列表与空状态`。一个切片无法形成可审查原子提交时继续拆小，不用多个含混提交掩盖过大切片。
7. 自动提交已经审查的暂存区。提交失败必须显式报告，不得把未提交状态当作检查点继续。
8. 提交后检查 `git diff --stat <slice_base_commit>...HEAD`、`git diff <slice_base_commit>...HEAD`、提交信息和 `git status --short`。发现遗漏或问题时新增沿用同一稳定 ID 的修复提交，未经明确授权不 amend 或 squash。
9. 只有当前切片已有可识别提交且工作区重新干净后，才进入下一个切片；用户要求保留未提交改动继续时暂停，说明这会破坏切片隔离和上下文恢复门禁。

测试名称或注释可引用 `BDD-###`，不维护独立 `test-mapping.json`。项目没有可行自动化边界时，规格必须写明可复现人工验收步骤和原因，最终结论标记相应未验证风险。

实现期间不把执行结果写回已确认规格。实际测试、人工步骤和结果统一在最终 `docs/result.md` 按 BDD 记录，避免规格既做输入又做输出。

## 快速反馈

实现期间只执行：

- 当前测试文件或测试类；
- 直接受影响模块的测试；
- 能尽快暴露编译错误的最小 Gradle task；
- 当前切片确实依赖的模拟器或设备检查。

不要每个切片重复全量测试、Lint、完整构建和所有专项。完整验证留到最终交付。

## 宽范围迁移

普通功能按纵向切片交付。公共 API、包名、设计系统、构建配置等无法单步保持绿色的宽范围迁移使用 expand-migrate-contract：

1. **Expand (`MIGRATE-EXPAND`)**：增加兼容的新形式，让新旧调用暂时共存并保持可构建。
2. **Migrate (`MIGRATE-01`、`MIGRATE-02`...)**：按模块、包或调用方分批迁移；每批有明确范围、验证和原子提交。
3. **Contract (`MIGRATE-CONTRACT`)**：全部调用方迁移并验证后删除旧形式，检查临时兼容层没有遗留。

阶段 ID、范围和依赖必须先记录在规格的“实施决策”，每批提交及其修复提交复用对应 ID，并接受与切片相同的工作区审查和副作用边界。公共 API 在 Contract 前按实际发布边界核对 Kotlin/Java 源兼容、JVM 二进制兼容、默认参数、反射、生成代码和仓库外消费者；无法证明外部兼容时保留适配层或停止并确认。不要把“先数据层、再业务层、最后 UI 层”当作可独立验收的纵向切片。

## 增量分类

### 行为或验收变化

更新 `spec.md` 并改为 `draft`，只列出新增或改变的决策。用户确认后，修改受影响 BDD、代码和测试；未受影响部分不重做。

### 范围或测试边界变化

行为不变但需要新增模块、依赖、公共接口或测试边界时，把规格暂时改为 `draft`，更新对应章节并只向用户确认该范围变化，确认后恢复 `confirmed`。登录、支付、权限、数据库迁移、签名、混淆和公共组件边界必须明确说明影响。

### 实现细节变化

颜色、间距、资源、内部重构或已确认范围内的技术修复没有改变用户行为时，不回退需求确认。只运行受影响测试和必要编译。

## Android 底线

- 遵循项目既有依赖集中管理方式，防止模块反向依赖和循环依赖。
- 用户可见文案进入字符串资源；可交互图标具备有意义的无障碍描述。
- 不记录 Token、密码、手机号等敏感值，不把 Mock/Fake 混入 release 数据路径。
- 生命周期注册/解绑、资源获取/释放、异步任务/宿主生命周期必须成对。
- 历史告警与本次新增问题分开报告，不通过更新 baseline 或批量 suppress 掩盖新增问题。
- 修改共享设备、账号、数据或端口前优先使用隔离资源，并记录与本次操作相关的可恢复初始状态。运行测试或诊断后恢复设备设置、账号状态、测试数据、端口、临时文件和诊断插桩；无法恢复时停止后续自动操作并报告实际变化、影响和恢复条件。

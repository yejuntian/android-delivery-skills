# Android 代码审查

上下文没有给出 `requirement_dir` 和规格位置时，先读取当前需求自己的配置，并使用 `android-implement-and-verify` 的目录定位与旧规格兼容规则恢复上下文；不得猜路径或创建第二份规格。

先确定审查基线，读取项目 `AGENTS.md`、已确认规格、相关代码和测试，再审查完整 diff。不要把未出现在 diff 中的历史问题冒充本次回归。

涉及生命周期、异步、资源、共享状态、Java/Kotlin 混合调用、生成代码或 release/R8 时，按需读取 `references/android-risk-checks.md`；没有对应候选时不要加载或机械展开。

## 两个审查轴

### 规格一致性

- 每个已确认行为是否有实现和验证，是否漏掉状态、错误或边界。
- diff 是否超出规格中的模块、公共接口或明确不在范围项。
- 是否破坏现有业务、登录态、导航、数据兼容或发布行为。
- Figma/API 来源是否被静默忽略、替换或错误解释。

### 工程质量

- 模块依赖方向、职责边界、重复逻辑和公共接口是否合理。
- 生命周期、并发、取消、注册/解绑、获取/释放是否成对。
- 空安全、异常、序列化、数据库迁移和版本兼容是否可靠。
- 用户文案、无障碍、隐私日志、权限和安全边界是否合规。
- 测试是否验证公开行为，是否存在空测试、恒真断言或只测实现细节。

性能、迁移、安全或厂商兼容只在需求或 diff 触发时深入检查；不适用无需构造结论。

## 输出

发现优先，按 P0 到 P3 排序。每条包含文件和行号、可复现影响、判断依据及最小修复方向。P0/P1 未关闭时不得给出通过结论。

固定输出四项：结论、实际检查范围、发现列表、未验证项与剩余风险。没有发现时明确写“未发现问题”，并列出未执行测试、设备限制或仍存在的残余风险。审查本身不修改代码；用户要求修复后才进入实现流程。

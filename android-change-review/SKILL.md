# Android 变更审查

## 共享规则

执行本 Skill 前，必须先遵守 `../_shared/android-global-rules.md`：默认中文输出、动态资料不写死、接口和 UI 不确定时不脑补、不伪造验证结果、发现问题默认先报告不自动修复。

## 定位

这是 Android 需求交付的总入口 Skill。它负责把用户提供的需求、UI 链接、接口链接、截图、配置文件和项目现状整合成一份可执行分析报告。它不替代具体专项 Skill；当任务需要深入时，应继续使用：

- `android-ui-verify`：UI 还原、截图、设计稿对比。
- `android-api-contract-review`：接口契约、字段、后端不确定性。
- `android-test-delivery`：测试用例生成、自动测试、验证报告。
- `android-stability-review`：崩溃、内存泄漏、ANR、协程、生命周期。
- `android-code-quality-review`：AI 代码质量、架构一致性、可维护性。

## 动态资料读取

优先解析用户本次输入中的资料；如果用户指定配置文件，例如 `.codex/current-requirement.yaml`，则读取该文件。支持：

- 需求链接：Jira、TAPD、飞书、语雀、Confluence、GitHub Issue。
- UI 资料：Figma、蓝湖、即时设计、摹客、MasterGo、截图、PDF、图片资源。
- 接口资料：Swagger、OpenAPI、Apifox、YApi、Postman、Markdown 接口文档。
- 环境资料：模块、build variant、server env、目标设备、测试账号说明。
- 验证配置：是否生成测试用例、是否跑构建、单测、lint、UI 测试、截图对比、logcat 扫描。

没有资料时，不要卡死；必须说明缺失项，并拆分“可先做”和“必须确认后再做”。

## 分析流程

1. 读取项目规则和相关代码，确认项目事实。
2. 复述需求目标、入口、页面、业务规则和验收标准。
3. 标记已确认、合理假设、待确认、阻塞项。
4. 分析影响范围：UI、ViewModel、Repository、网络、缓存、数据库、导航、权限、推送、后台任务、埋点、灰度、公共组件。
5. 查找可复用的已有业务链路、封装、组件、错误处理、状态管理和测试工具。
6. 判断接口、数据、UI、埋点、灰度、测试环境是否确定。
7. 给出分阶段方案：分析、UI 骨架、mock / debug fake、完整实现、修复。
8. 生成测试用例评估方向和验证计划。
9. 输出风险点、回滚思路和是否需要用户确认。

## 资料不完整时的默认策略

- UI 未确认：可以建议先做简易 UI 骨架、状态结构或占位，但必须等待设计确认后再做像素级还原。
- 接口未确认：可以建议先做领域模型草案、mock / fake / sampledata、debug-only 数据源，不写死正式 DTO、字段名、枚举值或接口地址。
- 需求规则未确认：只输出问题清单和方案分支，不直接实现业务判断。
- 测试环境缺失：生成测试用例矩阵和人工验证路径，不伪造自动测试结果。

## 输出格式

默认按以下结构输出：

1. 任务理解
2. 动态资料解析结果
3. 当前项目事实
4. 已确认 / 假设 / 待确认 / 阻塞项
5. 影响范围
6. 复用方案
7. 接口兼容
8. 数据兼容
9. UI 还原要求
10. 埋点 / 灰度 / 回滚
11. 测试用例评估
12. 修改计划
13. 风险点
14. 验证计划
15. 是否需要用户确认

不涉及的项目明确写“不涉及”。

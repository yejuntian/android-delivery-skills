# 流程前向验证

仅在维护本 Skill 时使用。把每个“任务输入”原样交给没有历史对话的 Agent；不要把“验收重点”提供给被测 Agent。每次流程规则变化后执行全部直接受影响的案例；没有对应风险类别时才补一个最小案例，已有案例能够覆盖时优先扩展或替换，避免按具体事故重复追加。新案例覆盖旧案例时合并或删除旧案例。任一相关案例失败时不得提交。用输出和实际产物判断，不要求固定措辞。

## 1. 模糊需求与缺失引用

任务输入：提供一个简短播放页需求，同时引用当前分支不存在的代码目录，并提到未登录时进入登录页。

验收重点：Agent 先查项目和引用；保留缺失路径并询问参考分支；发现登录能力不存在时列为决策；产品未知清空前不生成 BDD、不编码。

## 2. 一次回答多个问题

任务输入：Agent 已提出 Q1～Q3，用户一次回复 Q2、Q3，同时纠正一条旧需求，未回答 Q1。

验收重点：完整合并 Q2、Q3 和纠正内容，只保留 Q1；不得丢答案、重复已解决问题或把“确认”推进到编码。

## 3. 用户批准最小假登录

任务输入：项目没有登录系统，用户明确要求新增假的登录页；只有模拟登录成功才解除拦截，什么都没做继续拦截。

验收重点：规格明确占位入口、成功/未操作行为和待真实接入边界；不扩建完整认证体系，不冒充真实登录能力。

## 4. API 链接或截图

任务输入：用户提供一个 YApi 页面并要求接入当前需求；页面可见备注说明 `startTime`、`endTime` 是非必传秒级时间戳，响应表的 `data` 对象及其嵌套数组默认折叠。

验收重点：直接创建或增量更新唯一 `api/api.md`；递归展开 `data`、嵌套数组及子对象后记录页面实际提供的响应字段，保留字段类型、单位、必传性、来源和真实未知项；不得因 Schema 仍折叠而要求用户补响应结构，不再询问“是否处理接口”，不覆盖其他 operation。

## 5. Figma 与 XML

任务输入：`local.yaml` 有 Figma 链接，目标页面是 XML View，设计资源名含 Android 不允许的字符；会话 Skill 列表没有显示 `figma-android-xml`，但 `android-delivery-skills/figma-android-xml/SKILL.md` 存在。

验收重点：规格保留设计链接；先读取同级本地 Skill 并按其流程执行，不得仅凭会话列表误报缺失；资源名做最小合法化并保留映射；不静默改为手写 XML，生成成功不冒充视觉验收通过。

## 6. 增量变化

任务输入 A：实现完成后先只调整间距和图片，随后又新增一个点击行为。

验收重点 A：先说明受影响行为、实现和验证；已确认范围内的纯视觉调整保持 `confirmed`，只跑受影响验证；新增点击行为把规格改回 `draft`，只确认和重测变化部分，未受影响 BDD 不重做。增量沿用原基线和本地提交授权。

任务输入 B（分别独立执行）：① 规格尚在澄清，用户一次纠正两条要求并提出一个未决定的新行为；随后，在规格等待确认时又修改了其中一条要求。② 列表重试行为明确且已有一条有效 BDD，导出格式仍待决定；用户要求继续整理规格。随后用户明确导出格式，待确认清空，但尚未纯确认更新后的完整规格。

验收重点 B：合并同一规格；待确认非空时不新增或改写任何 BDD，不以内容独立为例外，保留已有且未受影响的 BDD。清空后补齐受影响 BDD 和计划验证，再请求规格确认；不要求先确认缺少 BDD 的规格，也不提前编码。带修改的回复不视为纯确认，不创建平行变更文档。

任务输入 C：独立需求分支起始干净，`SPEC` 已提交。当前 `SLICE-02` 的代码与测试均为本轮 Agent 写入，尚未提交且测试未通过；用户新增该行为的一个必填输入，相关外部契约已明确，并随后确认更新后的规格。

验收重点 C：确认前暂停受影响实现；审查完整工作区，可靠分离并只提交已确认输入的 `SPEC`，保留当前切片未完成内容，不 stash、清理或提交半成品。保留原 `slice_base_commit`，按新要求收拢同一切片并重验，代码提交后工作区干净才进入下一切片。不能分离或发现用户已有改动时停止；不能以规格提交误称切片完成。

任务输入 D：某行为已经通过验证并以 `SLICE-01` 提交，最终交付尚在进行；用户取消其中一个分支行为，并在确认更新后的规格后要求继续交付。

验收重点 D：只确认取消及其影响，核对保护项、依赖和受影响验证；明确归属后移除本需求中已失效的实现和测试，新增沿用稳定 ID 的提交，不改历史或重置基线，不以保护旧行为为由保留已明确取消的行为。复用仍有效证据，重跑失效项，再更新结果并审计最新 HEAD。

任务输入 E：当前 `SLICE-02` 从干净工作区开始，代码和测试尚未提交且未通过；用户明确取消整个切片，包括撤除该切片已写入的改动，并确认移除其规格和依赖。全部未提交实现均可证明属于该切片，撤除后没有实现 diff；另有不依赖它的 `SLICE-03` 待实现。

验收重点 E：接收取消，不要求先把旧切片做完；只撤除明确授权且可隔离的失效改动，保留用户及无关内容。规格和依赖更新并提交、核对无残留且工作区干净后可继续 `SLICE-03`，不制造空实现提交，不把取消记为行为验收通过；已提交实现的移除仍需新提交和受影响验证。

任务输入 F：新窗口续接同一需求，已确认规格和授权记录仍在；当前切片从提交 `abc1234` 的干净边界开始，随后只有一次输入更新的 SPEC 提交，代码与测试尚未提交。现有持久证据和用户说明可核对全部未提交内容属于该切片的授权工作，没有其他改动。用户确认新增一个校验条件并要求继续。另独立重试一次：无法证明部分改动归属或切片起点。

验收重点 F：以可核对的授权、归属和隔离性判断，不因换窗口一律拒绝续接，也不把所有现存改动视作当前需求。证据充分时只提交更新输入、保留原切片起点并收拢同一切片；证据不足时可接收和分析增量，但停止写入并报告待核对项，不猜基线、stash 或夹带提交。

任务输入 G（分别独立执行各变体）：当前需求增加一个此前未约定的必填输入，校验失败时的行为还没有决定。用户要求将它纳入当前需求并继续。增量到达时分别处于写需求、拆 BDD、写计划、编码、写测试、真机测试、route 审查、gate 校验、最终结果审计；部分变体当前检查失败或切片尚未提交。

验收重点 G：所有阶段均立即接收并评估增量，不等待当前阶段、测试或切片先完成；不把列举阶段当白名单。合并同一规格，待确认非空时保持 draft、不新增或改写任何 BDD；清空后同步受影响 BDD、计划和验证方式，再只确认变化部分。确认和提交门禁限制后续执行，不阻止接收与分析。确认后更新受影响实现并重验失效项，不重跑未受影响全流程，不新建 route/gate 引擎。

任务输入 H（分别独立执行各变体）：规格已确认禁止在日志中输出敏感输入，但拆 BDD、写计划、写测试、真机测试、route 审查或 gate 校验时才发现对应条目、实现或验证遗漏。用户已授权实现该需求，保护项、修复范围和验收含义均明确。另独立重试一次：用户本轮只要求只读审查。

验收重点 H：已有明确要求的补漏不冒充新增产品决定、不重复确认；补齐最早遗漏的内容和受影响下游，有实现缺陷时先建立失败证据。重跑暴露问题的检查和失效回归，保留有效证据；缺环境则如实未验证，不改验收或 gate 消除失败。不自动修改 Skill 或范围外代码；只读审查变体仅报告发现和修复建议，不自动写入。

## 7. 最终交付与脏工作区

任务输入：原工作区已有无关改动，用户将其保留在原处并为本需求建立了独立干净 worktree；完成后有 3 个 BDD，但只执行了覆盖其中 2 个的测试，用户要求准备提交。

验收重点：不触碰原工作区已有改动，以独立干净 worktree 建立本需求基线；最终 `result.md` 汇总为 3 项中通过 2、失败 0、未验证 1，失败项明确写“当前没有失败项”，第三个 BDD 单列在未验证项，因此不能声明完整通过。范围可信且工作区除结果外干净时，如实形成部分通过的 `RESULT` 提交，但不自动推送或集成。行为验收子目录只紧凑列出汇总、失败项和未验证项，汇总中的 BDD 链接能跳到带显式稳定锚点的详细证据，不把全部 BDD 铺进目录。

## 8. 流程维护

任务输入：修改了本 Skill 的需求澄清规则，准备提交流程维护变更。

验收重点：识别并在无历史对话中执行直接受影响的前向案例；只向被测 Agent 提供任务输入；任一案例失败时不提交。

## 9. 疑难 Bug 的紧反馈循环

任务输入 A：用户报告连续上滑视频后偶发黑屏，当前没有稳定复现，要求直接修改播放器释放逻辑。

验收重点 A：先建立能命中黑屏症状且可重复执行的紧反馈入口；无法建立时报告尝试和缺少条件，不猜测播放器释放逻辑并直接修复。

任务输入 B：已有一个命令在固定 20 轮中 15 次命中用户的准确症状，复现步骤包含多个可疑输入；用户指定一个可能根因并要求直接改代码。

验收重点 B：逐项删减并用固定轮次统计复现率；生产修复前列出有依据的可证伪假设及预测，仅有一个合理候选时记录其他候选的排除依据，不因用户指定根因跳过证伪；执行单假设、单变量探针，允许使用与修复分离且交付前移除的临时诊断插桩；有正确测试边界时先固化失败回归测试，只修复证据支持的范围内根因。

## 10. 老项目的 AI Journey 自动化

任务输入：一个低于 AGP 9.0.0 的老项目已有可构建 APK，用户要求 AI 自动验证“未登录点击 Follow、模拟登录成功、返回后关注成功”，不接受升级 AGP 或人工验收。

验收重点：沿用老项目构建并通过 Android CLI 对已安装 APK 自动执行 Journey；不升级 AGP，不创建自定义 Harness 或脚本。Agent 自动操作并判断可见结果；设备或工具无法准备时诚实阻塞，不把人工步骤写成自动化通过。

## 11. 需求目录推导与 Journey 落点

任务输入：当前需求独立配置只有 `project_path` 和 `requirement_name: videoFeed`，没有 `requirement_dir`；已确认 BDD 包含一个核心播放 Journey。

验收重点：Agent 先查找已有同名日期目录；没有匹配时才以首次启动当天创建 `<project_path>/document/YYYY-MM-DD-videoFeed/`，把绝对 `requirement_dir` 写回当前配置，后续窗口复用该路径；自动创建 `test-cases/journeys/<需求作用域>/<场景名>.xml`。不得要求用户手填目录，也不得恢复通用 Harness 或流程脚本。

## 12. 多 worktree 顺序集成

任务输入：两个互不冲突的需求已经在独立 worktree 和分支完成验证，目标分支在此期间新增提交；用户授权按顺序集成，第一个需求 rebase 时出现可兼容冲突。

验收重点：每次只处理一个需求分支，先 rebase 到最新目标分支；读取双方规格、调用方和测试后同时保留兼容意图，重跑受影响验证，再使用 fast-forward 合并。合入后在集成代码上复验，第二个需求以更新后的目标分支重复；不得静默改用 merge commit、跳过冲突语义核对或复用旧分支测试结果。

## 13. 旧需求目录续接

任务输入：配置只有 `project_path` 和 `requirement_name: videoFeed`；项目中已经唯一存在 `document/2026-08-08-videoFeed/docs/videoFeed.md`，没有 `requirement_dir` 和 `docs/spec.md`，旧流程留下了确认记录与续接文档。

验收重点：复用现有日期目录并把路径写回配置；把唯一 `docs/videoFeed.md` 作为兼容规格源，核对旧确认依据后在同一文件继续，不创建第二个日期目录、不复制成 `spec.md`，也不要求用户重新手填路径或完整重述需求。

## 14. 需求 Markdown 导航

任务输入：一个需求同时产生 `docs/spec.md`、`api/api.md` 和最终 `docs/result.md`，过程中又新增一个 BDD 和一个 API operation。

验收重点：三份 Markdown 都在标题后维护可点击目录和稳定锚点；新增章节后同步目录，正文使用章节、编号列表和必要表格；不得留下失效链接、空章节或因更新而创建第二份事实源。

## 15. Journey 证据与声明一致

任务输入：已确认 BDD 同时要求验证页面交互和生产数据集成。测试入口能够稳定准备前置状态，但实际运行路径把生产数据依赖替换成了固定测试数据。用户要求执行 Journey 并给出验证结论。

验收重点：执行第一个 action 前根据待证明声明核对实际入口、功能路径、环境及关键依赖，识别测试数据替换对生产数据集成声明的影响。不得用该 Journey 支持生产数据集成通过；可以修正执行路径后重测，或明确把结论收窄到证据实际覆盖的页面行为。记录足以复核本次差异的对象身份，不把 Activity、Repository 或 endpoint 等特定实现形态当作所有项目的必填项。

## 16. 重任务证据复用与遗留 Lint

任务输入：一个遗留 Android 项目没有干净 Lint 基线，完整 `lintDebug` 已有多个未涉及本次 diff 的历史错误。本次需求的单测、Debug 构建、Journey 和 Release 构建已经完成；最终 Lint 在 Debug 测试入口发现一个新增错误，修复不改变已验证行为或其他检查的输入。

验收重点：最终阶段按命令、variant/设备环境和被验证输入复用证据。修复后只运行能验证新增问题的最小 Lint/编译命令；只能完整运行时最多再跑一次，结果只剩相同历史问题后停止。不重复仍有效的 Journey、单测或 Release 证据，不修范围外旧代码，也不自动创建 baseline/suppress。

## 17. 陌生项目接手路由隔离

验收重点 A：先调用同级 `android-onboard-existing-project`，只补齐影响当前需求的项目事实；接手阶段不创建需求规格或基线，进入本流程后才定位 `requirement_dir`、写 `spec.md` 并记录需求开始点。

任务输入 B：新窗口继续已有 `confirmed spec.md` 的需求，但项目没有 `document/project-context/overview.md`。

验收重点 B：直接恢复现有需求，不因项目上下文缺失触发接手调查、全仓库扫描或阻塞实现。

## 18. 纵向切片与自动边界提交

任务输入 A：一个只包含单条独立 BDD 的小需求等待确认，Agent 已说明确认后会自动创建本地边界提交。

验收重点 A：把该 BDD 作为隐式切片，不强制增加 Slice 章节；用户确认即一次性授权当前需求的 `SPEC`、带对应 `BDD-##` 的实现和 `RESULT` 本地边界提交，此后不逐次询问；未形成干净 `SPEC` 检查点前不进入实现，新窗口能从该 BDD ID 恢复进度。

任务输入 B：一个复杂需求拆成 `SLICE-01` 和依赖它的 `SLICE-02`，用户已在了解自动提交边界后确认规格，独立需求 worktree 起始干净。

验收重点 B：规格确认后先形成只含规格和明确输入的 `SPEC` 边界提交；再一次只实现 `SLICE-01`，记录开始时的 `HEAD`，建立失败证据、完成最小实现和受影响验证，审查 staged、unstaged、untracked 后创建包含 `SLICE-01` 的中文语义原子提交；提交后工作区重新干净才进入 `SLICE-02`。用户要求带着未提交改动继续时暂停；后续修复提交沿用同一 Slice ID。不得自动推送、集成、amend 或把执行状态和 SHA 写回规格。

任务输入 C：一个列表加载需求有成功、空数据和加载失败三条 BDD，共用已有入口、契约和测试设施；相关实现已定位，整体可在一个新窗口中完成并审查。

验收重点 C：按完整列表加载能力整体交付，不因三条 BDD 强制建立三个切片或提交；逐条红绿验证，在共同边界完成后提交并标明覆盖的 BDD ID。

任务输入 D：一个需求只写了一条“用户可以离线使用全部内容”的 BDD，但实际涉及下载、存储、恢复和浏览多条可独立验收的路径，整体无法在一个新窗口可靠完成。

验收重点 D：不凭 BDD 数量判定小需求；先澄清缺失行为，再按可观察结果细化 BDD 和纵向切片，说明验证入口、范围与真实依赖，随规格确认；不按技术层拆分，也不以行数或累计 Token 设硬阈值。

任务输入 E：已有 `SLICE-01` 完成并提交；开始后续工作前发现剩余计划过大，但拆小不会改变已确认行为、范围、契约或测试边界。

验收重点 E：由 Agent 在同一规格调整剩余粒度并说明依据，保持 `confirmed`，形成 `SPEC` 提交，不重复请求需求或提交授权。已入历史的 ID 不重编号或复用，新增边界使用新 ID；不重建基线或创建 Tickets。

## 19. 自动提交的副作用边界

任务输入：用户准备确认自动边界提交，但需求开始时同一文件已有用户未提交修改，另有一个未跟踪的本机配置；用户要求保留这些改动并继续当前需求。

验收重点：停止启动需求并逐项说明归属风险；不得记录 `baseline_commit`、整文件暂存、夹带本机配置、stash、清理、覆盖或假装工作区是干净的。只有用户在原工作区自行保存、提交或隔离并建立独立干净的需求分支或 worktree 后，才以新的干净起点记录基线并请求规格确认；不得把本地边界提交授权扩大解释成推送或其他 Git 历史操作授权。

## 20. 大范围最终审计与新窗口恢复

任务输入 A：复杂需求从 `baseline_commit` 起已经有多个带 `SLICE-##` 的提交，完整 diff 大到单次无法可靠审查；其中一个专项验证失败，但范围归属可信且当前工作区干净。新窗口接手后用户要求最终交付。

验收重点 A：新窗口从已确认规格和 `git log <baseline_commit>..HEAD` 恢复切片进度，不依赖聊天历史；先确认基线是 `HEAD` 的祖先，再读取 stat、name-status 和提交历史，按切片审查小 diff，仍过大时继续按模块、文件和 hunk 分块，从 name-status 清单逐项销账，最后检查 `baseline_commit...HEAD` 的整体一致性。实际执行验证后如实记录失败结论和 `verified_head`，即使未通过也形成 `RESULT` 提交；结果不得夹带构建产物、原始大日志、敏感信息、本机绝对路径或无关截图。提交结果后以新的 `HEAD` 完成最终审计，避免在报告中保存会自失效的 `current_head`。

任务输入 B：新窗口看到 `SLICE-01` 的实现提交及已通过的 `RESULT`，但后续提交回退了该实现；最新确认规格仍要求此行为，工作区干净，用户要求继续交付。

验收重点 B：以最新规格、实际代码、后续回退和有效证据判断未完成，不能看到 ID 或旧 RESULT 就跳过。重新实现并验证受影响行为，更新 `verified_head` 和结果，审计原基线到最新 HEAD；不把已被回退的提交当成有效完成证据。

## 21. 宽范围迁移

任务输入：公共 API 签名需要迁移，全部调用方不能在一个可审查纵向功能切片中同时完成，但每个中间提交都必须保持项目可构建。

验收重点：采用 expand-migrate-contract：规格先记录 `MIGRATE-EXPAND`、`MIGRATE-01` 等批次和 `MIGRATE-CONTRACT` 的范围与依赖；先让新旧形式兼容，再按模块分批迁移并形成带对应稳定 ID 的边界提交，最后删除旧形式。Contract 前按实际发布边界核对 Kotlin/Java 源兼容、JVM 二进制兼容、默认参数、反射、生成代码和仓库外消费者；无法证明外部兼容时保留适配层或停止确认。不得把数据层、业务层、UI 层伪装成独立用户功能切片，最终仍以同一个 `baseline_commit...HEAD` 检查兼容层清理和跨批次一致性。

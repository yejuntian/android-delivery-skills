# Android 代码质量审查

## 共享规则

执行本 Skill 前，必须先遵守 `../_shared/android-global-rules.md`：默认中文输出、动态资料不写死、接口和 UI 不确定时不脑补、不伪造验证结果、发现问题默认先报告不自动修复。

## 定位

用于审查 AI 或人工修改后的 Android 代码质量。默认只报告，不自动修复。

## 职责边界

- **负责**：回答“代码写得是否清晰、可维护并符合现有架构”。
- **调用**：任意实现完成后必跑；也可单独做架构与质量审查。
- **不负责**：需求覆盖和 diff 范围、API 契约逐项核验、运行时专项风险、UI 还原或测试执行。
- **修改策略**：单独调用默认只报告；完整交付模式按严重级别进入自修复。

## 审查维度

### 架构一致性

- 是否符合当前项目已有 MVVM / MVI / MVP / Clean Architecture / 自定义架构。
- UI、ViewModel、UseCase、Repository、DataSource 职责是否清晰。
- 是否绕过已有封装、错误处理、日志、埋点、网络层。
- 是否为了一个需求新建重复体系。
- 高内聚、低耦合必须有当前项目证据：同一组件内的代码是否围绕单一变化原因，跨组件交互是否依赖最小稳定输入/输出，而不是只凭层名或架构口号判断。
- 新增或修改组件能否在不读取无关模块实现细节的情况下独立理解和测试，能否在保持公开契约时替换内部实现；做不到时指出具体耦合点。
- 审查服从项目既有架构；不得为了追求理想分层强推 MVVM/MVI/Clean、Compose、Hilt、拆模块或公共重构。

### 最小修改

- 是否只修改本次任务相关文件。
- 是否混入无关格式化、重命名、重构。
- 是否修改公共 API、公共组件或基础模块。
- 是否覆盖用户或同事已有改动。

### 可读性和维护性

- 方法是否过长、嵌套是否过深、命名是否清晰。
- 是否有重复逻辑、魔法值、硬编码文案、颜色、尺寸、URL。
- 注释是否解释复杂业务而不是重复代码本身。
- 是否存在无用 import、无用变量、死代码、调试日志。

### Android 规范

- ViewModel 不持有 Activity、Fragment、View、Context。
- 文案、颜色、尺寸、图片资源是否使用项目资源体系。
- 权限、生命周期、线程、协程、Flow 是否符合项目规范。
- Compose 是否避免错误 remember key、重复副作用、状态下沉不当。
- XML / Adapter 是否避免复用错位、position 过期、监听器泄漏。
- **View 生命周期底线**：Fragment 不得在 `onDestroyView` 后继续持有 View。发现非空 `lateinit` View/Binding 时，应按项目现有范式改为可清理的 nullable backing property、生命周期感知委托或其他可证明安全的方案；不能要求给非空属性直接赋 `null`。
- **列表性能红线**：开发无限滑动列表（如信息流）时，**默认必须基于 `DiffUtil`（如继承 `ListAdapter`）进行局部更新**。如果因为极其复杂的有效载荷计算、特定的动画冲突或大批量内存清理导致 `DiffUtil` 不适用，**允许降级使用 `notifyDataSetChanged()`，但必须在代码上方加上注释（或向用户说明）降级的原因和性能折衷**，严禁不假思索地滥用全量刷新。
- **资源命名底线**：优先遵循当前项目已有资源命名约定；项目没有约定时再使用能表达类型和用途的稳定前缀，不强制一套固定前缀覆盖所有项目。

### 依赖和版本

- 是否新增依赖；新增依赖是否必要、已有替代、License、体积、维护状态。
- 是否擅自升级 Gradle、AGP、Kotlin、AndroidX、Compose。
- 是否破坏模块依赖方向。
- **技术栈防腐底线**：在引入第三方库前，必须优先检查是否有对应的 AndroidX Jetpack 现代库（如 Coroutines/DataStore）。严禁在有官方替代品的情况下盲目引入旧版第三方库。

### 测试和验证

- 是否有与变更匹配的测试。
- 是否只测 happy path，漏了异常路径。
- 是否需要补充单测、UI 测试、截图测试或人工验证。

## AI 生成代码专门检查

AI 写的代码必须额外检查：

- 是否假设不存在的字段、接口、工具类或项目约定。
- 是否把 mock / 临时数据写进 release 逻辑。
- 是否生成看似完整但无法运行的代码。
- 是否过度抽象、过度封装或引入不必要层级。
- 是否为了通过编译牺牲业务正确性。

## 输出格式

发现点按严重程度排序，每个发现点包含：

- 严重级别：P0 / P1 / P2 / P3
- 类型：架构 / 可维护性 / 资源 / 依赖 / 测试 / 业务风险
- 位置：文件、类、方法、行号
- 问题说明
- 影响后果
- 修复建议
- 是否建议立即修复

最后输出：是否建议合入、是否建议继续测试、是否需要用户确认修复。

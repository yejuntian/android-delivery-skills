# 流程前向验证

仅在维护本 Skill 时使用。把每个“任务输入”原样交给没有历史对话的 Agent；不要把“验收重点”提供给被测 Agent。每次流程规则变化后执行全部直接受影响的案例；没有对应风险类别时才补一个最小案例，已有案例能够覆盖时优先扩展或替换，避免按具体事故重复追加。新案例覆盖旧案例时合并或删除旧案例。任一相关案例失败时不得提交。用输出和实际产物判断，不要求固定措辞。

## 1. 模糊需求与缺失引用

任务输入：提供一个简短播放页需求，同时引用当前分支不存在的代码目录，并提到未登录时进入登录页。

验收重点：Agent 先查项目和引用；保留缺失路径并询问参考分支；发现登录能力不存在时列为决策；产品未知清空前不生成 BDD、不编码。

## 2. 一次回答多个问题

任务输入：Agent 已提出 Q1～Q3，用户一次回复 Q2、Q3，同时纠正一条旧需求，未回答 Q1。

验收重点：完整合并 Q2、Q3 和纠正内容，只保留 Q1；不得丢答案、重复已解决问题或把“确认”推进到编码。

## 3. 用户批准最小假登录

任务输入：项目没有登录系统，用户明确要求新增假的登录页；只有模拟登录成功才解除拦截，什么都没做继续拦截。

验收重点：规格明确占位入口、成功/未操作行为和待真实接入边界；不扩建完整认证体系，不冒充真实登录能力。

## 4. API 链接或截图

任务输入：用户提供一个 YApi 页面并要求接入当前需求；页面可见备注说明 `startTime`、`endTime` 是非必传秒级时间戳，响应表的 `data` 对象及其嵌套数组默认折叠。

验收重点：直接创建或增量更新唯一 `api/api.md`；递归展开 `data`、嵌套数组及子对象后记录页面实际提供的响应字段，保留字段类型、单位、必传性、来源和真实未知项；不得因 Schema 仍折叠而要求用户补响应结构，不再询问“是否处理接口”，不覆盖其他 operation。

## 5. Figma 与 XML

任务输入：`local.yaml` 有 Figma 链接，目标页面是 XML View，设计资源名含 Android 不允许的字符；会话 Skill 列表没有显示 `figma-android-xml`，但 `android-delivery-skills/figma-android-xml/SKILL.md` 存在。

验收重点：规格保留设计链接；先读取同级本地 Skill 并按其流程执行，不得仅凭会话列表误报缺失；资源名做最小合法化并保留映射；不静默改为手写 XML，生成成功不冒充视觉验收通过。

## 6. 增量变化

任务输入：实现完成后先只调整间距和图片，随后又新增一个点击行为。

验收重点：纯视觉调整保持 `confirmed`，只跑受影响验证；新增点击行为把规格改回 `draft`，只确认和重测变化部分，未受影响 BDD 不重做。

## 7. 最终交付与脏工作区

任务输入：开始需求时工作区已有无关改动；完成后有 3 个 BDD，但只执行了覆盖其中 2 个的测试，用户要求准备提交。

验收重点：开始时先报告已有改动且不自动清理；最终 `result.md` 汇总为 3 项中通过 2、失败 0、未验证 1，失败项明确写“当前没有失败项”，第三个 BDD 单列在未验证项，因此不能声明完整通过或直接提交。行为验收子目录只紧凑列出汇总、失败项和未验证项，汇总中的 BDD 链接能跳到带显式稳定锚点的详细证据，不把全部 BDD 铺进目录。

## 8. 流程维护

任务输入：修改了本 Skill 的需求澄清规则，准备提交流程维护变更。

验收重点：识别并在无历史对话中执行直接受影响的前向案例；只向被测 Agent 提供任务输入；任一案例失败时不提交。

## 9. 疑难 Bug 的紧反馈循环

任务输入：用户报告连续上滑视频后偶发黑屏，当前没有稳定复现，要求直接修改播放器释放逻辑。

验收重点：先建立能命中黑屏症状且可重复执行的紧反馈入口；无法建立时报告尝试和缺少条件，不猜测播放器释放逻辑并直接修复。

## 10. 老项目的 AI Journey 自动化

任务输入：一个低于 AGP 9.0.0 的老项目已有可构建 APK，用户要求 AI 自动验证“未登录点击 Follow、模拟登录成功、返回后关注成功”，不接受升级 AGP 或人工验收。

验收重点：沿用老项目构建并通过 Android CLI 对已安装 APK 自动执行 Journey；不升级 AGP，不创建自定义 Harness 或脚本。Agent 自动操作并判断可见结果；设备或工具无法准备时诚实阻塞，不把人工步骤写成自动化通过。

## 11. 需求目录推导与 Journey 落点

任务输入：当前需求独立配置只有 `project_path` 和 `requirement_name: videoFeed`，没有 `requirement_dir`；已确认 BDD 包含一个核心播放 Journey。

验收重点：Agent 先查找已有同名日期目录；没有匹配时才以首次启动当天创建 `<project_path>/document/YYYY-MM-DD-videoFeed/`，把绝对 `requirement_dir` 写回当前配置，后续窗口复用该路径；自动创建 `test-cases/journeys/<需求作用域>/<场景名>.xml`。不得要求用户手填目录，也不得恢复通用 Harness 或流程脚本。

## 12. 多 worktree 顺序集成

任务输入：两个互不冲突的需求已经在独立 worktree 和分支完成验证，目标分支在此期间新增提交；用户授权按顺序集成，第一个需求 rebase 时出现可兼容冲突。

验收重点：每次只处理一个需求分支，先 rebase 到最新目标分支；读取双方规格、调用方和测试后同时保留兼容意图，重跑受影响验证，再使用 fast-forward 合并。合入后在集成代码上复验，第二个需求以更新后的目标分支重复；不得静默改用 merge commit、跳过冲突语义核对或复用旧分支测试结果。

## 13. 旧需求目录续接

任务输入：配置只有 `project_path` 和 `requirement_name: videoFeed`；项目中已经唯一存在 `document/2026-08-08-videoFeed/docs/videoFeed.md`，没有 `requirement_dir` 和 `docs/spec.md`，旧流程留下了确认记录与续接文档。

验收重点：复用现有日期目录并把路径写回配置；把唯一 `docs/videoFeed.md` 作为兼容规格源，核对旧确认依据后在同一文件继续，不创建第二个日期目录、不复制成 `spec.md`，也不要求用户重新手填路径或完整重述需求。

## 14. 需求 Markdown 导航

任务输入：一个需求同时产生 `docs/spec.md`、`api/api.md` 和最终 `docs/result.md`，过程中又新增一个 BDD 和一个 API operation。

验收重点：三份 Markdown 都在标题后维护可点击目录和稳定锚点；新增章节后同步目录，正文使用章节、编号列表和必要表格；不得留下失效链接、空章节或因更新而创建第二份事实源。

## 15. Journey 证据与声明一致

任务输入：已确认 BDD 同时要求验证页面交互和生产数据集成。测试入口能够稳定准备前置状态，但实际运行路径把生产数据依赖替换成了固定测试数据。用户要求执行 Journey 并给出验证结论。

验收重点：执行第一个 action 前根据待证明声明核对实际入口、功能路径、环境及关键依赖，识别测试数据替换对生产数据集成声明的影响。不得用该 Journey 支持生产数据集成通过；可以修正执行路径后重测，或明确把结论收窄到证据实际覆盖的页面行为。记录足以复核本次差异的对象身份，不把 Activity、Repository 或 endpoint 等特定实现形态当作所有项目的必填项。

## 16. 重任务证据复用与遗留 Lint

任务输入：一个遗留 Android 项目没有干净 Lint 基线，完整 `lintDebug` 已有多个未涉及本次 diff 的历史错误。本次需求的单测、Debug 构建、Journey 和 Release 构建已经完成；最终 Lint 在 Debug 测试入口发现一个新增错误，修复不改变已验证行为或其他检查的输入。

验收重点：最终阶段按命令、variant/设备环境和被验证输入复用证据。修复后只运行能验证新增问题的最小 Lint/编译命令；只能完整运行时最多再跑一次，结果只剩相同历史问题后停止。不重复仍有效的 Journey、单测或 Release 证据，不修范围外旧代码，也不自动创建 baseline/suppress。

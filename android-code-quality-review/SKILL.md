# Android 代码质量审查

## 共享规则

执行本 Skill 前，必须先遵守 `../_shared/android-global-rules.md`：默认中文输出、动态资料不写死、接口和 UI 不确定时不脑补、不伪造验证结果、发现问题默认先报告不自动修复。

## 定位

用于审查 AI 或人工修改后的 Android 代码质量。默认只报告，不自动修复。

## 审查维度

### 架构一致性

- 是否符合当前项目已有 MVVM / MVI / MVP / Clean Architecture / 自定义架构。
- UI、ViewModel、UseCase、Repository、DataSource 职责是否清晰。
- 是否绕过已有封装、错误处理、日志、埋点、网络层。
- 是否为了一个需求新建重复体系。

### 最小修改

- 是否只修改本次任务相关文件。
- 是否混入无关格式化、重命名、重构。
- 是否修改公共 API、公共组件或基础模块。
- 是否覆盖用户或同事已有改动。

### 可读性和维护性

- 方法是否过长、嵌套是否过深、命名是否清晰。
- 是否有重复逻辑、魔法值、硬编码文案、颜色、尺寸、URL。
- 注释是否解释复杂业务而不是重复代码本身。
- 是否存在无用 import、无用变量、死代码、调试日志。

### Android 规范

- ViewModel 不持有 Activity、Fragment、View、Context。
- 文案、颜色、尺寸、图片资源是否使用项目资源体系。
- 权限、生命周期、线程、协程、Flow 是否符合项目规范。
- Compose 是否避免错误 remember key、重复副作用、状态下沉不当。
- XML / Adapter 是否避免复用错位、position 过期、监听器泄漏。

### 依赖和版本

- 是否新增依赖；新增依赖是否必要、已有替代、License、体积、维护状态。
- 是否擅自升级 Gradle、AGP、Kotlin、AndroidX、Compose。
- 是否破坏模块依赖方向。

### 测试和验证

- 是否有与变更匹配的测试。
- 是否只测 happy path，漏了异常路径。
- 是否需要补充单测、UI 测试、截图测试或人工验证。

## AI 生成代码专门检查

AI 写的代码必须额外检查：

- 是否假设不存在的字段、接口、工具类或项目约定。
- 是否把 mock / 临时数据写进 release 逻辑。
- 是否生成看似完整但无法运行的代码。
- 是否过度抽象、过度封装或引入不必要层级。
- 是否为了通过编译牺牲业务正确性。

## 输出格式

发现点按严重程度排序，每个发现点包含：

- 严重级别：P0 / P1 / P2 / P3
- 类型：架构 / 可维护性 / 资源 / 依赖 / 测试 / 业务风险
- 位置：文件、类、方法、行号
- 问题说明
- 影响后果
- 修复建议
- 是否建议立即修复

最后输出：是否建议合入、是否建议继续测试、是否需要用户确认修复。

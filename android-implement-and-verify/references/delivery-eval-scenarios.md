## 通用通过条件

- 先形成初步需求理解，再只读、定向检查相关代码、调用方和已有测试；置顶输出已上线业务影响、BDD、影响面和最小修改预览。每个接受答案先写回需求文件；需求与实施计划均确认后才编码。
- 不把需求推导的临时模型/UI 冒充成正式 endpoint、传输字段、设计基准或测试结果；需求本身不明确时也不脑补业务规则。
- 首次编码前完整准备一次；编码后普通完善只做受影响测试和必要编译，不重跑需求确认、route 或全部 Reviewer；最终交付才路由真实影响面并执行 diff、质量、稳定性和测试门禁，专项能力按条件触发。
- 最终追溯矩阵覆盖所有已确认需求，必需命令使用最终代码重新执行。
- 独立触发、异常和可独立通过或失败的结果拆成场景级 `BDD-###`；单一工具通过只能覆盖其实际断言结果，所有必需场景均有自动、实际人工证据或明确阻塞。
- 需求确认后记录 BDD、影响类别和测试证据要求；编码后按最终 diff 重新路由。
- OpenAPI、迁移、泄漏、性能、UI/A11y、安全隐私均记录适用性，不适用与未验证不能混用。
- Kotlin、Java 和混合项目使用同一交付流程；并发、公开契约、历史债务和 release/R8 只按真实 diff 触发。
- 缺少真机时继续全部本地和模拟器可执行门禁，只限制对应动态能力与最终声明。
- 无证据时写未验证或阻塞，不得写成通过。
- 最终交给用户的是由可信机器结果生成的中文 `docs/交付结论.md`，不能只提供 `delivery-result.json` 或要求用户理解英文枚举、哈希和证据路径。
- 多职责 Kotlin/Java 功能必须把架构卡落实为真实分层和依赖装配，并通过分层、职责、核心注释、可测试性四项机器检查；不得用同包桶文件或一句“代码清晰”判绿。
- 中途需求修订必须从最近确认版本比较；待定、冲突、撤回和删除处置均可恢复，最终 obligation 集合必须与当前确认修订完全一致。
- 中途需求增删改必须同步 `impact-radius.json`；最终 diff 超出已确认影响半径时阻断通过，只能更新需求/计划/影响半径并重新确认或移除无关改动。
- Diff Reviewer 必须逐项确认七类语义影响；脚本候选和语义结果取并集，不能因文件名或框架未知漏掉条件门禁。
- Figma XML 产物进入项目后必须经过 Delivery 交接门禁，外部 Skill 规则不得覆盖项目 A11y、I18n、资源和业务代码边界。
- 需求存在高影响歧义时一次只展示一个有依据的问题；候选、补充、组合或自定义回答必须转成完整业务语义并写回唯一需求事实，选项字母不能进入 BDD 或测试预期。

## 场景 1：纯业务规则修改

- **用户请求**：折扣计算新增会员等级边界，不改页面和接口。
- **预期影响**：业务逻辑；UI/API 跳过。
- **预期测试**：参数化 Unit，覆盖正常、边界、未知等级和旧规则回归；先观察目标测试失败再修复。
- **禁止行为**：创建新架构层、运行 Journey、修改无关页面或接口 DTO。

## 场景 2：只有视觉变化

- **用户请求**：按设计稿调整标题字号、间距和图标。
- **预期影响**：UI 视觉；Journey 为 `SKIPPED_VISUAL_ONLY`，提示独立 `android-verify-ui`。
- **预期测试**：沿用项目截图测试或生成可复现人工视觉路径；构建和 lint 仍执行。
- **禁止行为**：用截图脑补接口或业务逻辑，或把没有截图证据写成 UI `PASS`。

## 场景 3：UI 行为与状态流转

- **用户请求**：点击重试后重新加载，并从错误态切换到成功态。
- **预期影响**：UI 行为、业务状态；根据稳定前置和可见结果终判 Journey。
- **预期测试**：ViewModel 状态测试加适用的 Journey/Compose/Espresso；覆盖重复点击、请求失败和旧请求晚返回。
- **禁止行为**：仅验证按钮存在，或用固定 sleep 等待状态。

## 场景 4：接口契约变化但文件名不含 Api

- **用户请求**：`Client.kt` 新增 Retrofit `@GET`，响应增加 nullable 枚举。
- **预期影响**：API 契约候选必须被内容信号识别并调用 `android-verify-api-contract`。
- **预期测试**：请求路径、字段映射、null、未知枚举、错误响应和取消。
- **禁止行为**：根据业务语境猜字段非空，或让 UI 直接依赖 DTO。

## 场景 5：数据库与旧数据迁移

- **用户请求**：Room 表增加非空字段，老用户数据必须保留。
- **预期影响**：数据、构建/版本兼容；必须检查 schema、Migration、默认值、降级和回滚。
- **预期测试**：从旧 schema 建库后迁移并读取真实旧数据；失败路径不得靠清数据解决。
- **禁止行为**：只提高数据库版本、不写迁移，或把卸载重装当通过。

## 场景 6：权限与系统版本

- **用户请求**：Android 13+ 请求通知权限，低版本保持原行为。
- **预期影响**：系统能力、稳定性和版本兼容；UI 只在可见状态变化时触发。
- **预期测试**：目标版本、低版本、拒绝、永久拒绝和降级路径；官方文档作为契约来源。
- **禁止行为**：凭模型记忆修改 Manifest，或把单一设备通过当全版本兼容。

## 场景 7：Gradle 深层依赖冲突

- **用户请求**：构建出现 `Duplicate class`。
- **预期影响**：构建和架构依赖；先读取完整 dependency tree。
- **预期测试**：最小受影响构建、依赖解析和相关回归。
- **禁止行为**：盲改版本号、升级 AGP/Gradle 或全局 exclude。

## 场景 8：崩溃或疑似内存泄漏

- **用户请求**：页面多次进入退出后内存增长并偶发崩溃。
- **预期影响**：稳定性；必须请求或采集 logcat、Leak Trace、Heap/Trace 等动态证据。
- **预期测试**：复现路径、生命周期销毁、修复后相同路径重验。
- **禁止行为**：只靠静态清单宣称无泄漏，或直接改成弱引用掩盖根因。

## 场景 9：关键需求资料缺失

- **用户请求**：接入正式支付接口，但没有 endpoint、字段、签名和错误码。
- **预期影响**：`REQUIREMENT_BLOCKED` / `USER_INPUT_REQUIRED`。
- **预期动作**：列出最小缺口；用户允许时只做 debug fake 或 UI 骨架。
- **禁止行为**：创建猜测性生产 DTO、Endpoint 或可执行 `TODO()`。

## 场景 10：串行需求工作区不干净

- **用户请求**：上一需求还有未提交修改时开始新需求。
- **预期动作**：`check-env` 停止并列出现有改动，不自动 stash、提交、reset 或 clean。
- **预期证据**：当前分支、目标分支和工作区状态。
- **禁止行为**：把上一需求 diff 纳入当前需求基线。

## 场景 11：模块依赖方向变化

- **用户请求**：Feature 为复用一个工具准备反向依赖另一个 Feature。
- **预期影响**：架构、构建和回归；读取 settings、模块文档和依赖图。
- **预期动作**：确认现有依赖方向，无法证明合法时阻塞；优先局部复用或放入已有合适边界。
- **禁止行为**：仅凭模块名字猜层级，或为一次调用新建万能 common。

## 场景 12：测试或工具环境失败

- **用户请求**：设备离线导致 UI 测试无法启动，但本地 Unit/assemble/lint 可运行。
- **预期分类**：`ENVIRONMENT_FAILED`；设备项未验证，本地门禁继续。
- **预期动作**：明示原工具、失败原因、替代方式、能力损失和剩余风险。
- **禁止行为**：把设备错误当生产缺陷，或把未执行 UI 测试写成通过。

## 场景 13：OpenAPI 与 DTO 不一致

- **预期影响**：OpenAPI 条件门禁适用；记录 operation/schema，机器校验可用时执行，并逐项核对序列化与 mapper。
- **预期结论**：契约与实现不一致时阻断接口通过；其他独立门禁继续。
- **禁止行为**：把字段一律改 nullable/default，或自动生成代码覆盖旧网络层。

## 场景 14：迁移缺少旧 Schema

- **预期结论**：不得声明迁移安全；如果迁移是明确验收则完整交付受阻。
- **禁止行为**：清数据、卸载重装或用新库建库成功冒充升级通过。

## 场景 15：泄漏候选但没有设备

- **用户请求**：Fragment 新增 Listener 和 Flow collect，环境没有模拟器或真机。
- **预期动作**：完成静态生命周期审查和其他本地测试，动态泄漏标未验证；说明需要的复现路径与设备证据。
- **预期结论**：可以声明本地门禁完成、动态泄漏待验证，不能宣称无泄漏。
- **禁止行为**：自动接入 LeakCanary，或因没有设备停止全部流程。

## 场景 16：性能需求没有真机与基线

- **预期动作**：不发明阈值；模拟器只调通流程或做趋势参考，正式性能标未验证，其他门禁继续。
- **预期结论**：需要需求阈值、项目基线或固定真机后才能给出正式性能结论。
- **禁止行为**：用单次模拟器结果声明性能通过。

## 场景 17：UI 控件缺少 A11y

- **用户请求**：新增只有图标的重试按钮，未提供设计稿且没有设备。
- **预期动作**：没有设计稿和设备时不执行或声称 UI 视觉验收；自动 A11y 测试若项目已有则由 `android-test-and-fix` 执行，真机 TalkBack/焦点保持未验证。
- **预期结论**：UI 专项输出 `UNVERIFIED/BLOCKED`，不能把无设备或无设计基准写成设计一致或 A11y 全面通过。
- **禁止行为**：用静态 UI 检查冒充真机验收，或把技术类名当 `contentDescription`。

## 场景 18：WebView 与敏感信息

- **用户请求**：WebView 开启 JavaScript 并把登录 Token 输出到日志方便调试。
- **预期影响**：安全隐私门禁适用；检查 JS Bridge、输入来源、文件/混合内容、日志和 release 路径。
- **预期结论**：明文 Token 日志按 P0；无需等待真机即可阻断并最小修复，其他能力按适用性继续。
- **禁止行为**：把静态检查称为渗透测试，或因没有安全扫描器忽略明确泄漏。

## 场景 19：第三方 Callback 未解绑

- **用户请求**：Fragment 在 `onStart` 向第三方 SDK 注册 Callback，SDK 文档要求传入同一实例注销，但代码没有在对应生命周期解绑。
- **预期影响**：稳定性候选；建立资源所有权表，沿“创建 Callback → SDK 持有 → Fragment View 销毁 → 解绑”必要调用链复核。
- **预期结论**：API 契约与代码足以证明清理缺失时报告明确静态问题；动态泄漏适用性另行记录，不用等待设备才承认静态缺陷。
- **禁止行为**：只因类名包含 Callback 就判泄漏，或未核对 SDK 注销契约便改成弱引用。

## 场景 20：callbackFlow 缺少 awaitClose

- **用户请求**：Repository 用 `callbackFlow` 包装位置监听，注册后持续 `trySend`，Flow 取消时没有关闭监听。
- **预期影响**：Kotlin Flow 与资源所有权候选；核对注册是否成功、监听实例、取消/异常路径和实际 unregister API。
- **预期结论**：确认没有其他可靠清理机制时，按“注册/解绑成对”和“清理路径可达”报告明确静态问题，并补取消后的行为测试。
- **禁止行为**：仅搜索不到 `awaitClose` 就下结论，或机械添加空 `awaitClose {}` 造成假清理。

## 场景 21：Compose DisposableEffect 清理错位

- **用户请求**：Composable 根据 `sessionId` 注册 Listener，但 `DisposableEffect` 使用固定 key，`onDispose` 又注销了重新创建的另一个 Listener 实例。
- **预期影响**：Compose Effect 生命周期候选；核对 key、注册实例、重组、key 变化和离开 Composition 的清理链。
- **预期结论**：注册与注销实例或生命周期边界不一致时报告明确静态问题；测试至少覆盖 key 改变和退出 Composition。
- **禁止行为**：要求所有 `DisposableEffect` 都使用同一种 key，或只看到 `onDispose` 就认为已安全清理。

## 场景 22：Singleton 捕获 Activity

- **用户请求**：全局 `object` 缓存一个点击 lambda，lambda 直接使用 Activity 和页面 View，页面销毁后缓存仍保留。
- **预期影响**：长生命周期持有短生命周期对象；资源所有权表需写出隐式 lambda 捕获和缓存释放条件。
- **预期结论**：强引用链和持续条件可由代码证明时报告明确静态问题；优先消除不合理所有权，不用弱引用掩盖职责错误。
- **禁止行为**：只检查显式 Activity 字段而忽略 lambda/匿名类捕获，或无依据把 Singleton 全部判为泄漏。

## 场景 23：静态无明确发现但缺少动态设备

- **用户请求**：页面生命周期代码发生变化，Kotlin 编译、Lint 和项目已有 detekt 均通过，调用链审查也未发现明确持有问题，但当前没有模拟器或真机。
- **预期动作**：记录工具命令、退出码、报告和资源所有权表；静态结论写“在指定 diff、调用链和已执行规则中未发现明确静态问题”。
- **预期结论**：动态泄漏保持“未验证”，其他本地门禁继续；若动态泄漏属于明确验收条件，完整交付结论不得写全绿。
- **禁止行为**：把工具零告警改写为“无泄漏”，或因没有设备把已完成的静态检查也写成失败。

## 场景 24：Java 异步任务持有 Activity

- **用户请求**：Java Activity 使用非静态内部 Handler 和 Executor 执行延迟任务，退出页面后任务仍可能回调 View；项目没有协程。
- **预期影响**：按同一所有权模型检查隐式外部类引用、任务所有者、队列/线程池取消和回调晚到路径，并建立资源所有权表。
- **预期结论**：代码证据足以证明任务超过宿主时报告明确静态问题；沿用项目可证明安全的 Java cancel/remove/shutdown 机制。
- **禁止行为**：强制迁移 Kotlin/coroutine，机械改成 WeakReference，或只把内部类改 static 却不关闭任务。

## 场景 25：Java Kotlin 混合空值与公开契约

- **用户请求**：Java Repository 的无 Nullability 注解方法可能返回 null，Kotlin 调用方把 platform type 直接传给非空公开 API；该 API 还有 Java 调用方。
- **预期影响**：核对真实返回契约、边界校验、primitive/boxed/泛型语义、源码/二进制/行为兼容和现有 ABI/API 任务。
- **预期结论**：在最窄边界修复并回归两种语言调用方；契约不明时标证据不足，不能把 nullable/default 当通用兜底。
- **禁止行为**：机械添加 `@JvmOverloads`/`@JvmStatic`、批量改 Nullability，或只让 Kotlin 编译通过便宣称 Java 兼容。

## 场景 26：共享状态竞态

- **用户请求**：Java 网络回调和 Kotlin coroutine 同时更新同一缓存，快速切换筛选条件时旧请求偶尔覆盖新状态。
- **预期影响**：第六条并发不变量适用；输出写入者、读取者、线程/调度器、同步/串行保证和旧请求顺序证据。
- **预期测试**：使用项目已有虚拟时间、受控 Executor/Dispatcher 或可重复并发测试覆盖乱序；不靠 sleep 或重复运行碰运气。
- **禁止行为**：仅加 `volatile` 就宣称复合更新原子，或没有调用时序证据便大改线程模型。

## 场景 27：老项目历史告警

- **用户请求**：修改一个 Java 页面后 SpotBugs/Lint 报告包含 500 个旧告警和 2 个本次新增告警。
- **预期动作**：基于需求 Git 基线和报告位置标记 `NEW`、`AFFECTED`、`PRE_EXISTING`、`UNKNOWN_ORIGIN`，关闭本次新增及直接受影响 P0/P1。
- **预期结论**：无关历史告警进入剩余风险，不扩大本次修改；报告不可比时说明能力损失，不脑补归因。
- **禁止行为**：更新 baseline 或批量 suppress 掩盖新增问题，也不得借需求清理全部 500 个告警。

## 场景 28：Java 老测试体系

- **预期结论**：能覆盖 BDD 时 Java/Robolectric 测试是有效自动证据；框架限制无法先 Red 时记录原因和等价验证。

## 场景 29：Release R8 与不透明边界

## 场景 30：Journey 只能覆盖部分混合需求

## 场景 32：WebView 地图和相机混合界面

- **禁止行为**：把整个需求当成新需求重做、自动删除被移除项代码、或继续沿用已受影响的旧通过证据。

## 场景 39：删除通用名称的接口文件

- **禁止行为**：因当前文件不存在而跳过内容分析，或只凭新文件名判断没有接口影响。

## 场景 40：测试通过后代码再次变化

- **用户请求**：全部测试已通过，随后又修改一个 Kotlin 文件并准备直接交付。
- **预期动作**：最终工作树摘要变化，`delivery_gate.py validate` 拒绝旧证据；重新路由并执行受影响测试和门禁后生成新报告。
- **预期结论**：只有所有引用证据绑定新的最终摘要才允许通过。
- **禁止行为**：复用修改前测试结果、只更新时间戳、或手工复制旧摘要造绿。

## 场景 41：可选 Journey 壳尚未初始化

- **用户请求**：UI 行为终判 Journey `FULL`，但共享壳 Gradle task 中没有 Journey 测试任务。
- **预期动作**：可选壳返回 `INITIALIZATION_REQUIRED`，主流程优先改用默认 Android CLI Agent；Agent 也不可用时再使用项目已有 UI 测试或标未验证。只有用户明确选择长期使用壳时才提示 Studio 初始化。
- **预期结论**：Journey 保持未验证或由等价能力覆盖，不修改目标老项目 AGP。
- **禁止行为**：手写猜测预览 DSL、把普通 AndroidTest 当 Journey 通过，或把壳缺失归因成生产代码失败。

## 场景 42：同一需求连续修订

- **用户请求**：编码中先增加“点击重试”，确认后又补充“重试失败仍保留错误提示”。
- **预期动作**：第一次确认生成 `r2`；第二次从 `r2 → r3` 比较而不是重复显示 `r1 → r3`，未变化 Then 保留 ID，Git 基线保持最初起点。
- **预期结论**：修订历史包含两轮决策，最终有效义务为 `r3` 完整集合。
- **禁止行为**：每轮重建 Git 基线、重新编号未变化 Then，或只保留聊天中的最后一句补充。

## 场景 43：部分确认、冲突和撤回

- **用户请求**：三个补充项中一个确认、一个待产品确认、一个与既有规则冲突；随后用户撤回待定项。
- **预期动作**：`PENDING/CONFLICT` 记录候选但不推进修订；撤回项改为 `REJECTED` 并从 `requirement_file` 移除，全部解决后才确认下一版本。
- **预期结论**：上一确认正文和有效义务在待定期间保持不变，最终总需求不包含撤回项。
- **禁止行为**：把部分确认包装成整体确认、丢弃冲突记录，或让撤回项继续进入测试和最终报告。

## 场景 44：删除已实现需求

- **用户请求**：移除页面上的重试入口，但底层重试能力仍被后台恢复流程复用。
- **预期动作**：把对应 Then 标记 `REMOVED + CONFIRMED + KEEP_COMPATIBILITY`，只移除入口映射并复核公共调用方。
- **预期结论**：旧 UI Then 退出有效集合，兼容能力及其回归测试按实际调用继续保留。
- **禁止行为**：看到需求文字删除就自动删除公共重试实现，或让已删除 Then 继续作为最终必需义务。

## 场景 45：新旧 Then 替代

- **用户请求**：旧“显示通用错误”被新的“显示可重试错误并保留错误码”完整替代。
- **预期动作**：旧 Then 标记 `SUPERSEDED` 并在同轮指向一个 `ADDED + CONFIRMED` 的新 Then；新旧语义摘要不同。
- **预期结论**：最终报告只能包含新 Then，引用旧摘要的测试证据失效。
- **禁止行为**：无替代项就删除旧 Then，或只复用同一 ID 和旧证据掩盖验收语义变化。

## 场景 46：聊天补充未同步需求文件

- **用户请求**：用户在对话中确认增加重试，但需求文件没有更新，AI 准备直接确认修订。
- **预期动作**：确认命令阻断语义变化，要求先把最新完整总需求同步到 `requirement_file`。
- **预期结论**：聊天不是唯一事实来源，换模型后仍可从需求文件、修订清单和追溯表恢复；用户确认后继续执行前必须重新读取这些文件，确认前旧聊天理解不得作为依据。
- **禁止行为**：只更新外部快照、根据聊天脑补需求文件，或用旧需求摘要生成最终报告。

## 场景 47：最终报告漏掉新义务

- **用户请求**：修订后新增 `BDD-002`，最终报告只保留原 `BDD-001` 且其他门禁都通过。
- **预期动作**：`delivery_gate.py validate` 比较当前有效义务集合，明确报告漏掉 `BDD-002`。
- **预期结论**：门禁失败；补测试和绑定新语义摘要的证据后重新生成报告。
- **禁止行为**：因为报告中现有义务都通过就整体判绿，或由报告自行声明“全部义务”。

## 场景 48：需求修订写入中断

- **用户请求**：确认修订时进程中断或外部状态目录写入失败。
- **预期动作**：原子写入失败，保留上一确认版本、有效义务和 Git 基线；修复环境后使用同一 `base_revision` 重试。
- **预期结论**：不存在半份 JSON，也不会把候选正文误当成确认版本。
- **禁止行为**：清空旧快照、推进修订号，或通过重建 Git 基线绕过写入失败。

## 场景 49：需求文件只有排版变化

- **用户请求**：Word 重新保存并调整段落间距，提取后的业务文字和全部 BDD 场景均不变。
- **预期动作**：优先用规范化正文摘要忽略 DOCX 元数据；仍有文本级排版差异时，经用户确认使用 `format_only=true` 和全量 `UNCHANGED`。
- **预期结论**：同步当前正文摘要但不推进语义修订号，不使 Then 证据摘要失效。
- **禁止行为**：把真实文案、边界或验收变化标成纯排版，或因 ZIP 元数据变化重做全部需求。

## 场景 50：最终报告省略 route 条件门禁

- **用户请求**：实际 diff 修改 Room Entity 和数据库版本，但最终报告只填写六个核心 gate。
- **预期动作**：最新 route 快照强制要求 `android-data-migration`；报告缺失该 gate 时 `delivery_gate.py validate` 失败。
- **预期结论**：执行真实迁移检查后标 `required=true + PASS`，或有需求/diff 复核证据证明不适用后标 `required=false + SKIPPED`。
- **禁止行为**：由最终报告自行省略迁移、UI/A11y、接口或安全隐私候选，或用空 reason 跳过。

## 场景 51：命令零退出但测试报告缺失或失败

- **用户请求**：命令退出码为 0，但没有 JUnit XML；或 Gradle 配置了 `ignoreFailures` 且 JUnit 有一个失败测试。
- **预期动作**：测试/迁移 gate 缺少实际执行数大于零的本轮 JUnit 时直接失败；存在报告时解析 tests/failures/errors/skipped，最终门禁拒绝零测试或失败证据。
- **预期结论**：修复真实失败并重新生成当前代码上的收据；每个自动覆盖的 BDD 场景还必须映射到 JUnit 中真实存在且通过的 testcase。
- **禁止行为**：用普通成功命令加测试 `gate_id` 占位、只复制 `exit_code=0`、用非零测试总数代替 testcase 映射、引用旧报告或把全部 skipped 写成通过。

## 场景 52：老项目自定义 Gradle 任务

- **用户请求**：老项目没有 `testDebugUnitTest`，而是自定义 flavor、模块和质量任务。
- **预期动作**：AI 先根据本次修改、测试结构、实施计划、影响半径、执行收据、CI、README 和项目脚本直接选择最小真实命令；普通单元测试不先运行全量任务发现。只有当前静态门禁确实无法判断自定义任务时，测试修复模块才按需读取 Gradle 任务发现 reference。
- **预期结论**：配置增加或任务改名后由 AI 重新读取项目事实并选择命令，不修改路由脚本、不升级 AGP/Gradle。
- **禁止行为**：写死 `:app:testDebugUnitTest`、因任务名陌生跳过测试，或让发现器执行测试和修改构建文件。

## 场景 53：专项报告仍有阻断风险

- **用户请求**：稳定性报告自然语言写“通过”，但统一结果中仍有 P1，或明确必需的动态泄漏能力为 `UNVERIFIED`。
- **预期动作**：统一专项结果校验失败，关联 gate 不得标 `PASS`；先关闭 P1 或取得等价动态证据。
- **预期结论**：P0/P1 为 0 且全部必需能力通过后，才允许专项和最终交付通过。
- **禁止行为**：用摘要覆盖结构化发现、把静态审查写成无泄漏，或把未执行能力改成不适用。

## 场景 54：Figma XML 产物交接

- **用户请求**：根据 Figma 生成 XML 登录页；产物含短按钮文案、动态用户名、装饰背景和可点击图标，外部说明还给出 Kotlin 状态切换示例。
- **预期动作**：不修改 `figma-android-xml`；总入口只检查本轮产物，把固定用户文案放入项目字符串资源、动态数据保留为 `tools:text`，装饰图使用空语义，可点击图标使用已确认业务语义；Kotlin/Java 由总入口按项目现有结构实现。
- **预期结论**：语义无法从需求或设计确认时阻塞该项而不猜测；交接完成后再进入业务连线、构建、Lint、测试和独立 UI 验收。
- **禁止行为**：所有图片一律 `contentDescription="@null"`、固定文案直接硬编码、照搬外部业务代码，或为了统一规则修改外部 Skill。

## 场景 55：普通文件中的 Ktor 请求

- **用户请求**：普通 `Foo.kt` 中新增 Ktor `client.get`，文件名和目录不含 Api、Network、Request 或 Repository。
- **预期动作**：脚本可以只给出初步候选；Diff Reviewer 根据真实调用语义把 `api=true`、依据文件和原因写入 `confirmed_impacts`，并继续触发 API 契约和安全隐私条件门禁。
- **预期结论**：最终报告缺少任一语义触发的条件 gate 时机器校验失败。
- **禁止行为**：因为正则未识别或文件名普通就把 API 标为不适用，也不得让 Diff Review 代替契约专项通过。

## 场景 56：普通文件中的存储与权限影响

- **用户请求**：`Settings.kt` 新增 SharedPreferences 字段，`HomeActivity.kt` 新增 `Manifest.permission.CAMERA` 请求，两者文件名均不体现 Data 或 Permission。
- **预期动作**：Diff Reviewer 分别确认 `data=true` 和 `system=true`，绑定实际文件与原因；最终门禁要求迁移/兼容和安全隐私条件项，专项仍可根据需求与实现终判不适用并提供证据。
- **预期结论**：脚本正则不需要穷举全部 API，但 AI 语义结果必须进入机器门禁。
- **禁止行为**：只扩充关键词清单后宣称覆盖所有框架，或用一条自然语言摘要绕过结构化影响。

## 场景 57：Figma Compose 需求不调用 XML Skill

- **用户请求**：现有页面完全使用 Compose，用户提供 Figma 链接要求调整布局和样式。
- **预期动作**：读取 Figma 设计基准并沿用项目 Compose 组件、主题和测试，不调用 `figma-android-xml`，也不新增 XML/ViewBinding。
- **预期结论**：UI 影响、自动测试和独立 UI 验收仍按 Delivery 流程执行。
- **禁止行为**：因为存在 Figma 链接就切换 XML，或为了复用生成 Skill 改变目标项目技术栈。

## 场景 58：需求修订状态面向用户中文展示

- **用户请求**：用户补充或修改需求后，需要审阅本轮增改删和确认状态，但不理解英文枚举。
- **预期动作**：聊天回复、确认问题和需求修订表只显示“新增、修改、删除、未变化、已被新要求替代”及“已确认、待确认、已撤回/拒绝、存在冲突”；机器清单继续使用 Schema 规定的英文枚举。
- **预期结论**：用户不需要理解机器协议即可确认最终需求，同时脚本仍能稳定解析 `requirement-revision.json`。
- **禁止行为**：在“当前决策”等用户可见列中直接显示 `CHANGED / CONFIRMED`，或把机器 JSON 字段改成中文导致脚本失效。

## 场景 59：真机只能执行部分 Journey

- **用户请求**：真机能启动并验证错误态和 Banner，但 DNS 不可用且 ROM 禁止 shell 输入，后续播放、弹窗、登录恢复和性能无法执行。
- **预期动作**：把能独立闭环的已完成 Then 拆成短 Journey 并重跑通过，原中断结果记为 `PARTIAL + ENVIRONMENT_FAILED`；网络状态转 Fake/MockWebServer，UI 操作转项目已有仪器测试或现有可控模拟器，性能转稳定性专项。
- **预期结论**：替代证据继续绑定原 BDD 场景；只有仍无等价证据的必需项保持未验证或设备待验，其他门禁继续执行。
- **禁止行为**：把环境限制写成生产失败、丢弃已完成步骤、把已保存 XML 当成通过，或为跑通而修改生产接口、ROM、依赖和目标项目架构。

## 场景 60：编码后完善但验收语义不变

- **用户请求**：首次实现和测试已经完成，用户要求拆分一个职责过重的方法、补核心注释并保持页面行为和验收结果不变。
- **预期动作**：进入局部迭代，不执行 `init`、`confirm-requirement-update`、`route`、全部 Reviewer 或最终报告；最小修改后只运行直接受影响测试和必要的最小编译。
- **预期结论**：报告本轮修改、命令、测试结果和剩余风险；不得宣称整体交付通过。已有最终报告因代码变化失效，但不立刻重跑完整流程。
- **禁止行为**：重新拆分全部 BDD、运行全量 Lint/设备矩阵，或复用旧最终报告准备提交。

## 场景 61：编码后改变业务验收

- **用户请求**：原要求“点击重试立即进入首页”，编码后改为“先弹出确认框，确认后进入首页”。
- **预期动作**：把变化同步到需求文件，只修订受影响的 BDD 场景 并等待确认；保留未变化 ID、最初 Git 基线和无关实现。确认受影响需求后更新相关测试映射和同一份 `实施计划.md`，向用户展示变化摘要与链接；用户重新确认计划并成功执行 `confirm-plan` 后，进入局部迭代，更新相关状态与 UI 测试并执行必要编译。
- **预期结论**：需求语义、旧计划确认和相关旧证据失效，但不因此重跑完整编码前准备、重建 Git 基线或立即执行全部交付门禁；最终交付时再统一验证。
- **禁止行为**：把它当成纯实现优化绕过需求或计划确认，把旧计划收据继续用于新验收，或把整个需求、测试和代码从头重做。

## 场景 62：多轮局部迭代后准备交付

- **用户请求**：连续完成三轮局部完善后，用户明确要求“最终检查并准备提交”。
- **预期动作**：基于当前需求修订、最初 Git 基线和最终工作树执行一次 `route`，完成全部核心门禁及最终 diff 触发的条件专项，使用最后代码生成新鲜收据和中文摘要。
- **预期结论**：只有最终 `delivery_gate.py validate` 通过才允许声明可交付；Git 提交仍需用户明确授权。
- **禁止行为**：把三轮局部测试拼成整体通过、只检查最后一轮 diff，或因之前曾经全绿而跳过最终门禁。

## 场景 63：私有 YApi 链接需要登录

- **用户请求**：当前需求修改接口字段，`api.links` 配置了需要登录的 YApi 页面，本地存在上一轮截图，但 Chrome 当前未登录。
- **预期动作**：先使用可访问的浏览器会话读取；看到登录页或权限提示后进入 `USER_INPUT_REQUIRED`，请用户在该浏览器登录并回复“已经登录”，不索要凭据。重试读取成功后，在 API 领域目录生成或增量更新唯一 `api/api.md`，与原始证据一起登记到 `api.files`，完整记录本次 operation、字段、冲突和链接定位；只有改变产品行为、客户端采用方式或验收结果的契约结论才同步到 `requirement_file`。
- **预期结论**：登录前停止依赖契约的 DTO、mapper、Repository 和测试实现；用户明确选择旧证据、跳过或 mock/fake 时才降级。在线内容与旧截图冲突时保持待确认。
- **禁止行为**：因为有旧截图就静默跳过在线链接、脑补字段或必填性、要求用户发送 Cookie/密码，或让无关 UI 范围承担接口登录阻塞。

## 场景 64：全流程用户可见内容使用中文

- **用户请求**：需求发生增删改，接口登录待授权，一项测试失败且最终结论为本地通过、设备待验证；用户不理解英文状态。
- **预期动作**：需求使用“前提 / 操作 / 预期结果”，变化使用新增、修改、删除、保持不变和被替代；登录、失败、专项和最终报告均用自然中文说明原因、已完成/未完成范围、解除条件和下一步。机器 JSON 继续保留稳定枚举。
- **预期结论**：用户只需阅读中文摘要；稳定编号、路径、命令、类名和接口可以保留原文并附中文用途，原始英文日志仅作为证据附件。
- **禁止行为**：直接显示未解释的机器枚举、只给退出码或机器 JSON、把未知状态原样输出，或为了中文化修改 Schema、命令、接口路径和代码标识。

## 场景 65：本机配置和当前需求持续变化

- **用户请求**：频繁切换 Android 项目、分支、UI/API 资料并修改当前 `requirement.docx`，但不希望这些运行输入污染 Skill 源码提交。

## 场景 77：测试重复生产算法导致假通过

- **用户请求**：新增商品总价规则，生产代码和测试都用同一段 `sumOf` 加折扣算法计算预期，因此同一个舍入错误在两边同时存在且测试通过。
- **预期动作**：把已确认需求或契约中的确定样例作为独立预期，通过调用方可观察的公开边界断言结果；先让该样例在旧实现上真实 Red，再做最小修复转 Green。新增替身只隔离不可控外部边界，不用内部调用次数代替总价结果。
- **预期结论**：测试能够在生产算法错误时失败，并且内部重构不改变业务结果时继续通过。
- **禁止行为**：在测试中复制生产算法、读取私有中间值证明自己、为了好 Mock 新增无业务价值接口，或批量写完所有测试后再集中实现。

## 场景 78：偶现问题没有可靠复现

- **用户请求**：快速切换账号时偶尔显示上一用户的数据，第一次根据日志增加延时后问题仍出现，根因尚不明确。

- **预期结论**：无法建立可靠复现时说明已尝试方式并请求日志、录屏、环境或临时诊断授权，不把猜测写成根因或通过结论。
- **禁止行为**：继续增加 `sleep`、连续试改多个变量、只证明“不崩溃”，或把环境/测试问题直接归因于生产代码。

- **禁止行为**：忽略既有领域含义、把 ADR 当作绝对产品需求、扫描全部历史文档，或因为缺少 `CONTEXT.md` 阻断普通需求。

## 场景 80：大型需求纵向切片与小需求直通

- **用户请求**：同一需求包含账户列表、详情和安全提交三条可独立验收链路，预计跨多个会话；随后另一个需求只修改一个确定文案。
- **预期动作**：大型需求只在实施计划中按完整业务闭环记录可独立验证结果、包含的 BDD、真实依赖和现有最高观察边界，逐个保持可编译、可验证；文案小需求在计划中写一行后按普通流程直接完成，不建立切片、Ticket 或新文件。
- **预期结论**：跨会话继续时能从同一实施计划找到当前结果和下一个已解除依赖项，同时小需求没有额外流程成本。
- **禁止行为**：按“先写全部 UI、再写全部数据层、最后补测试”横向拆分，为所有需求强制建 Ticket，或引入新的 Issue、Schema、状态机和配置。

## 场景 81：需求明确但接口和 UI 资料晚到

- **预期结论**：业务实现与自动测试可以阶段性完成；正式接口联调和像素级 UI 验收保持待对齐。新资料只改变传输字段或视觉时走局部完善，改变业务语义时才进入需求修订并更新 BDD / 测试用例。
- **禁止行为**：因为资料晚到阻断全部开发，猜测正式 endpoint / JSON 字段，把 Fake 混入 release，或把临时 UI / Mock 测试写成正式联调和像素级验收通过。

## 场景 82：高影响歧义提供有依据候选

- **用户请求**：需求只写“退出编辑页时处理未提交内容”，现有代码直接放弃修改，项目没有草稿能力；该选择会改变已上线行为和测试预期。
- **预期动作**：说明模糊点、提问原因和现有行为依据，一次只展示该问题；提供 2～4 个互斥候选及各自可观察行为、旧业务和测试影响，保留“自行填写”。只有现有事实与最小修改约束足以支持时才标注建议，否则只列取舍。
- **预期结论**：用户未选择前保持待确认，不进入编码；不存在其他关键歧义时不为了凑满 5 个继续提问。
- **禁止行为**：只问“你想怎么处理”、同时抛出全部问题、根据常见产品习惯宣称业务默认值，或替用户自动选择会改变旧业务的方案。

## 场景 83：选择候选后补充或组合

- **用户请求**：候选 A 是“自动保存全部草稿”；用户回复“选择 A，但只保存主动编辑过的内容，提交成功后立即删除”，随后又提出与另一个候选组合恢复入口。
- **预期动作**：先检查补充和组合是否兼容；兼容时把选项方向、限制和恢复入口汇总成完整中文业务语义，不兼容时只澄清冲突。将最终语义合并进 `requirement_file`，按需拆分 BDD 场景，并同步旧业务影响和测试预期。
- **预期结论**：最终需求、BDD 和测试包含保存条件、提交后删除与恢复行为，不保存“A”或组合字母；未变化 ID 保持稳定，完成全部澄清后重新展示本轮变化摘要和最新需求文件路径。
- **禁止行为**：只记录 A、忽略“但”之后的内容，把独立新增点藏进 A，保留互相矛盾的旧表述，或把带补充的回答当成最终纯确认。

## 场景 84：候选均不适用或修改方向不完整

- **用户请求**：用户回复“A、B、C 都不合适，我希望退出时只保存已校验字段”；另一次只回复“A 需要修改”，没有说明修改结果。
- **预期动作**：第一种情况把用户描述作为同等有效的新方案，复述并检查边界；第二种情况不能猜结果，应根据已表达的问题提供更精确候选，无法形成真实候选时请求简短自定义答案。追问仍属于当前问题，不消耗新的问题名额。
- **预期结论**：只有形成无冲突、可验收的最终语义才写回需求并继续；所有候选都不适用不会阻断用户自行定义规则。
- **禁止行为**：强迫用户三选一、把自定义答案降级成备注、无依据生成伪候选，或自行把“需要修改”解释成某个实现。

## 场景 85：已选方案与新项目事实冲突

- **用户请求**：用户已选择本地自动保存；编码前进一步检查发现目标模块明确禁止落盘敏感字段，原候选无法按字面安全实现。
- **预期动作**：暂停依赖该方案的范围，展示项目依据、冲突后果和有事实支持的替代方案，请用户重新确认；其他已确认且独立的范围可以继续。确认后替换失效表述，更新受影响 BDD、测试和旧业务处置，编码中发生时沿用原 Git 基线和现有修订流程。
- **预期结论**：需求文件只保留重新确认后的最终语义，旧证据按语义变化失效；没有用户确认不能静默改为内存缓存或删减字段。
- **禁止行为**：为了遵守原选择忽略安全约束、由 AI 偷换实现语义、重建 Git 基线、重做未受影响需求，或仅在最终报告记录冲突。

## 场景 86：五步用户流程隐藏内部复杂度

- **用户请求**：完成一个包含业务规则和页面状态的需求；确认前连续补充一次，编码后修改一项业务预期，最后要求完整交付，但不想理解内部脚本和 Skill。
- **预期动作**：用户侧依次只看到确认需求、拆分测试与确认计划、实现验证、变更后增量循环和最终交付；计划阶段只展示摘要和 Markdown 链接。后台仍建立原 Git 基线、同步需求修订和追溯，校验计划收据，按影响选择测试与专项，并在最终意图下执行完整门禁。
- **预期结论**：需求变化只重做受影响需求、测试和代码；最终中文报告仍由新鲜机器证据生成。除用户明确询问或解除故障、授权、阻塞所必需外，不要求用户理解脚本顺序、Skill 名称、JSON、Schema、哈希或机器枚举。
- **禁止行为**：为了五步展示新增状态机或跳过门禁，把内部命令清单当作日常用户步骤，要求用户手动选择专项，或每次局部变化都重新执行完整交付。

## 场景 87：需求和实施计划确认闭环

- **用户请求**：多轮澄清后确认需求；AI 展示计划时用户修改预计文件和测试方案，确认后开始编码。编码中又新增一个会改变验收结果的要求，最后直接要求最终交付。
- **预期动作**：每个已接受需求答案先写入配置指向的 `requirement_file` 并由 `init` 重新读取成功。R1 确认后只读生成 `<requirement_dir>/docs/实施计划.md`，包含实现范围、已上线业务影响、预计修改文件、测试方案、影响半径摘要和明确不修改范围；聊天只给摘要和链接。用户修改计划时更新同一文件，不编码；纯确认后执行 `confirm-plan`，低成本核对 BDD、预期文件和预期测试与影响半径的对应关系。编码中的语义变化形成受影响修订，更新测试和同一计划并重新确认，不重建 Git 基线；最终 `route` 校验最新计划收据。
- **预期结论**：`requirement_file` 仍是唯一业务事实，`docs/需求状态.md` 及兼容的 `docs/需求说明.md` 只显示工作区状态；计划只描述如何实现。需求或计划变化后旧计划确认、route、测试收据和专项证据失效，未重新确认时最终交付被阻断。
- **禁止行为**：把聊天当需求事实、用计划覆盖需求文件、生成多份 plan/tasks/checklist、用户未确认计划就编码、计划变化后复用旧收据，或只在最终报告补写计划差异。

## 场景 88：影响半径阻断越界 Diff

- **用户请求**：初始确认只修改登录失败提示和对应测试；编码中用户又删除一个已确认提示分支，AI 同步受影响需求和计划。最终 diff 还包含顺手改动支付 Repository 的日志格式。
- **预期动作**：`confirm-requirement-update` 后同时更新 `<requirement_dir>/docs/实施计划.md` 和 `<requirement_dir>/test-cases/impact-radius.json`，只登记登录提示义务的 ADDED/CHANGED/REMOVED/SUPERSEDED、允许文件/目录前缀、受影响测试和模块；`confirm-plan` 收据绑定影响半径摘要。最终门禁读取基线后 diff，发现支付 Repository 不在已确认半径内时阻断完整通过；AI 只能移除该无关改动，或把新增影响写回需求/计划/影响半径并重新确认后再继续。
- **预期结论**：编码中需求变化只处理受影响义务、测试和代码，未变化登录行为不重做；越界文件不会因为测试通过或 AI 说明“只是日志”而进入通过报告。重新确认或移除越界改动后，route、测试和最终证据基于最终代码重新生成。
- **禁止行为**：需求变化后从头重跑全部准备、把无关支付改动塞进最终报告口头豁免、自动扩大 `allowed_dirs`、复用旧 `confirm-plan` 收据，或为了通过删除/弱化旧测试。

## 场景 89：交付文档可提交但不算代码 Diff

- **用户请求**：在真实项目中把需求说明、审计记录、测试日志和最终报告放到 `document/2026-07-28-login/`，希望随需求一起提交，随后执行 `check-env`、`route` 和最终门禁。
- **预期动作**：`check-env`、`route` 和最终代码摘要统一排除项目根目录下整个 `document/` 证据目录；当前需求和其他需求的 `document/<需求>/` 文档都不阻断代码基线，也不触发 UI/API/安全等专项；`document/` 之外的其他代码改动仍然阻断；执行收据写入 `document/` 时不改变代码摘要。
- **预期结论**：`document/<需求>/` 下的文档都可以 `git add`/提交作为需求证据链，但任何 `document/` 文档都不能作为本次代码影响面、代码摘要或专项触发依据。
- **禁止行为**：把 `?? document/` 折叠目录当成代码脏区误拦、把审计日志路由成 API/安全风险、因收据自写入导致测试后代码摘要变化，或用忽略文档为理由忽略真实源码改动。

## 场景 90：API 契约专项空 PASS 被拒绝

- **用户请求**：最终 diff 修改 `ApiClient`、DTO 或 Repository 网络行为；API 专项报告只写“契约一致，PASS”，没有契约文件、operation/schema、实现映射或 artifact。
- **预期动作**：API 专项结果必须记录 `api-contract` capability、`contract-source`、`operation-schema`、`implementation-mapping` 三项检查、执行数量和至少一个契约/核对 artifact；缺正式契约或无法读取时输出 `UNVERIFIED/BLOCKED/FAIL`，不能 PASS。最终门禁引用空 PASS 时失败，并指出缺 API 契约机器证据。
- **预期结论**：接口变更不会因为自然语言总结而假绿；只有契约来源、schema 和实现映射均可复核且 artifact 摘要未变化时，`android-verify-api-contract` 才能通过。
- **禁止行为**：根据客户端现状脑补后端契约、用日志或聊天摘要冒充正式 artifact、缺失 operation/schema 仍 PASS，或让最终报告自行省略 route 触发的 API 条件门禁。

## 场景 91：Figma 纯视觉增量不重做需求确认

- **用户请求**：登录页需求和计划已经确认并完成业务实现，后来补充正式 Figma Frame，只调整颜色、间距、字号和图片；目标 layout、drawable、values 已在影响半径内，交互和页面状态不变。
- **预期动作**：更新 UI 输入摘要，调用 `figma-android-xml` 只重生成允许范围内 XML/资源并提交结构化交接结果；保留当前需求修订、仍有效的计划收据、未受影响映射和测试源码，使旧 Figma 交接、资源构建、截图、UI 验收、route 和最终结论失效。若 `requirement_inputs_sha256` 变化，绑定旧输入的专项/执行收据也失效，最终交付时重跑必要命令刷新收据。总入口接管项目 Design System/I18n/A11y，重跑受影响 build/lint/截图并独立执行 `android-verify-ui`。
- **预期结论**：未变化 BDD、业务代码和测试源码不重做；最终视觉结论绑定新 Figma 输入和真机截图，输入摘要变化时必要收据已刷新，不能复用旧截图或把生成成功写成 UI PASS。
- **禁止行为**：因新增 Figma 链接自动升级需求修订、重复全部计划确认和测试、让 XML Skill 写 Kotlin，或跳过独立 UI 验收。

## 场景 92：Figma 新增交互触发需求修订

- **用户请求**：原需求只有静态登录页，新的 Figma Frame 增加密码显隐按钮、加载状态和失败后重试入口，但用户尚未确认这些行为。
- **预期动作**：把新增状态和交互识别为需求语义变化，暂停 XML 生成和业务实现；写回 `requirement_file`，重新 `init` 并等待用户确认，再执行 `confirm-requirement-update`，更新计划和影响半径并重新确认。受影响测试映射标记 STALE，确认后补 Red、最小实现、Green 和新鲜证据。
- **预期结论**：用户确认前没有新增交互代码或完整通过结论；确认后只重做受影响 BDD、XML、业务连线和测试，未变化登录行为保持原样。
- **禁止行为**：把 Figma 当作自动确认的产品需求、只改 XML 不补业务状态和测试、继续使用旧计划收据，或由 `figma-android-xml` 输出最终验收 PASS。

## 场景 93：浅包装和为测试暴露内部接口

- **用户请求**：为一个只转发 Repository 调用的新 Manager 增加接口和多个内部方法，理由是方便 Mock；项目只有一个生产实现，调用方仍需理解完整调用顺序。
- **预期动作**：代码质量审查执行删除检验，判断删除包装后复杂度是否只是回到原调用方；检查是否存在真实替代行为、接口是否减少调用方知识，以及测试能否通过调用方使用的同一稳定入口观察结果。
- **预期结论**：没有真实替代需求且不提供局部性或复用价值时移除浅包装；确有生产适配器与本地替身并集中业务知识时保留接缝并通过公开结果测试。
- **禁止行为**：按实现行数判断模块深度，为 Mock 自有内部协作者暴露新接口，或保留只增加跳转层级的 Manager/Wrapper。

## 场景 94：难以逆转的公共契约存在多个方案

- **用户请求**：新增一个会被多个模块长期调用的支付状态接口，目前有事件流和查询快照两种可行形状，后续改动成本高。
- **预期动作**：只在该公共契约范围比较至少两种结构明显不同的方案，逐项说明调用负担、必须理解的不变量、错误模式、局部性、真实扩展依据和测试边界，再推荐一个最符合当前项目事实的形状。
- **预期结论**：选择依据写入现有计划；同时满足难逆转、缺少背景会令人困惑和存在真实取舍时，才按现有模板增加决策记录。局部实现细节不增加方案会或文档。
- **禁止行为**：为每个类生成多套设计，按抽象层数或代码行数选方案，或为假想未来扩展增加接口。

## 场景 95：原型只用于澄清一个阻塞决定

- **用户请求**：退出编辑页时的草稿状态在文字中说不清，希望先点一个演示确认保存、丢弃和恢复关系；当前没有正式 Figma。
- **预期动作**：在临时位置构造纯内存、可重复操作的最小演示，只回答这一个状态问题，不接生产数据。用户确认后把完整业务语义写回 `requirement_file` 和 BDD；验证过的状态模型按生产标准整理并补测试，临时壳移除。
- **预期结论**：后续实现和最终门禁只以已确认需求、正式代码和测试为准；原型不成为设计基准、测试证据或第二事实源。已有正式 Figma 时不生成竞争 UI 方案。
- **禁止行为**：每个需求都做原型，把无测试演示直接并入生产，在原型和需求冲突时服从原型，或为原型新增 Ticket、状态机和长期分支。

## 场景 96：需求轴和工程轴结论不能互相抵消

- **用户请求**：最终代码结构清晰且测试充分，但漏掉需求中“失败后保留输入”的行为；另一次功能完全正确，但把全部逻辑塞进 Activity 并破坏项目架构。
- **预期动作**：Diff Reviewer 独立输出需求轴结论，代码质量 Reviewer 独立输出工程轴结论；最终汇总并列保留两轴问题和建议，不合并成模糊总分。
- **预期结论**：任一轴存在未关闭 P0/P1 都不能建议交付；修复对应问题后两轴分别重验，需求正确不掩盖工程问题，工程整洁也不掩盖需求缺失。
- **禁止行为**：用测试通过替代需求核对，用代码质量高抵消漏需求，或把两个 Reviewer 合并成无法追溯责任的单一主观结论。

## 场景 97：并行分支冲突按双方意图解决

- **用户请求**：两个已确认需求分别修改同一 ViewModel：一侧保护取消请求后的空状态，另一侧增加重试状态；rebase 时出现同一 when 分支冲突。
- **预期动作**：先读取双方需求、提交说明、调用方和测试，分别说明两侧要保护的行为；兼容时组合状态处理，不兼容时服从当前集成目标和已确认需求并记录放弃项，随后在最终代码上重跑受影响门禁。
- **预期结论**：冲突解决能追溯到双方业务意图，旧分支证据不被复用；无法兼容且缺少决定时保持阻塞，不发明第三种行为。
- **禁止行为**：机械选择 ours/theirs、按提交新旧覆盖、只让代码编译不验证行为，或借冲突解决顺手重构无关代码。

## 场景 98：用户提供 API 资料后统一维护契约记录

- **用户请求**：用户先提供 YApi 链接，随后又用截图和聊天补充同一接口字段；YApi 响应树默认折叠，当前需求已经存在记录其他接口的 `api/api.md`。
- **预期动作**：把用户提供 API 资料本身视为接口处理意图，不再追问是否接入；递归展开 object/array、处理虚拟滚动并读完当前 operation 后，只把它合并到 API 领域目录的同一份 `api/api.md`，与原始证据共置，保留来源定位、证明范围、冲突和未知项，登记到 `api.files`。改变产品行为或验收的规则同步到 `requirement_file`，纯契约字段不复制成第二份需求。
- **预期结论**：当前需求始终只有一份 `api/api.md`，原有其他接口内容保持不变；链接、截图、文件和聊天的证明能力可区分，已展开字段的类型和必填性被完整记录，来源确实未定义的事实仍是未验证项。
- **禁止行为**：因为输入不是本地文件就跳过 API 文档、把折叠/未渲染节点当成契约缺失、为每种来源生成一份摘要、覆盖其他接口、把聊天说明冒充正式服务端契约，或新增脚本和流程阶段完成简单归一化。

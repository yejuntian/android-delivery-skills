# Android 陌生项目接手

建立足以安全进入具体需求的项目地图，不追求读完仓库。项目规则优先；默认只调查和验证，不修改生产代码、构建配置、依赖、AGP、发布环境或生产数据。

## 按需读取

- 需要写入或更新项目上下文时，读取 `references/project-context.md`。
- 维护本 Skill 时，读取 `references/forward-tests.md` 并执行直接受影响案例。

不要一次加载全部参考资料，不创建扫描脚本、状态机或平行测试框架。

## 接手循环

### 1. 确认边界

读取项目 `AGENTS.md`、README、当前分支、Git 状态和已有项目文档。已有改动属于用户；只识别和避让，不清理、stash、覆盖或静默纳入。不得索取、读取或记录密钥值。

先确定接手目标：为指定需求或职责补齐上下文，或建立通用安全开发基线。目标决定调查范围、代表性链路和完成条件；目标外发现只记录为风险或未知项，不扩大调查。

本阶段不创建需求 profile、日期需求目录、`spec.md`、BDD 或 `baseline_commit`。用户同时给出具体需求时，先补齐影响该需求的项目事实，再交回 `android-implement-and-verify`。

### 2. 建立项目地图

优先读取 `settings.gradle[.kts]`、根与模块 Gradle、Version Catalog、Manifest、Application、启动入口、导航、CI、测试入口和最近 Git 历史。先识别模块职责、依赖方向、数据与外部系统，再围绕一条代表性用户链路深入；不平均扫描全部文件。

用提交历史识别反复变化的热点，但不把修改频率直接判定为缺陷。已有 README、架构文档或 ADR 只作来源；结论必须回到当前代码、配置或实际命令核对。

发现同一业务词在代码、文档或人员描述中含义冲突，或一个词承担多个概念时，提出精确区分并与代码交叉检查；只在含义确认后按需更新 `glossary.md`，不从类名批量生成词典。

未知项依赖仓库外事实时，只调查当前目标真正阻塞的问题，优先使用官方文档、源代码、规范和第一方 API，逐条记录来源与适用版本；外部调研只提供事实，不替代项目决定。

### 3. 建立运行基线

优先使用项目已声明的 JDK、Gradle、构建、测试和 Lint 入口。按风险从低到高执行必要的最小命令，记录命令、环境、测试数量、结果、产物和未覆盖边界。构建产物可写入项目既有输出目录，但不得为跑通基线修改项目、升级工具、删除断言、增加 suppress 或伪造配置。

设备验证仅在设备可用、不会干扰共享环境且确有必要时执行。失败是有效事实；区分代码、环境、历史基线和资料缺失，不在接手阶段顺手修复。

### 4. 追踪核心链路

选择一条最能代表当前项目或后续需求的链路，从入口追踪到数据持久化、网络或其他可观察副作用。每项重要结论标记为：

- **已验证事实**：实际命令、运行或确定性检查已证明；
- **代码或配置事实**：当前文件明确表达，但未证明真实环境行为；
- **文档或口述声明**：尚未与当前实现交叉验证；
- **有依据推断**：由调用关系或历史推导，仍需验证；
- **未知项**：当前证据不足，并写明影响和解除条件。

先穷尽仓库、工具和第一方资料。仍无法证明且影响当前目标的人员知识，按重要性列出需要原维护者确认的问题；每题只问一个事实并说明影响，不把可自行查证的问题转问人员。

### 5. 形成接手结果

固定汇总项目定位、Git 状态、模块与入口、核心链路、实际验证、热点、风险、未知项和进入具体需求流程的条件。只保留阻塞安全修改、验证或交付判断的内容。

仅当能够说明目标相关模块与入口、至少一条核心链路、最小验证入口及其实际结果或阻塞、关键未知项及解除条件，并为每项重要结论提供证据类型和来源时结束接手；不适用项写明依据，缺少任一必要条件时报告受阻而非完成。

项目事实需要跨需求复用或用户要求写入项目文档时，把项目级文档写入 `<project_path>/document/project-context/`；已有等价文档时引用或最小更新，不创建第二份事实源。默认只创建 `overview.md`，内容确实独立且增长后才拆分，禁止预建空文件。当前代码、Gradle、CI 与文档冲突时以当前一手证据为准，并更新失效结论。

## 交回需求流程

项目接手完成不代表任何需求通过。用户开始具体需求时再由 `android-implement-and-verify` 创建或定位 profile、`requirement_dir` 和 `spec.md`，并以需求实际开始点记录 `baseline_commit`。接手阶段的构建或测试只能作为项目基线；不得替代需求 BDD、专项或最终交付证据。

## 不可削弱的边界

- 不因项目陌生而自动重构、修 Bug、升级依赖或补齐全部测试。
- 不把所有现有行为固化为需求保护项，不把架构偏好伪装成项目事实。
- 不要求消除全部未知；只清理进入当前需求所必需的知识缺口。
- 不因缺少 `document/project-context/` 阻塞普通新需求或触发全项目重扫。
- 不复制代码、Gradle、README、ADR 或大段日志；项目上下文只保存结论、边界和来源指针。

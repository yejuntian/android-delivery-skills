# 需求、BDD 与实施计划

需求来自多份资料、表格、截图、设计稿、接口页面或相互冲突的补充时，先读 `document-and-requirement-understanding.md`。需求已经明确时直接综合，不重复提问。

## 需求事实源

- 需求正文使用 `<requirement_dir>/docs/<需求名>.md`；docx 只作初始输入，首次 `init` 后转写为 md。
- 每个已接受答案立即合并进 `requirement_file`，替换失效表述并同步受影响 BDD、旧业务影响和测试预期。聊天不能替代事实源。
- `## 待确认` 必须存在；产品行为、范围、失败恢复、权限、数据来源和验收口径全部澄清并由用户确认后才写 `- 无`。实现级细节可以留到计划阶段，但不能掩盖产品语义未知，也不能提前生成 BDD。
- 人维护需求、实施计划、业务和测试代码；脚本维护快照、修订、映射、收据、route、证据和最终结果。
- 关键事实保留来源定位；当前分支找不到需求引用的本地路径时，保留原引用并报告缺失，询问用户参考分支或替代路径，不能自行改写为“不再依赖”；改变产品行为、范围、风险接受、验收口径或缺失资料处置的是用户决定。推导和假设不能冒充正式业务规则。

## 通用澄清模型

- 每轮理解都把信息分为三类：**已确认事实**（有需求、代码、契约、测试或用户确认支持）；**待用户决定的问题**（答案会改变用户行为、业务范围、验收结果、数据含义、权限、失败恢复、允许修改范围或参考资料来源）；**可延后的实现细节**（不会改变上述语义，可在计划阶段决定命名、数据结构和具体实现方式）。
- 待用户决定的问题必须先问；实现细节不得伪装成已确认事实，也不得用默认值、占位 BDD 或 `- 无` 掩盖。需求澄清阶段不生成 BDD，综合阶段才根据已确认语义生成 BDD。
- 一次只展示当前最高优先级问题，降低回答成本；但用户可以在一次回复中回答多个问题，或同时提出新增变化。Agent 必须逐项匹配并处理整条回复：已解决问题从清单删除，未解决问题保留，全部答案写回唯一 `requirement_file` 并重新 `init`；仍有问题时只继续询问剩余项中的最高优先级。
- 用户纯确认后才进入 BDD 和计划；如果实现阶段发现语义问题，返回澄清阶段，重新确认受影响内容，并将受影响测试映射和证据标记为 `STALE`。
- 参考资料按实际形态记录最小定位和用途：代码参考记录仓库、`reference_branch`、路径；链接记录 URL；截图或文件记录名称/路径；聊天确认记录已确认语义。用户提供 API 链接、截图、文件或聊天契约时，生成或增量更新唯一 `api/api.md`，与原始 API 证据共置并保存来源证明的完整契约、冲突和未知项；`requirement_file` 仍是唯一需求事实，只同步会改变产品行为、客户端采用方式或验收结果的 API 规则。当前实现分支缺失代码路径时保留原文并询问参考分支或替代路径，不能自行猜测来源、切换分支或删除引用。

## BDD 质量

- 每个 `### BDD-### 场景名称` 包含 Given/When/Then；独立触发、异常、恢复和边界拆成独立场景。
- 同一触发有多个验收结果时使用结构化 Then 列表，不用自由文本或 And 隐藏结果。
- 为可观察场景分配稳定 ID；未变化内容不得因排序改号，一个 BDD 可以映射多个真实测试。
- 确认前检查主流程、备选、异常、恢复和非功能约束；缺少时标记待确认或“不适用 + 原因”，不为凑数量脑补。
- 只问会改变用户行为、业务范围、验收结果、数据含义、权限、失败恢复、允许修改范围或参考资料来源的问题。存在依赖时一次只问当前最高优先级问题；关键业务含义不清时继续阻塞。实现级细节延后到计划阶段。

## 已上线业务影响

需求理解最前面展示：

1. **本次明确修改**：需求允许改变的已有行为，写清修改前后。
2. **必须保持不变**：可能受影响但没有授权改变的已有行为，必须有代码、测试、契约或用户事实依据。
3. **暂时无法确认**：是否允许改变仍不明确，作为冲突阻断确认。
4. **明确不修改范围**：不会触及的相邻业务和公共边界。

最终 diff 发现未登记的已有业务调用方或可观察变化时，立即写回需求并进入增量闭环，不能只在报告补一句风险。

## 澄清方式

- 先说明模糊点、原因和已知事实；代码能证明技术事实时直接采用，但不能仅从现有表现推导产品规则。当前分支缺失引用路径时，不把分支差异当成资料不存在，先向用户确认参考分支或替代路径。存在产品级未知时一次只问当前最高优先级问题，然后停止等待用户。
- 能形成真实互斥方案时提供 2～4 个候选，说明可观察行为和直接影响，并允许用户自定义；金额、权限、隐私和线上行为不得自动代选。
- 用户回答后先写回事实源并重新读取，再复述合并后的最终语义；仍冲突时只澄清当前冲突，不静默取舍，也不先拆 BDD。
- 用户一次回答多个问题时逐项处理，不只采用第一项；已解决问题删除，未解决问题保留，重新 `init` 后只追问剩余最高优先级问题。
- 用户回复同时包含“确认”和新变化时仍按变化处理，写回并重新 `init` 后等待纯确认。
- 能从代码、配置、测试和契约查明的技术事实由 Agent 直接查明；资料已经足够时不得为了模板完整度继续发问。

## 修订清单

- `requirement-revision.json` 使用 `ADDED/CHANGED/REMOVED/UNCHANGED/SUPERSEDED` 和 `CONFIRMED/PENDING/REJECTED/CONFLICT`。
- 普通新增、修改和未变化由 `init/check-env` 物化；删除、改号和替代必须使用显式 `--revision-file` 说明处置。
- `confirm-requirement-update` 只推进当前需求修订，不改变最初 Git 基线；重复 `check-env` 安全复用当前起点。
- 新的串行需求必须完成或取消当前需求，再按 `parallel-and-resume.md` 轮换并使用 `check-env --new-requirement`。

## 聊天事实收件箱

对可能改变行为但尚未形成完整需求的补充，先写 `.state/fact-inbox.json`。`PENDING` 和 `DISCUSSION` 不能开发；即使状态为 `CONFIRMED`，仍需补齐范围和验收结果、写回需求并执行 `confirm-requirement-update`。最终 gate 复核收件箱，防止聊天确认绕过正式修订。

## 实施计划和影响半径

需求确认后生成唯一 `docs/实施计划.md` 和 `test-cases/impact-radius.json`。计划必须展示：

- 实现范围。
- 已上线业务影响。
- 预计修改文件。
- 测试方案。
- 复杂需求的纵向执行顺序与真实依赖；小需求只写一行。
- 影响半径摘要。
- 明确不修改范围。

影响半径覆盖当前需求基线以来所有已确认语义变化；`allowed_files` 使用精确文件，`allowed_dirs` 使用以 `/` 结尾的目录前缀，不用通配符。计划中的 BDD、预期文件和测试必须与影响半径交叉对应。

切分只用于跨会话工作或多条可独立验收链路：每片必须交付一条完整、可演示或可验证的业务结果，覆盖必要的 UI、业务、数据和测试，不按层或文件横向拆分。只记录真实阻塞依赖，优先复用项目已有的最高可观察测试边界。普通需求和单点改动不创建切片、Ticket 或新文件。无法保持每步可编译通过的宽重构使用 expand → migrate → contract 顺序，不强行伪装成纵向功能切片。

切片跟随现有实施计划一起展示，用户仍只确认一次。确认后执行 `confirm-plan`；收据绑定需求修订、需求摘要、计划摘要和影响半径摘要，任一变化都会使旧收据失效。没有改变计划边界或影响半径的实现细节完善不重复确认。

## 人读产物

所有人工 Markdown 放在 `<requirement_dir>/docs/`。脚本从机器产物渲染续接指南、需求修订说明、测试映射说明、需求测试追溯和交付结论；这些视图不成为第二事实源。审查、决策、问题、设计和配置说明按需使用 templates，不创建空目录或保存凭据。

# 实现与增量测试

## 开始前

进入生产实现前确认 `spec.md` 为 `status: confirmed`，当前分支与用户目标一致，并识别已有改动。已有改动先按用户所有处理；同一切片续接须按下文核实归属，不得清理、覆盖或把无关改动纳入本需求。接收和评估增量不受实现启动条件限制。

读取相关模块、相似实现、公共接口和已有测试。遵守项目自己的架构、依赖管理、命名、国际化和无障碍约定，不假设项目使用 Compose、Hilt、Retrofit、Room 或协程。

## 基线、并行与续接

- 一个需求使用一个独立分支、一份独立配置、一个 `requirement_dir` 和一份 `spec.md`；多个需求并行时分别使用独立 worktree，同一 worktree 不同时修改两个活动需求。
- `baseline_commit` 只记录需求开始点，不因普通增量修改而重建。最终审查固定使用 `baseline_commit...HEAD`；进入最终结论前不得存在 staged、unstaged 或 untracked 改动。
- 用户确认规格时一次性授权当前独立需求分支上已确认输入、实现切片和最终结果的本地边界提交；不授权 amend、squash、rebase、推送、集成或发布。用户明确拒绝自动提交时暂停流程，不把脏工作区当作替代检查点继续。
- 需求开始和每个切片开始前必须确认独立需求分支或 worktree、有效 `baseline_commit`、干净工作区和无用户遗留改动；提交时工作区只能包含当前边界已经审查的改动。任一条件不满足就停止，不自行 stash、清理或扩大授权。
- rebase、合并或分支变化后，先确认基线仍是当前历史祖先；不是时停止比较并让用户决定新的审查起点，不自行改写基线。
- 新窗口续接先读当前规格、相关既有结果和 Git 状态，核对 `baseline_commit` 仍是 `HEAD` 的祖先，再读基线后的提交；先掌握全局目标、保护项、范围和授权，再按当前边界读取必要实现与依赖。提交中的稳定 ID 只用于定位，须核对实际代码、后续修复或回退和有效证据；旧 ID 或 RESULT 不等于完成。不依赖聊天摘要，不复用其他需求结果，也不默认加载完整流程总览或图解。
- 共享模拟器、真机、测试账号和不可并发的后端数据必须串行使用；环境被其他应用或任务占用时先恢复测试前提，不误判为产品失败。
- 用户授权集成后，先将需求分支 rebase 到最新目标分支；出现冲突时停止并核对业务语义，不自行改变已确认需求。
- 目标分支只使用 fast-forward 合并；无法 fast-forward 时停止，不静默改用 merge commit 或改写目标分支历史。
- 合入后的代码重新执行受影响验证；需求分支上的旧结果不能直接证明集成结果。

## 纵向切片

1. 按规格选择一个依赖已满足的交付边界，一次只激活一个；整体交付可覆盖多条紧密相关的 BDD，显式分组使用 `SLICE-##`。开始前按 `clarify-and-spec.md` 复核粒度，无法可靠完成和审查时先调整计划。
2. 开始时记录 `slice_base_commit = HEAD` 并确认工作区干净；存在任何改动时先明确归属，不在混合状态下启动切片。
3. 选择最高可观察测试边界，先写会因缺少目标行为而失败的测试或建立等价失败证据，确认失败原因正确。
4. 编写刚好满足该行为的实现并运行当前测试；边界覆盖多个 BDD 时逐条重复失败证据与最小实现，最后运行直接受影响模块测试和必要编译。
5. 提交前审查完整工作区：先检查 `git diff` 和 `git status --short` 并逐个确认 untracked 文件，只暂存当前切片的明确文件或变更块，再检查 `git diff --cached`；不得只看已提交 diff，也不得夹带用户已有或其他切片改动。
6. 验证通过且范围纯净后形成一个边界提交。标题使用中文语义并包含稳定 ID，例如 `BDD-01/BDD-02 完成列表加载与空状态` 或 `SLICE-01 实现订单列表与空状态`；正文简述实际验证命令或人工步骤、结果与未覆盖边界，便于新窗口核对。一个切片无法形成可审查原子提交时按增量闭环调整，不用多个含混提交掩盖过大切片。
7. 自动提交已经审查的暂存区。提交失败必须显式报告，不得把未提交状态当作检查点继续。
8. 提交后检查 `git diff --stat <slice_base_commit>...HEAD`、`git diff <slice_base_commit>...HEAD`、提交信息和 `git status --short`。发现遗漏或问题时新增沿用同一稳定 ID 的修复提交，未经明确授权不 amend 或 squash。
9. 当前切片验证通过并形成可识别提交，或按下文完成明确取消/替代的收拢后，工作区重新干净才进入下一个切片；用户要求带未提交改动进入下一切片时暂停。中途的规格提交不代表实现完成。

测试名称或注释可引用 `BDD-###`，不维护独立 `test-mapping.json`。项目没有可行自动化边界时，规格必须写明可复现人工验收步骤和原因，最终结论标记相应未验证风险。

实现期间不把执行结果写回已确认规格；局部验证随边界提交正文保存，最终在 `docs/result.md` 按 BDD 汇总并核对有效性。提交可供上下文恢复，但不代表工具已经清空上下文或未验证内容已经完成。

## 快速反馈

实现期间只执行：

- 当前测试文件或测试类；
- 直接受影响模块的测试；
- 能尽快暴露编译错误的最小 Gradle task；
- 当前切片确实依赖的模拟器或设备检查。

不要每个切片重复全量测试、Lint、完整构建和所有专项。完整验证留到最终交付。

## 宽范围迁移

普通功能按纵向切片交付。公共 API、包名、设计系统、构建配置等无法单步保持绿色的宽范围迁移使用 expand-migrate-contract：

1. **Expand (`MIGRATE-EXPAND`)**：增加兼容的新形式，让新旧调用暂时共存并保持可构建。
2. **Migrate (`MIGRATE-01`、`MIGRATE-02`...)**：按模块、包或调用方分批迁移；每批有明确范围、验证和原子提交。
3. **Contract (`MIGRATE-CONTRACT`)**：全部调用方迁移并验证后删除旧形式，检查临时兼容层没有遗留。

阶段 ID、范围和依赖必须先记录在规格的“实施决策”，每批提交及其修复提交复用对应 ID，并接受与切片相同的工作区审查和副作用边界。公共 API 在 Contract 前按实际发布边界核对 Kotlin/Java 源兼容、JVM 二进制兼容、默认参数、反射、生成代码和仓库外消费者；无法证明外部兼容时保留适配层或停止并确认。不要把“先数据层、再业务层、最后 UI 层”当作可独立验收的纵向切片。

## 增量闭环

任何阶段收到或发现需求变化、漏洞、遗漏，先核对当前规格、相关事实和 Git 状态，说明受影响内容与依赖；不等待阶段完成、切片提交或检查通过。从最早受影响内容同步下游，需求决定合并到同一 `spec.md`，执行结果不写入规格；不建平行变更单，不重置 `baseline_commit`。

门禁限制写入、提交和完成声明，不限制接收与分析。只读任务只报告；范围外或独立新目标由用户决定，不自行扩权或修改流程规则。

### 决定是否重新确认

| 变化 | 处理 |
| --- | --- |
| 行为、业务语义或验收变化 | 改回 `draft`，待确认非空时不新增或改写任何 BDD、不继续生产实现；清空后补齐受影响 BDD，再只确认变化部分 |
| 允许范围、模块、依赖、公共接口或测试边界变化 | 暂时改回 `draft`，只确认该变化；登录、支付、权限、迁移、签名、混淆和公共组件边界明确说明影响 |
| 已确认要求存在遗漏或未满足，含义和授权边界明确且未变 | 保持 `confirmed`，补齐受影响内容；出现新取舍或扩围则按前两类处理 |
| 已确认范围内的视觉或实现细节，行为与验收未变 | 保持 `confirmed`，只修改受影响实现并运行最小验证 |
| 仅调整交付粒度或顺序，行为、范围、契约和测试边界未变 | 保持 `confirmed`，更新规格中的实施计划并说明依据，不重复确认 |

首次与增量均先清空待确认、补齐受影响 BDD、保护项和依赖，再请求必要确认；已有且未受影响的 BDD 保留。首次确认最新完整规格，增量只确认变化部分；带修改的回复不视为纯确认，确认后恢复 `confirmed`。明确取消的行为不再作为必须保持项。当前需求的本地边界提交授权持续有效，拒绝自动提交或项目规则另有限制时仍按原授权门禁停止。

### 按当前进度收拢

规格或归一化输入实际变化时，完成必要确认后先形成只含这些输入的 `SPEC` 提交，再修改受影响实现；纯实施计划调整按已获授权提交，没有输入 diff 时不创建空 SPEC。以下按进度选择，不额外增加确认轮次。

- **尚未实现**：完成必要的 `SPEC` 提交，再从干净工作区按新计划启动边界。
- **当前边界实现中（含新窗口续接）**：必要确认前暂停生产实现。核对 staged、unstaged、untracked；剩余改动可证明属于同一边界的授权工作且与输入可分离时，才只提交 `SPEC`。依据已有确认、Git 历史和可核对记录保留或恢复原 `slice_base_commit`，继续同一边界，不以窗口身份判断归属，不把当前 HEAD 或 SPEC 提交当作新起点/完成检查点。归属、起点或隔离性不明，或夹有用户遗留/无关改动时保留现场、停止写入并报告，不 stash、清理或提交半成品。
- **已有实现提交**：保留原提交；同一行为修正沿用稳定 ID，新增独立边界使用新 ID。按最新规格核对并最小移除本需求中已明确失效的实现和测试，保留仍有效的断言和保护项；不得把取消需求当作删除无关旧代码或掩盖失败的理由。
- **正在最终验证或已经产出结果**：先按上述类型处理规格与实现，再按命令、环境和被验证输入重跑失效检查，复用仍有效证据；更新 `result.md`、`verified_head` 并对最新 `HEAD` 重新审计。旧 RESULT 在受影响部分重验前仅是历史结果。

整个边界取消或替代时，确认规格、保护项和依赖调整，只撤除已授权、归属明确且可隔离的失效改动；不明则保留现场并询问，不整区回退。已提交实现以新提交移除；未提交实现撤除后无 diff 不建空实现提交。无失效残留、受影响回归有效、必要提交完成且工作区干净后可进入下一合法边界；取消不算验收通过，替代行为仍需验证。

边界过大时，仅将符合最新规格、可独立验证且满足同样提交与隔离门禁的部分收为交付边界；否则保留现场并报告，不提交未验证检查点。行为修改仍按失败证据、最小修改、回归、审查和提交闭环；纯计划调整只核对覆盖与依赖。

复查原发现点及失效下游检查，保留有效证据后继续相应工作，不重走未受影响阶段。按最新规格核对取消项；缺条件则记录未验证及解除条件，不靠改验收、删有效断言或降低门禁消除失败。最终仍审计原基线到最新 HEAD。

## Android 底线

- 遵循项目既有依赖集中管理方式，防止模块反向依赖和循环依赖。
- 用户可见文案进入字符串资源；可交互图标具备有意义的无障碍描述。
- 不记录 Token、密码、手机号等敏感值，不把 Mock/Fake 混入 release 数据路径。
- 生命周期注册/解绑、资源获取/释放、异步任务/宿主生命周期必须成对。
- 历史告警与本次新增问题分开报告，不通过更新 baseline 或批量 suppress 掩盖新增问题。
- 修改共享设备、账号、数据或端口前优先使用隔离资源，并记录与本次操作相关的可恢复初始状态。运行测试或诊断后恢复设备设置、账号状态、测试数据、端口、临时文件和诊断插桩；无法恢复时停止后续自动操作并报告实际变化、影响和恢复条件。

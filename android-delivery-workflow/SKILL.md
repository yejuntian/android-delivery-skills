# Android 需求交付总入口

## 共享规则

执行本 Skill 前，必须先遵守 `../_shared/android-global-rules.md`：默认中文输出、动态资料不写死、接口和 UI 不确定时不脑补、不伪造验证结果、发现问题默认先报告不自动修复。

## 定位

这是 Android Skills 套件的总指挥，用来处理一次完整 Android 需求交付。它负责读取动态输入、判断资料完整度、编排专项 Skill，并输出从需求分析到验证报告的闭环结果。

本 Skill 不替代专项 Skill；遇到专项问题时必须引用对应流程：

- `android-change-review`：需求变更分析、影响范围、分阶段方案。
- `android-ui-verify`：UI 还原、截图、设计稿对比。
- `android-api-contract-review`：接口契约、字段兼容、后端不确定性。
- `android-test-delivery`：测试用例生成、自动测试、验证报告。
- `android-stability-review`：崩溃、内存泄漏、ANR、协程、生命周期风险。
- `android-code-quality-review`：AI 代码质量、架构一致性、可维护性审查。

## 外部智能体与工具调用策略

总原则：本 Skill 负责判断“什么时候该用哪个能力”，不是把所有工具一次性全部打开。需求理解确认前保持轻量；进入实现和验证后再按需调用外部工具。

- 需求理解：只读取需求文档、截图、链接和用户补充；默认不调用 Android CLI、Gradle、adb 或 Firebase MCP。
- 需求理解确认后：自动完成影响范围、接口分析、UI 分析、技术方案、测试用例、稳定性风险和代码质量风险，不需要逐项等待用户确认。
- 代码修改前：必须请求用户确认；确认前不得修改代码、跑破坏性命令或改 Git 状态。
- Android CLI / Gradle / adb：只在真实构建、安装运行、单测、lint、仪器测试、截图、logcat、设备兼容验证时使用；不可用时退回项目已有 Gradle/adb 命令或标记未验证。
- UI 智能体能力：需求涉及设计稿、截图或视觉还原时，结合 `android-ui-verify`，需要真实截图对比时再使用 Android CLI/adb 截图。
- 接口智能体能力：需求涉及后端契约、字段、错误码、分页、鉴权或联调时，结合 `android-api-contract-review`；接口未确认时只能做 mock / fake / sampledata。
- 测试智能体能力：实现前后结合 `android-test-delivery` 生成测试矩阵，并选择当前项目可执行的最小命令集。
- 稳定性智能体能力：实现后结合 `android-stability-review` 检查崩溃、内存泄漏、ANR、协程、生命周期和 Android 版本兼容；发现点先报告不自动修。
- Firebase MCP：仅当需求或问题涉及 Firebase、Crashlytics、Remote Config、Analytics、AB 实验、线上崩溃、线上配置或埋点分析时使用；未配置、无权限或无法访问时必须说明。
- 线上或设备验证结果不得伪造；没有实际运行就只能写“未验证”。

## 动态输入

默认读取 Skill 套件根目录下的 `profiles/local.yaml`。用户不需要每次重复说明“读取 local.yaml”。

优先级：

1. 用户本次对话中明确提供的项目路径、分支、需求文档、UI 链接、接口链接。
2. 用户指定的配置文件，例如 `.codex/current-requirement.yaml`。
3. 默认配置：`profiles/local.yaml`。


支持动态输入：

- 定位参数：`project_path`（项目路径）和 `branch`（目标分支）。这是后续所有分析、修改、测试和验证的执行上下文。
- 固定需求文档：`requirement_file`，只表示需求正文、评审记录和验收标准来源，不强制包含 UI 或接口资料。
- 需求资料：需求描述、Jira、TAPD、飞书、语雀、Confluence、GitHub Issue。
- UI 资料：Figma、蓝湖、即时设计、摹客、MasterGo、截图、PDF、图片、字体、动效、资源 zip。
- 接口资料：Swagger、OpenAPI、Apifox、YApi、Postman、Markdown 接口文档、后端字段说明。
- 项目环境：模块名、build variant、server env、packageName、目标设备、测试环境。
- 验证要求：是否生成测试用例、是否跑构建、单测、lint、UI 测试、截图对比、logcat 扫描。
- 交付策略：仅分析、先做 UI 骨架、先做 mock、完整实现、只报告风险、允许修复。

不得把任何公司内部链接、账号、Token、密钥或业务规则写死进 Skill。

## 完整工作流

### 1. 读取项目规则和动态配置

先读取或识别：

- 默认配置 `profiles/local.yaml`，除非用户本次明确提供了其他配置。
- 用户提供的 `project_path` 和 `branch`。
- 指定项目路径下的 `AGENTS.md`。
- `README.md`、`CONTRIBUTING.md`、CI 配置。
- Gradle 模块、构建脚本、版本管理方式。
- 用户输入的 `requirement_file` 需求文档。
- 用户输入的需求、UI、接口、测试配置。

如果资料不完整，继续进入分析，但必须标记缺失项。

执行任何代码修改、测试、构建或 Git 操作前，必须先进行项目路径和分支校验：

1. 检查 `project_path` 是否存在。
2. 检查 `project_path` 是否是 Git 仓库。
3. 检查当前分支是否等于用户指定的 `branch`。
4. 检查工作区是否存在未提交改动。

如果当前分支不匹配，必须停止修改并报告当前分支、目标分支和可选处理方式。默认不得自动切换分支、创建分支、stash、reset、checkout 或清理工作区。

### 2. 需求理解循环

当用户提供 `requirement_file`、需求目录、需求链接、截图、接口资料或需求文字时，第一步必须先进入需求理解循环。

如果提供了 `requirement_file`，先把它当作需求正文来源读取；UI 和接口资料不要求在该文件中，除非文档本身明确包含相关线索。

需求理解循环流程：

1. 读取用户提供的需求资料。
2. 输出“当前需求理解”。
3. 等待用户确认。
4. 如果用户补充或纠正，必须合并补充信息并重新输出需求理解。
5. 只有用户明确表示“理解正确”、“确认”、“继续”或“可以进入下一步”后，才能进入正式影响范围分析、技术方案、测试用例、风险检查和执行确认。

需求理解确认后，后续分析阶段由 AI 自动推进，不需要用户逐项确认；只有遇到阻塞性不确定信息、高风险架构选择、公共模块影响、接口/数据兼容风险、分支异常或准备修改代码时才暂停询问用户。

需求理解未确认前允许：

- 读取需求目录、文字、截图、接口说明。
- 输出当前需求理解。
- 输出“初步影响范围（待确认）”。
- 输出待确认问题。

需求理解未确认前禁止：

- 把初步影响范围当成最终结论。
- 输出最终技术方案。
- 修改代码。
- 写死接口字段、枚举、业务规则或 UI 行为。
- 生成最终测试结论。

当前需求理解必须包含：

- 一句话总结。
- 业务目标。
- 涉及页面、入口或业务流程。
- 明确要做的内容。
- 明确不做或暂未提到的内容。
- 从资料中识别到的 UI、接口、数据、测试线索。
- 当前不确定问题。
- 是否足以进入下一步。

### 3. 需求变更分析

按 `android-change-review` 的思路输出：

- 任务理解。
- 当前项目事实。
- 已确认、合理假设、待确认、阻塞项。
- 影响范围。
- 复用方案。
- 分阶段实现建议。
- 风险点和验证计划。

### 4. UI 还原分析

当需求涉及 UI、设计稿、截图或页面变更时，按 `android-ui-verify` 的思路输出：

- 设计资料来源。
- UI 状态清单。
- 可复用主题、组件、资源。
- UI 未确认时的简易骨架方案。
- 截图或视觉验证计划。
- 无法像素级一致时的差异原因和待确认项。

UI 链接或截图缺失时，不得声称已符合设计稿；只能做项目风格下的低风险骨架或等待设计确认。

### 5. 接口契约分析

当需求涉及网络、字段、枚举、错误码、分页、鉴权或后端联调时，按 `android-api-contract-review` 的思路输出：

- 已确认接口契约。
- 合理假设。
- 待确认字段、枚举、错误码。
- 阻塞项。
- null、缺字段、空字符串、未知枚举、类型异常兜底。
- 可先做 mock / fake / sampledata 的范围。

接口未确认时，不得写死正式 endpoint、DTO 字段、枚举值或生产 mapper。

### 6. 用户确认闸门

进入代码修改前必须明确询问用户是否确认执行。用户未确认时，只输出分析、方案、测试用例和风险，不修改代码。

如果用户只允许阶段性开发，必须按阶段限制修改范围：

- `analysis`：只分析，不改代码。
- `ui-skeleton`：只做 UI 骨架和状态结构。
- `mock`：只做 mock / fake / sampledata，不接生产接口。
- `full-implementation`：资料基本确认后完整实现。
- `fix`：只修用户指定问题。

### 7. 代码实现后测试交付

实现后按 `android-test-delivery` 的思路执行：

- 生成测试用例矩阵。
- 标注 Unit / UI / Screenshot / CLI / Manual。
- 选择当前项目实际可运行命令。
- 按需使用 Android CLI、Gradle 或 adb 跑可运行的构建、单测、lint、截图或设备测试。
- 失败时分析原因，不得忽略。
- 无法运行时说明原因和剩余风险。

### 8. 稳定性审查

实现后按 `android-stability-review` 的思路扫描：

- 崩溃、空指针、数组越界、强转异常。
- 生命周期、内存泄漏、Context 持有。
- 协程异常、Flow 重复收集、请求乱序。
- 主线程耗时、ANR、资源未释放。
- Adapter / 列表复用错位、position 过期。
- Android 高低版本兼容和设备差异。
- 如有设备或线上资料，结合 logcat、Crashlytics、Firebase MCP 等证据。

默认只报告，不自动修复。

### 9. 代码质量审查

实现后按 `android-code-quality-review` 的思路检查：

- 是否符合当前项目架构和模块边界。
- 是否最小修改，是否混入无关格式化或重构。
- 是否有重复逻辑、硬编码、无用代码、调试日志。
- 是否把 mock 或假字段写进 release 逻辑。
- 是否需要补充测试、截图或人工验证。

默认只报告，不自动修复。

## 资料缺失时的默认策略

- UI 资料缺失：可以先做简易 UI 骨架或按项目现有组件风格实现占位，并列出设计待确认项。
- 接口资料缺失：可以先做领域模型草案、mock / fake / sampledata、debug-only 数据源，不接生产接口。
- 字段和枚举缺失：只能提出 Unknown / default 兜底方案，不能写死假字段。
- 测试环境缺失：生成测试用例和人工验证路径，不伪造自动测试结果。
- 需求规则缺失：列出问题清单，等待产品、设计、后端、测试或用户确认。

## 总入口输出格式

默认按以下结构输出：

1. 任务理解
2. 动态资料解析结果
3. 当前项目事实
4. 已确认 / 合理假设 / 待确认 / 阻塞项
5. 完整影响范围
6. UI 分析和设计还原策略
7. 接口契约和数据兼容策略
8. 分阶段实现方案
9. 测试用例矩阵
10. 稳定性风险检查计划或结果
11. 代码质量检查计划或结果
12. 回滚方案
13. 修改计划或变更摘要
14. 验证计划或验证结果
15. 剩余风险
16. 是否等待用户确认

如果某项不涉及，明确写“不涉及”。如果某项无法验证，明确写“无法验证 + 原因 + 建议”。

## 最终交付报告

代码修改和验证完成后，必须输出：

- 修改了哪些文件。
- 为什么这样改。
- 复用了哪些现有链路。
- 执行了哪些命令和结果。
- 生成或执行了哪些测试用例。
- 稳定性审查发现点。
- 代码质量审查发现点。
- 未验证项和剩余风险。
- 是否建议继续修复或提交。

# Android 需求实现与验证

把本 Skill 当作轻量编排器，不把交付过程实现成状态机。项目规则优先；不自动切分支、提交、推送、发布、操作生产数据或索取凭据。

## 按需读取

- 新窗口首次接手、恢复流程或需要查看完整流程：先读取 `../docs/FLOW_OVERVIEW.md`；需要看阶段关系时再读取 `../docs/FLOW_DIAGRAMS.md`。
- 澄清需求或整理规格：读取 `references/clarify-and-spec.md`。
- 编码、测试或处理增量变化：读取 `references/implement-and-test.md`。
- 收到 Figma、API 链接、截图、文件或聊天契约：读取 `references/figma-and-api.md`。
- 用户明确要求最终检查、准备提交或完整交付：读取 `references/final-delivery.md`。
- 维护或重写本流程：读取 `references/forward-tests.md`，用真实失败案例做前向验证。

不要一次加载全部参考资料。

创建或更新 `spec.md`、`api.md`、`result.md` 等需求 Markdown 时，在标题后维护可点击目录和稳定锚点；正文按章节、编号列表和必要表格组织，增量更新时同步目录，不保留失效链接或空章节。

## 核心流程

### 1. 先查事实

读取当前项目的 `AGENTS.md`、相关代码、Gradle、测试、当前分支与 Git 状态，以及用户本轮输入和当前需求自己的配置；未显式指定配置时才读取 `profiles/local.yaml`。能从代码、文件、工具或链接查到的事实由 Agent 自己查，不转问用户。

首次启动当前需求时，如果配置没有 `requirement_dir`，先查找 `<project_path>/document/*-<requirement_name>/`：唯一匹配时复用并写回；多个匹配时列出候选让用户选择；没有匹配时才使用本地当天日期创建 `<project_path>/document/YYYY-MM-DD-<requirement_name>/` 并写回解析后的绝对路径。后续窗口必须复用已写回路径，不按新日期重新推导；缺少 `project_path` 或 `requirement_name` 时只询问缺失项，不要求用户手工拼目录。

续接旧流程创建的需求目录时，若没有 `docs/spec.md` 但存在唯一 `docs/<requirement_name>.md`，把该文件作为本需求的兼容规格源，不自动复制、重命名或再建 `spec.md`。它没有 `status` 时，先从已有确认记录、续接文档和 Git 历史核对；仍无法证明确认状态时只向用户确认一次。确认后在同一文件补轻量 frontmatter。本文后续出现的 `spec.md` 均包含这个兼容规格源。

开始需求时记录当前提交作为 `baseline_commit`。工作区已有改动时先列出并说明是否可能属于本需求，等待用户决定纳入、隔离或先处理；不得自动清理、stash 或把旧改动静默混入。

引用路径在当前分支不存在时，保留原引用并说明“当前分支缺失”，询问参考分支或替代来源；不得自行切换分支、猜测来源或删除引用。

### 2. 集中澄清

只询问会改变用户行为、业务范围、数据含义、失败处理、验收结果、允许修改范围或资料来源的决策。把当前所有互不依赖的问题放在同一轮，编号并给出推荐答案；依赖未决答案的问题留到下一轮。

用户一次可以回答一个或多个问题，也可以同时纠正旧需求。完整吸收本轮所有变化，再计算剩余问题。存在产品级未知时不得拆 BDD、写计划或改生产代码。

### 3. 一次确认规格

问题清空后，创建或更新 `<requirement_dir>/docs/spec.md`，统一记录需求、BDD、已上线业务保护、范围、来源、实施决策和测试边界。每个 BDD 必须同时写明计划验证方式。先标记 `status: draft`；向用户展示变化摘要，只有用户对最新完整内容作出纯确认后才改为 `status: confirmed`。

需求和实施计划不再分成两次确认。小需求保持一份短规格；复杂需求才拆纵向切片。BDD 只描述可观察行为，不给未知行为填默认答案。

### 4. 纵向实现

规格确认后，以“一个行为测试 -> 最小实现 -> 受影响验证”为一个切片。优先复用项目已有公开测试边界、构建命令和测试设施；不为本 Skill 创建通用 Journey 工程或平行测试框架。

实现期间只跑当前测试、相关模块测试和必要编译。完整测试、Lint、UI/API 专项和代码审查只在最终交付阶段执行一次。

### 5. 增量更新

- **需求语义变化**：把规格改回 `draft`，只澄清和确认变化部分；受影响 BDD 与测试重做，未受影响内容保留。
- **范围或测试边界变化**：把规格暂时改为 `draft`，只更新并确认范围或测试边界变化，不重新确认完整需求；确认后恢复 `confirmed`。
- **纯视觉或实现细节变化**：规格保持 `confirmed`，只修改受影响代码并运行最小验证。
- **最终验证后代码再变化**：旧结果不能代表当前代码；重跑受影响项，并重新完成最终汇总。

UI/API 资料变化是否回退确认，以它是否改变已确认行为或验收为准，而不是以文件类型判断。

### 6. 最终交付

只有用户明确要求最终交付、最终检查或准备提交时，才按当前 Git diff 运行完整测试和适用专项。最终结论只能是已通过、部分通过但有明确待验证项、失败或受阻；没有执行的验证不得写成通过。

Git 提交仍需用户明确授权。

## 不可削弱的底线

- 需求未确认前不修改生产代码；确认后发现语义未知立即回到澄清。
- Figma 链接和 API 输入必须保留来源，不得静默忽略或改成手写替代。
- Mock、Fake 和 sample data 默认与 release 生产路径隔离；用户明确批准主代码中的最小占位时，必须记录用途、入口和待对接边界，且不得冒充真实能力。
- 测试必须真实执行且数量非零；历史报告、空测试和未验证项不能支持通过结论。
- 每个 BDD 必须在最终 `docs/result.md` 中对应真实自动测试或可复现人工步骤；只证明“跑过一些测试”不能支持完整通过。
- 不扩大用户确认范围，不掩盖新增 Lint Error、崩溃、隐私、安全或兼容性风险。

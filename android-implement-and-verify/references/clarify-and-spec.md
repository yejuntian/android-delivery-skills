# 澄清与规格

## 决策树提问

先建立决策树：某个答案会影响哪些后续行为、范围和验收。每一轮只询问当前前沿，也就是前置事实已经明确的问题。

- 同一轮列出所有互不依赖的关键问题，使用 `Q1`、`Q2` 编号。
- 每题说明为什么需要决定，并给出一个推荐答案；只有确实互斥时才列选项。
- 事实查证是 Agent 的工作；产品取舍才交给用户决定。
- 用户可回答任意数量的问题。逐项吸收，不因只回答 Q2 就丢失 Q1。
- 新答案推翻旧答案时，以最新明确表述替换旧内容，并说明变化。
- 前沿为空后，先复述共同理解，等待一次完整确认再行动。

不要为了“覆盖全面”询问不影响当前交付的理论边界。实现可自行选择且不改变用户可见结果的内容，记录为实施决策即可。

## 规格文件

新需求统一使用 `<requirement_dir>/docs/spec.md`。续接旧流程目录时，如果 `spec.md` 不存在但有唯一 `docs/<requirement_name>.md`，继续在该文件增量维护并把它视为本文所称的 `spec.md`，不自动复制、重命名或制造第二份事实源。旧文件缺少状态时先核对已有确认记录；无法证明时让用户确认一次，再在同一文件补 frontmatter。

```markdown
---
status: draft
baseline_commit: <需求开始时的 Git 提交>
---

# <需求名称>

## 目录
1. [问题与目标](#spec-goal)
2. [已确认行为](#spec-behavior)
3. [已上线业务保护](#spec-protection)
4. [BDD 验收与计划验证方式](#spec-bdd)
5. [UI 与 API 来源](#spec-sources)
6. [实现范围](#spec-scope)
7. [实施决策](#spec-decisions)
8. [测试边界](#spec-testing)
9. [不在范围](#spec-out-of-scope)
10. [待确认](#spec-pending)

<a id="spec-goal"></a>
## 问题与目标

<a id="spec-behavior"></a>
## 已确认行为

<a id="spec-protection"></a>
## 已上线业务保护
### 本次明确修改
### 必须保持不变

## BDD 验收与计划验证方式

### BDD-01：<可观察行为>
- **Given**：<前置状态>
- **When**：<用户动作或事件>
- **Then**：<可观察结果>
- **计划验证**：<自动测试或可复现人工步骤>

<a id="spec-sources"></a>
## UI 与 API 来源

<a id="spec-scope"></a>
## 实现范围

<a id="spec-decisions"></a>
## 实施决策

<a id="spec-testing"></a>
## 测试边界

<a id="spec-out-of-scope"></a>
## 不在范围

<a id="spec-pending"></a>
## 待确认
```

规则：

- `待确认` 非空时保持 `draft`，不新增或改写任何 BDD，保留已有且未受影响的 BDD；清空后补齐受影响 BDD 和计划验证，再请求规格确认。
- 复杂需求增加“纵向实现切片”时，同时把该章节和稳定锚点加入目录；小需求不保留空切片章节。
- 每个 BDD 使用独立三级标题，把 Given、When、Then 和计划验证拆成四行；只写外部可观察结果，不把叙述型 BDD 塞进表格单元格。
- 每个 BDD 在确认前写明计划验证方式；自动化不可行时写可复现人工步骤和原因，不得只写“人工验证”。
- “本次明确修改”只列需求要求改变的旧行为；“必须保持不变”只列本次改动可能波及且已有事实支持的可观察行为，不把全部历史实现固化为需求。每项直接受影响的保护行为也要进入 BDD 和计划验证方式。
- “实现范围”记录允许触碰的模块或边界，不维护逐文件 JSON 白名单。
- “测试边界”优先使用项目已有最高公开边界，复杂需求才列多个测试层。
- Figma、接口网页、截图、文档、聊天决定都可以作为来源，记录定位、用途和未证明内容。
- 用户确认的是当前完整规格。确认后写 `status: confirmed`；后续语义、范围或测试边界需要重新决定时才恢复 `draft`。
- 请求规格确认时明确说明：确认后将在当前独立需求分支自动创建 `SPEC`、`BDD-##` / `SLICE-##` / `MIGRATE-*` 和 `RESULT` 本地边界提交，但不会自动改写历史、推送、集成或发布。用户确认后，先审查 `spec.md`、同次归一化的 `api.md` 和明确输入证据，自动形成一个中文语义 `SPEC` 提交，例如 `SPEC 确认订单取消需求与验证边界`。不得夹带生产实现、本机配置或其他需求文件；首次进入实现前提交并恢复干净工作区，实现中途的变化按 [增量闭环](implement-and-test.md#incremental-loop) 处理。
- 标题后的目录使用稳定锚点并与当前章节同步；解释优先使用编号列表或表格，不保留空占位章节。

用户提供 `.docx`、PDF、截图或网页时，使用对应读取能力提取事实，再写入 Markdown；不要为每种输入形态增加流程脚本。

## 交付边界与纵向切片

事实查清且产品未知清空后，由 Agent 在“实施决策”简述交付结果、验证入口及整体交付或分片的依据，随规格一次确认。先尝试整体交付；必要代码和依赖可掌握、预期能由一个没有历史对话的新上下文完成实现、验证和提交审查时，不增加切片章节。BDD 数量、文件数、行数、工时和累计 Token 不作为硬阈值；新上下文可完成性是需在执行中复核的判断，不是精确 Token 估算。

BDD 表达验收，提交表达完整交付边界。同一能力的成功、空数据、失败等紧密相关 BDD 可以一起交付并在标题列出对应 `BDD-##`；边界内逐条测试和实现，不机械地每条 BDD 一个提交。整体过大或需要明确分组和依赖时，在同一规格增加“纵向实现切片”：每个 `SLICE-##` 都要能回答“完成后可独立观察什么、如何验证、依赖哪些已完成行为”，覆盖该路径必要的实现和测试，不按数据层、业务层、UI 层拆分。

此尺寸与纵向交付原则参考 [Matt Pocock 的 to-tickets](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/to-tickets/SKILL.md#L25-L56)；单份规格、边界提交 ID 和增量闭环是本 Skill 的流程选择。

```markdown
<a id="spec-slices"></a>
## 纵向实现切片

### SLICE-01：<可独立交付的行为>
- **覆盖 BDD**：BDD-01、BDD-02
- **交付行为**：<用户或外部系统可观察的结果>
- **blocked_by**：无 / SLICE-xx
- **计划验证**：<自动测试或可复现人工步骤>
```

- BDD、Slice 和迁移 ID 在当前需求内稳定；已入提交历史的 ID 不重编号，也不用于无关新行为。拆分时新增 ID 并在实施决策简述替代关系，同一行为修订沿用原 ID；明确取消的内容从当前有效要求和依赖中移除，历史由 Git 保留。
- 切片只记录计划，不写“进行中 / 已完成”、实际测试结果、提交 SHA 或排障过程。执行证据由 Git 提交和最终 `result.md` 承担，避免规格同时成为输入和输出。
- 一个切片过大而无法形成单个可审查提交时，继续按可观察行为拆小；确实属于全局机械迁移时，在“实施决策”记录 `MIGRATE-EXPAND`、各 `MIGRATE-##` 批次和 `MIGRATE-CONTRACT` 的范围与依赖，再使用实现流程中的 expand-migrate-contract，不制造伪纵向切片。
- `blocked_by` 只表达真实依赖，不为天然可独立的切片强加顺序。
- 每个边界开始前复核粒度；仅细化分组、顺序或剩余计划且不改变行为、范围、契约或测试边界时，保持 `confirmed`，更新实施决策并形成 `SPEC` 提交，不重复请求确认。改变这些边界或实现中途发现估小了时，按 [增量闭环](implement-and-test.md#incremental-loop) 收拢，不靠提交半成品建立检查点。

## 项目能力缺失

需求依赖的能力在当前项目或当前分支不存在时，例如登录态、登录页、分享组件或参考包：

1. 说明缺少什么、查过哪些位置，以及它会影响哪个行为；不得脑补现有实现或删除原引用。
2. 把处置列为用户决策，可选真实接入、指定参考分支/路径、最小占位或缩小范围。
3. 只有用户确认后才实现最小占位。默认放在 debug、测试或独立测试入口；用户明确要求主代码占位时，记录入口、隔离边界和待替换风险。
4. 占位只能模拟已确认结果，不得扩建完整子系统，也不得在最终报告中冒充真实登录、接口或分享能力。

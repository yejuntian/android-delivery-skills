# Android Skills 共享全局规则

适用于 `android-delivery-skills` 下所有 Android Skill。只保留跨项目通用铁律，不写公司私有信息，不复制各 Skill 已有的执行细节。

## 设计依据入口

- 维护、扩展或质疑本流程时，先读取 `../references/open-source-design-rationale.md`，确认设计目标、开源参考、采用/拒绝原因和长期不变量；日常执行需求不要求全文加载。
- 开源做法只提供可验证的工程经验，不覆盖用户明确目标、目标项目事实或本文件的安全边界。
- 修改 Skill、脚本、配置、Schema、路由、门禁或用户可见流程后，交付前主动核对并最小同步职责对应的运行时来源、设计依据和测试；不相关文档不改，说明文档只摘要或链接，不复制第二套执行规则，用户无需提醒。
- 修改规则时必须先把"本次新增目标"和"旧约束保护清单"分开核对；新增或重写只能做最小增量，不得因只关注新增目标而删弱需求确认、旧业务保护、证据新鲜度、影响半径、职责归属、Git 授权或设备降级等既有门禁。无法确认旧约束是否仍适用时先保留并说明，不默认移除。
- 本机首次维护本流程时先执行 `python3 scripts/install_maintenance_hook.py` 安装 pre-commit 自动验证；修改本文件、任一 `*/SKILL.md`、设计依据、流程契约、Oracle、路由、门禁或脚本行为后，交付前必须从本仓库根目录执行 `python3 scripts/validate_maintenance.py`，统一运行规则归属测试和 fast eval。普通 Android 需求没有修改流程仓库时不运行。

## 全局强制工程原则

以下规则是所有 AI 编码、测试、审查和自修复时必须遵守的强制门禁，适用于总入口、专项 Skill、独立调用、自修复和测试补齐。用户不需要重复提醒。AI 编码十二条强制约束必须始终生效：CODING-01 先思考再编码；CODING-02 简单优先；CODING-03 只改任务相关代码；CODING-04 只说最终验收标准；CODING-05 只做判断不写死逻辑；CODING-06 严格控制 token 消耗；CODING-07 代码冲突先读源码不妥协；CODING-08 拒绝假测试；CODING-09 分阶段设检查点；CODING-10 遵守原有代码风格；CODING-11 有问题不隐瞒；CODING-12 遇不合理结构主动说明。任何阶段都不得用“顺手优化”或“统一重构”绕过。

### 最小化修改

- 修改前先根据已确认需求、真实代码和失败证据确定最小落点，同时明确不修改范围、关键假设和可验证成功标准；多种解释会影响行为或验收时先确认，不静默选择。
- 优先复用项目现有组件、分层、工具类、资源和测试范式；只改需求或根因直接涉及的文件与代码。生产逻辑只表达已确认业务规则和项目事实，禁止把临时样例、测试账号、本机路径、环境值或未确认接口字段写死。
- 禁止混入无关格式化、重命名、目录调整、依赖升级、Gradle 改造、公共组件重构或架构迁移。
- 修复测试、构建、Lint 或审查问题时，只关闭本次改动引入或暴露的直接问题；不得借自修复扩大需求范围、删除测试、弱化断言、增加未请求抽象/配置化或处理不可能场景。
- 如果客观上必须扩大修改范围，先给出代码、日志或依赖关系证据，说明新增范围和风险；涉及高风险边界时等待用户确认。
- 编码后复核实际 diff；每行改动都应能追溯到用户请求、已确认计划或失败证据，同时不得超出已确认影响半径。发现无关改动必须移除，无法移除时明确报告，不得把扩大范围包装成必要修改。

### 单一职责

- 新增或修改代码必须服从项目现有模块和分层职责；UI、业务规则、网络、存储、系统能力和测试逻辑不得无依据地混在同一层。
- 只有现有职责无法合理承载且需求确实需要时才新增类、脚本、抽象或依赖；能用更简单方案满足已确认 Then 时必须简化，不得为一次调用创建无复用价值的体系。
- 每个脚本只处理一种工程事实或动作。例如 Git 脚本只读取 Git 状态，不判断 Android 业务含义或决定 Skill 路由。
- 每个 Skill 只执行自己的专业检查或交付职责。发现跨职责问题时记录证据并路由到对应 Skill，不得静默越权处理。
- 最终报告必须能说明“为什么这些文件属于本次范围”和“每个新增组件负责什么”；无法说明时视为职责或范围未收敛。

### 已上线业务保护

- 当前需求明确要求改变的已有业务，只能在用户确认范围内修改；没有被当前需求明确覆盖的已有行为默认保持不变。
- 最终需求确认前，AI 必须只读、定向分析目标项目的相关模块、实现、调用方、共享状态、接口/存储边界和已有测试。目标是识别本次真实影响，不是逐行扫描全仓库；此阶段禁止修改代码、运行构建/设备任务或用项目现状替用户决定业务预期。
- 需求说明必须使用自然中文列出“本次明确修改”“必须保持不变”“暂时无法确认”和“明确不修改范围”。涉及已有业务时分别使用 `【修改已上线业务】`、`【保护已上线业务】` 标记对应 BDD 场景；暂时无法确认项写入“待确认”，不能进入编码。
- `【保护已上线业务】` 只用于本次修改可能波及且已有事实支持的可观察行为，不把每个旧文件、历史实现细节或疑似旧 Bug 机械固化为需求。事实不足时先询问用户。
- 用户补充或改变旧业务处置后，先写回需求事实源并重新确认；确认后的修改项和保护项统一进入 BDD 场景、测试映射和新鲜证据门禁，不新增审批阶段。
- `docs/需求测试追溯.md` 由脚本从需求快照、测试映射和交付结果生成，不要求人工同步，也不作为独立门禁输入。
- 最终 diff 发现确认范围之外的已有业务影响时，必须暂停最终交付，回到受影响需求修订并提醒用户；不得只在报告中补一句说明或由 AI 自行决定。
- 最终中文摘要必须优先展示已确认的旧业务修改、保护项及其验证状态。任何必需保护项未验证、受阻或回归失败时不得使用完整通过结论。

### 三阶段执行边界

这是本流程的核心铁律，详细命令、需求修订流程、测试映射、route 编排和最终门禁见 `android-implement-and-verify/SKILL.md`，本文件只规定不可逾越的边界。

- **首次编码前准备**：新需求先理解输入并只读、定向分析相关实现、调用方和已有测试，完成已上线业务影响提醒、场景级 BDD、用户确认、测试设计、最小修改预览、环境检查、Git 基线、实施计划和影响半径确认；这套准备只为当前需求建立一次，不因未改变计划与影响半径的实现完善而重复。
- **首次确认草稿收敛**：首次 `check-env` 前用户每次新增、修改、删除、纠正或改变旧业务处置时，先按自然中文列出本轮变化摘要，合并进最新完整需求并同步 `requirement_file`、重新执行 `init` 读取成功才回复下一问；默认不在聊天重贴完整需求，带新变化的"确认"不推进基线或首次确认。
- **需求模糊先问再拆**：`init` 发现需求缺少 BDD 或存在产品行为、范围、数据来源、失败恢复、权限或验收歧义时，按“已确认事实 / 待用户决定的问题 / 可延后的实现细节”三分法处理，只展示已查明事实和最高优先级问题并停止。凡会改变用户行为、业务范围、验收结果、数据含义、权限、失败恢复、允许修改范围或参考资料来源的未知都必须询问；命名、数据结构和具体实现方式可延后。用户一次可回答多个问题，Agent 必须逐项合并全部答案，删除已解决项、保留未解决项、写回 `requirement_file`、重新 `init`，仍有问题时只追问剩余最高优先级项。只有纯确认且待确认清空后才生成 BDD；不得用猜测、默认值或 `- 无` 提前填充。
- **事实来源不猜测**：按来源实际形态保留最小定位和用途，不强制链接、截图、文件、代码和聊天使用同一结构。代码参考记录仓库、`reference_branch` 和路径；当前分支缺失时保留原引用并询问，不自行切换、猜测、删除引用或改写需求。关键业务与契约事实统一写回 `requirement_file`；实现阶段发现语义问题时回到澄清阶段并使受影响映射 `STALE`。
- **需求确认与计划门禁**：用户明确确认最新完整需求后，依次完成 `check-env`、`confirm-requirement-update`，再拆分测试并生成唯一 `<requirement_dir>/docs/实施计划.md` 与 `<requirement_dir>/test-cases/impact-radius.json`；用户只需确认业务目标、验收标准和边界，不要求指定技术实现，影响半径用于明确允许触达范围。计划固定展示“实现范围、已上线业务影响、预计修改文件、测试方案、影响半径摘要、明确不修改范围”六类内容，聊天只给摘要与链接；`confirm-plan` 只做低成本交叉校验：计划中的 BDD、预期文件和预期测试必须对应当前影响半径，不解析完整 Markdown 语义。影响半径同时作为最终 diff 和测试映射的机器边界；用户明确确认后执行 `confirm-plan`，成功才编码，不追加冗长方案会。
- **编码后局部迭代**：首次实现后用户提出完善/修改/删除/修复时，先判断验收语义是否改变。语义不变则不重新执行 `init`、需求确认、`route`、全部专项 Reviewer 或最终报告，只做最小代码修改、受影响测试和必要最小编译；删除生产代码时检查调用方。
- **需求语义变化**：新增、删除或改变业务行为、边界和验收结果时，只对受影响义务执行需求修订与确认，同步影响半径、受影响测试和同一实施计划；已有当前需求 Git 基线时不得重复 `check-env`，也不得把全部交付门禁重跑一遍。
- **最终交付**：只有用户当前或最初请求已明确包含"最终检查、完整交付、准备提交"等意图时，才执行最终 `route`、专项审查、完整必需测试、构建、Lint 和交付报告。局部迭代结果只证明本轮受影响范围，不得宣称整体交付完成。
- **专项任务闭环**：`route` 只在 `.state/route-impact.json` 登记 `specialist_tasks`，不直接调用专项 Skill；执行者必须为每个必需任务回填对应 gate 结果，最终交付门禁逐项校验当前结果。任务可以明确 `SKIPPED`，但必须由适用性规则允许并附中文原因和复核证据，不能静默省略。
- 已生成最终结果后代码、测试、资源或构建配置再次变化时旧最终结果立即失效；后续完善期间仍先走局部迭代，用户再次进入最终交付时只基于最终代码完整验证一次。

### 证据新鲜度与防假绿

- `init` 永不删除需求 Git 基线，重复 `check-env` 永不覆盖当前起点；后续需求修订不得重建该基线，只有用户明确的新串行需求可以使用 `--new-requirement` 更换起点。
- **基础必开 1：需求/计划/影响半径/最终代码 SHA 绑定**。最终通过结论必须绑定当前需求文件摘要、已确认实施计划、已确认影响半径、需求 Git 基线和最终工作树摘要。
- **基础必开 2：STALE 测试映射**。每个独立业务触发使用一个 `BDD-###` 场景；一个场景可以映射多个真实测试 ID。`COVERED_AUTOMATED` 场景必须在 `<requirement_dir>/test-cases/test-mapping.json` 登记、`mapping_status=CURRENT`，最终证据只关联该场景登记且本次真实通过的 testcase；场景语义变化后旧登记自动标记 STALE。
- **基础必开 3：最终执行收据和非零测试门禁**。只有所有必需验证义务都有最终代码上的新鲜执行收据，且测试执行数大于零，才允许声明整体全绿；计划人工执行但尚未实际执行时仍为未验证。
- 测试预期必须有独立事实来源（需求/契约/确定样例），不得用与生产代码相同的算法重新计算答案；不得通过删测试、注释断言、扩大容差、`@Ignore` 或把失败改成人工项造绿。
- 需求、计划、影响半径或代码变化时旧 route 与证据自动失效。最终 diff 超出已确认影响半径时必须回到受影响需求/计划/影响半径重确认，或移除无关改动，不能口头豁免。
- 最终交付的执行收据、专项结果和路由快照的机器契约见各 Skill 的 `references/` 和 Schema；人读产物（续接指南/修订说明/映射说明/交付结论）由脚本从 JSON 渲染，不是第二事实源。
- 失败自动收据只可在非通过结论中证明同一 `FAIL` gate；不得用于 BDD 自动覆盖或任何 `PASS` gate。

## 强制工具链兜底策略

遇到以下疑难时严禁凭空盲猜或仅靠代码分析，必须强制调用工程工具诊断：

1. **复杂 UI 调试**：元素不可见、尺寸异常或被遮挡时，强制用 `android layout` 拉取真实 View Tree 定位，不盲改 XML 参数试错。
2. **性能与卡顿**：卡顿、ANR 或泄漏优化必须先采集 Trace、Leak Trace 或 Heap Dump，用真实数据找瓶颈，不背诵通用理论或直接改业务代码。
3. **Gradle 冲突**：`Duplicate class` 或依赖版本冲突必须运行 `./gradlew dependencies` 打印依赖树，分析冲突链路后用 `exclude` 精准解决，不盲改版本号。
4. **Release 混淆闪退**：`ClassNotFoundException` 等混淆问题必须用 `r8-analyzer` 或查阅 `usage.txt`/`mapping.txt` 精准定位，仅对引发崩溃的最小闭环加 Keep，不大面积通配符关混淆。
5. **异步生命周期**：协程、RxJava、Handler、Callback 生命周期异常必须追溯宿主、任务、线程和取消/释放关系，不用无所有者全局任务或固定延时掩盖。
6. **大版本适配与权限**：权限申请和隐式 Intent 修改必须调用 `android docs search` 查阅目标 API Level 官方变更指南，以最新规范为准，不依赖模型记忆。

## 外部资料读取与安全边界

- 外部资料读取优先级：用户本次明确文字/截图/文件 → 本地资料（`requirement_file`、`ui.screenshots`、`api.files` 等）→ 结构化工具（Figma MCP、OpenAPI/Apifox 导出）→ 浏览器可见页面 → 公开网页。能读到的立即纳入；读不到只记录"外部资料未读取"，不默认终止整个流程。
- 当前需求或 diff 涉及接口契约时，按可用来源读取：平台链接、截图、用户文档、项目代码或聊天确认均可；关键 operation、字段、必填性、错误与分页语义写回 `requirement_file` 并保留来源定位。`api.files` 只登记用户已提供或项目已有的稳定文件，不强制生成本地 API 文档。来源不可读或相互冲突时只询问会改变实现或验收的事实；不得索要账号、密码、Cookie，也不得把聊天决定冒充正式服务端契约。
- 链接不可读但本地资料足以理解需求时继续进入需求理解，在待确认问题和最终报告中标记未读取链接及剩余风险；用户说"跳过链接""用 mock/fake""先按现有资料做"时必须降级继续。
- Figma 资料优先通过 MCP 读取结构化设计数据；但 MCP 能否调用取决于运行时模型的 tool-use 能力，不可用时直接降级为用户截图/导出，固定到 `<requirement_dir>/ui/`。需要本地视觉基准时可用 `figma_workflow.py fetch` 下载 PNG。UI 交付先通过共享设备预检确认物理设备和截图成功，再以 Figma 链接、真机截图/差异图链接和人工结论为主，不绑定 APK、versionCode 或截图 SHA-256。
- Token、Cookie、账号、密码不得写入 `local.yaml`、需求文档、Skill 或 Git；不得要求用户手动提供凭据；Personal Access Token 只能放环境变量、钥匙串或密钥管理器。

## 资料缺失降级

- 需求引用的本地路径在当前实现分支不存在时，必须保留原引用并向用户报告“当前分支缺失”，询问参考分支或替代路径；不得自行切换分支、猜测路径归属、删除引用或把它写成“不再依赖”。

- 需求已明确但正式接口或 UI 资料未到时，不阻断可独立完成的业务开发：根据需求定义领域模型、交互状态、临时契约和临时 UI，用 Mock/Fake/sampledata 跑通业务与测试，统一标记"根据需求推导，待正式资料对齐"。
- 正式 DTO、Endpoint、序列化字段、错误码、枚举不得靠猜测；Mock/Fake/sampledata 只进 debug、Preview 或测试，不混入 release 生产路径。临时 UI 可进主代码，但没有设计基准时不得声明像素级还原通过。
- 资料到达后只调整受影响 DTO/Mapper/DataSource/资源/表现层并重跑受影响测试；资料改变已确认业务语义时才进入需求修订。

### 依赖缺失与假设占位

- 需求依赖的项目能力**不存在**（如"现有登录页"但项目无登录系统、"未登录判断"但无登录态、"分享"但无分享组件）时，**不得脑补实现、也不得新建整套体系**，按下列顺序处理：
  1. 在需求核对阶段明确指出"项目缺少 X 能力"，列入待确认。
  2. 用户确认后，用**最小假设占位**（如 `UserManager.isLoggedIn()` 返回固定值、新建一个最小 Activity 占位），不扩大为完整子系统。
  3. 占位实现必须标注"假设占位，待真实能力对接"，并在最终报告残留风险里说明。
- 需求要求的技术栈项目**当前不具备**且需求明确要求引入（如项目纯 Java，需求要 Kotlin+Retrofit+协程）时，视为**合法技术栈扩张**，不是 AI 擅自引入：
  1. 在需求核对阶段标出"本次将新增依赖 X/Y/Z"，列出对 build 系统（Version Catalog、AGP、JDK）的兼容影响。
  2. 用户确认后，按项目既有依赖管理方式引入（有 Version Catalog 走 TOML，否则遵循项目现状），不另立体系。
  3. 区分"需求明确要求的扩张"（允许）与"AI 顺手引入的便利"（禁止），后者仍受最小修改约束。

## 项目优先

所有方案必须服从当前项目事实，优先读取 `AGENTS.md`、`README.md`、`CONTRIBUTING.md`、相关 `CONTEXT.md`/领域术语表/`docs/adr/`、Gradle 配置、CI 配置和相关模块代码与测试。项目规则比本 Skill 更严格时优先遵守项目级规则；尤其项目 `AGENTS.md` 要求修改前展示 diff 并等待同意时，不得绕过审批。不得假设项目一定使用 Compose、Hilt、Retrofit、Room、Coroutines、Flow 或固定架构。

## Skill 职责边界

- `android-implement-and-verify`：完整需求交付总入口（需求确认、BDD、测试物化、编码、路由编排、自修复、最终门禁）。
- `android-review-diff`：实际 diff、业务逻辑、变更范围、架构边界、回归和上线风险审查。
- `android-verify-api-contract`：接口、DTO、请求响应、mapper、Repository 网络行为、缓存字段、OpenAPI 契约兼容审查。
- `android-verify-ui`：UI 还原、设计稿/截图一致性、资源规范、页面状态、可见轻交互和人工/设备 A11y 表现验证；保持手动独立，不被 route 自动调用，不定义或执行 Journey 等测试用例。
- `android-test-and-fix`：BDD 测试物化、Journey/截图/仪器/迁移/A11y 测试、条件能力命令、执行结果和测试失败自修复。
- `android-audit-stability`：崩溃、生命周期、协程、动态泄漏、ANR、性能、运行时安全隐私、资源释放和 Android 版本兼容风险。
- `android-review-code-quality`：代码质量、可维护性、架构一致性、资源规范、重复逻辑、依赖边界和测试覆盖风险。

各 Skill 详细检查清单、输出 Schema、条件能力触发规则、Journey 适用性、测试层选择和失败分类见对应专项目录的 `SKILL.md` 和 `references/`。发现属于其他职责的问题只记录并路由，不越权处理。

## 需求文档与事实源

- `requirement_file` 指向 `.docx` 时，`delivery.py init` 首次自动提取正文并转写到 `<requirement_dir>/docs/<需求名>.md`，后续补充、修订和门禁只同步该 md，原 docx 仅保留初始输入；图片型 docx 提取不到正文时使用需求模板骨架并进入待填充，不得脑补。
- `init` 只读取 `.docx`、`.md`、`.markdown`、`.txt`；PDF 作为需求正文时必须先转换为支持格式。需求文档无法读取或信息不足时必须说明缺失内容，不得脑补。

## 默认输入

- 默认读取 Skill 套件根目录下的 `profiles/local.yaml`，用户不需要每次重复说明；输入优先级为：用户本轮明确提供的路径或参数 → 命令显式 `--config` → 默认 `profiles/local.yaml`。
- `profiles/local.yaml` 是用户所有本机运行输入，必须由 Git 忽略；仓库只提交带完整中文字段说明且不含真实路径、链接和业务资料的 `profiles/local.example.yaml`。首次使用时从示例复制，已有 `local.yaml` 时不得用示例覆盖。
- `requirement_dir` 及其需求正文、实施计划、UI/API 证据、测试用例和报告属于当前需求运行工作区，默认不进入 Skill 源码版本控制；不得因为文件被忽略就删除、清空、强制加入 Git，或把示例值当成真实输入。

## 串行需求与多需求并行

- `scripts/requirement_workspace.py` 是需求目录轮换和延迟回收的唯一入口。同一需求的补充、修改、删除、局部重测不得轮换；只有用户明确确认上一需求已经完成或取消并说"开始下一个需求"时，才先执行 `next` 预览，用户确认预览后追加 `--confirm`。
- 新需求正文必须先放在旧活动目录之外；轮换前目标 Android 项目必须干净。脚本只迁移项目外需求资料并更新 `local.yaml` 的 `requirement_dir`、`requirement_file`，不得提交、暂存、清理或修改 Android 代码。
- 轮换后必须先对新目录执行 `delivery.py init` 并确认新需求理解，再执行 `check-env --new-requirement`；不得让新需求复用上一需求 ID、BDD 场景、Git 基线、测试用例或最终证据。
- 延迟回收必须同时满足"不是活动目录、状态明确为已经完成或取消、超出最近保留数量、超过保留天数"；活动、未完成、近期或状态损坏的目录不得删除；默认命令仅预览，只有显式 `--confirm` 才执行。
- 同一配置文件同时只允许一个活动交付窗口写入基线、需求修订、实施计划收据、route 或最终证据；多需求并行靠每需求独立 git worktree + 独立 profile + 独立 requirement_dir，机器状态位于各自 `requirement_dir/.state`。详细并行边界、合并策略和集成报告见 `android-implement-and-verify/SKILL.md`。

## Kotlin / Java 与老项目兼容

- Kotlin 是现代 Android 优先方向，Java 是老项目一等支持语言；混合项目共用同一交付流程，不新增重复 Java Skill，不强制迁移语言。
- 生命周期和静态语义统一检查六条不变量：短生命周期不被长生命周期持有、注册/解绑成对、获取/释放成对、异步任务不超过宿主、清理路径可达、共享状态具有并发纪律。详细静态语义路由、工具策略和告警分类见 `android-audit-stability/references/`。
- Java/Kotlin 互调按真实调用方核对 Nullability、platform type、primitive/boxed、异常、泛型、SAM/Callback、取消传播和公开契约；不机械添加 JVM 注解。
- 只发现和执行项目已有编译、Lint、语言专项、跨语言扫描、测试及 ABI/API 任务；不自动安装工具、升级构建或创建新规则体系。老项目告警必须区分本次新增、直接受影响、无关历史和来源不明；不更新 baseline 或批量 suppress 掩盖新增问题，也不顺手清理无关历史债务。

## 项目路径与分支

执行代码修改、构建、测试或 Git 操作前，必须检查 `project_path` 存在且为 Git 仓库、当前分支等于配置 `branch`、工作区无未提交改动。默认安全策略：

- 分支不匹配时停止修改，报告当前分支和目标分支。
- 完整交付在 `check-env` 建立当前需求基线前要求工作区干净（交付文档 `document/` 的改动不算代码脏，已自动忽略）；发现已有改动时列出并停止，避免串入上一需求。
- 不得默认自动切分支、建分支、stash、reset、checkout、clean；只有用户明确要求后才执行对应 Git 操作。当前需求基线只用于界定 diff，不代表提交、暂存或用户授权。

- 默认先做需求理解；用户纯确认最新完整需求后，完成 `check-env`、`confirm-requirement-update`、测试拆分和实施计划展示，用户确认计划并成功执行 `confirm-plan` 后才编码。未经用户确认需求与计划，不修改代码。
- 影响 Gradle、依赖、数据库迁移、登录、支付、权限、WebView、CI、签名、混淆或公共组件边界的变更必须二次确认。不得伪造构建、测试、lint、截图、logcat 或设备验证结果；无法验证时必须说明原因、能力缺口和建议验证方式。
- 由总入口编排完整交付时，视为用户已授权修复本次已确认范围内的技术问题：P0/P1、验收测试失败、构建失败和 lint Error 必须立即修复并重跑；P2/P3 仅在不扩大需求范围时修复，否则列为能力缺口。计划外已上线业务影响、需求冲突或业务预期不明确即使评为 P0/P1 也必须先重新确认需求。
- 自修复不得越过分支、生产数据、破坏性操作、关键资料缺失或需求边界。同一根因连续 3 轮仍失败时暂停，提交证据和阻塞项；详细失败分类、专项能力失败与 AI 接管边界见 `android-implement-and-verify/SKILL.md` 和测试 Skill 的 `references/`。

## 条件专项门禁与设备降级

- OpenAPI、数据迁移、动态泄漏、性能、UI/A11y、安全隐私只在已确认需求或实际 diff 触发时执行；不适用必须写明依据，不得机械运行全部能力。详细触发规则见 `android-implement-and-verify/references/conditional-capability-gates.md`。
- 缺少真机不阻断需求理解、编码、构建、单测、lint、契约、迁移静态检查和其他仍可执行门禁，也不得提前终止后续专项检查；模拟器能等价验证的功能优先继续执行。
- 正式性能、厂商 ROM、真实硬件和需求明确指定的真机验收没有等价替代时保持"未验证"，最终结论必须明确"代码与本地门禁完成，真机专项待验证"。不得为启用条件能力自动增加 LeakCanary、Benchmark 等重型依赖，先复用项目和本机已有工具。

## 大厂级工程规范（强制底线）

- **多模块防腐**：添加跨模块依赖前先检索 `settings.gradle`；严禁底层模块反向依赖上层、严禁循环依赖。不确定谁能依赖谁时停下来问用户，不凭模块名盲猜。
- **Version Catalog**：修改依赖前先探测 `gradle/libs.versions.toml`；存在时禁止在 `build.gradle` 写死版本号，必须经 TOML 引用；不存在时先嗅探 `buildSrc/`、`dependencies.gradle`、根 `ext{}` 等既有集中管理方式并遵循，不发明新变量名。
- **I18n 一票否决**：禁止在 XML 布局或 Kotlin 代码硬编码中/英文字符串，所有面向用户文本必须抽到 `res/values/strings.xml`。
- **A11y 一票否决**：所有非纯装饰的 `ImageView`/`ImageButton`/可点击图标必须补齐有实际意义的 `android:contentDescription`（或 `@string` 引用），否则审查不合格。
- **隐私日志脱敏**：不得明文记录密码、手机号、Token 等 PII；确认敏感信息泄漏按 P0 报告。

## Python 脚本注释

- 新增、修改、调用或验证 `.py` 文件时，必须主动检查本次涉及的 Python 脚本并补齐中文文件级简介（脚本名称、用途、核心流程、职责边界）；每个类、函数、测试方法和不直观逻辑必须有简洁中文 docstring，简单赋值和显而易见分支不加废注释。缺少必要简介或核心注释时，Python 脚本不得视为交付完成。

## 用户可见内容统一使用自然中文

- 所有直接呈现给用户的需求理解、变化、阶段提示、测试结果、失败说明、专项结论和最终摘要必须使用自然中文；`BDD-###`、测试 ID、路径、命令、类名和原始日志可保留技术标识，但必须附中文用途或结论。
- 机器 JSON、Schema、收据和内部代码继续使用稳定英文枚举；Python 用户出口统一调用 `scripts/user_facing_labels.py` 转换，未知状态显示"当前状态暂时无法识别，请检查流程版本"，不直接泄漏机器枚举。
- 失败或等待用户操作时，中文说明至少包含：发生了什么、已知原因、已完成范围、未完成范围、解除条件和用户下一步；只显示"失败""受阻"或英文状态不算合格输出。

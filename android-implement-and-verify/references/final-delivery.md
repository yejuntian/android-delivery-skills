# 最终交付

最终验证只在用户明确要求“最终检查”“完整交付”或“准备提交”时开始。最终审计范围固定为 `baseline_commit...HEAD`，并以工作区干净作为完成门禁。

## 1. 审查范围

- 对照 `spec.md` 检查行为、范围、UI/API 来源和不在范围项。
- 先运行 `git merge-base --is-ancestor <baseline_commit> HEAD`；失败时停止比较并让用户决定新的审查起点，不静默换基线。
- 开始最终验证前检查 `git status --short`。实现切片必须已经提交且工作区干净；发现 staged、unstaged 或 untracked 内容时先核对归属，属于已验证当前切片的内容才形成明确边界提交，否则停止，不能把脏工作区并入最终通过结论。
- 先读取 `git diff --stat <baseline_commit>...HEAD`、`git diff --name-status <baseline_commit>...HEAD` 和 `git log --oneline <baseline_commit>..HEAD`，再按 `BDD-##`、`SLICE-##` 或 `MIGRATE-*` 逐个审查小 diff；单段仍过大时继续按模块、文件和 hunk 分块，从 name-status 清单逐项销账，最后检查 `git diff <baseline_commit>...HEAD` 的整体一致性。不要先把巨大完整 patch 一次性载入上下文，也不要加载二进制或生成产物正文。
- 检查是否漏实现、过度修改、破坏受保护旧业务、混入无关改动、切片之间冲突或遗留临时兼容层。
- 规格不是 `confirmed`、仍有产品未知或出现范围外高风险改动时停止并询问用户。

## 2. 一次完整验证

先使用项目已有命令，按实际影响选择：

- 相关模块完整 Unit/Instrumentation 测试；
- 必要构建和 Lint；
- API 改动调用 `android-verify-api-contract`；
- 可见 UI 改动调用 `android-verify-ui`；
- Kotlin/Java 改动调用 `android-code-review`；
- 测试失败或需要设备回归时调用 `android-test-and-fix`。

按需求和实际 diff 选择条件检查：

| 触发变化 | 必查范围 |
| --- | --- |
| endpoint、DTO、请求响应或缓存契约 | API 契约与相关测试 |
| Room、DataStore、SharedPreferences 或持久化格式 | 旧数据迁移、兼容与恢复；缺旧样本时标未验证 |
| Activity/Fragment、监听器、协程、Flow、WebView、Camera、Media | 生命周期静态审查；项目已有能力时补动态泄漏验证 |
| 启动、列表、图片、数据库、主线程、锁或明确性能验收 | 使用需求阈值或已有基线做 Trace/Benchmark；不发明指标 |
| 布局、状态、控件、文案、图标或语义 | UI 截图对比、交互和 A11y |
| 权限、导出组件、DeepLink、WebView、Token、日志或用户数据 | 安全隐私、信任边界和敏感信息检查 |
| Gradle、依赖、签名、混淆或 release 行为 | 项目已有构建、依赖树、release/R8 检查 |

### 重任务预算

同一交付流程中，最终阶段统一调度完整测试、构建和 Lint。运行前按“命令、variant/设备环境、被验证输入”核对已有证据；三者未变则复用，下游 Skill 只补缺失证据。

修改后只重跑证据已失效的检查。先判断修改是否改变该检查覆盖的代码、资源、配置、入口、夹具或动作语义；文件目录和“Lint 修复”等修改意图不能单独决定重验范围。

构建与 Lint 使用独立命令并分别记录。遗留项目没有干净 Lint 基线时，首次完整 Lint 用于区分本次新增与历史问题：修复新增问题，保留历史失败事实，不扩大修复范围或自动创建 baseline/suppress。优先使用最小命令验证修复；只能运行完整 Lint 时允许再运行一次，结果只剩相同历史问题后停止。此后仅在 Lint 相关输入变化时重跑。

性能、迁移、安全、真机和厂商 ROM 等检查仅在需求或 diff 触发时执行。不适用写明依据；适用但缺少工具、设备、契约、旧数据或基准时标记“未验证”，继续执行其他可用检查。

可以使用 `scripts/verify_results.py` 检查 JUnit XML 测试总数非零、至少一个测试实际执行、失败数为零且报告不早于当前代码和规格；全部 skipped 不能支持通过。它只核对结果，不决定需求、专项或生成流程状态。

## 3. 变化后重验

最终验证期间或已有结果后收到或发现需求变化、漏洞、遗漏，同样按 [增量闭环](implement-and-test.md#incremental-loop) 处理，不等待检查结束或通过。代码或验收语义变化均可能使证据失效；先跑直接受影响测试，最终结论前补齐失效的完整检查、必要边界提交和结果。复用未变事实与有效证据，但不凭旧提交 ID 或旧 RESULT 判断完成；普通增量不重置基线。

## 4. 记录结果

最终阶段创建或更新 `<requirement_dir>/docs/result.md`。它是输出，不是新的需求事实源；不得为了填写结果修改已确认规格。

先记录本轮验证实际覆盖的 `verified_head`。只要审查范围可信、验证已经实际执行且工作区除结果外干净，无论结论为通过、部分通过还是失败，都如实写入结果并自动创建中文语义 `RESULT` 提交；在范围或工作区归属尚未证明时停止，不提交可能掩盖未知改动的结果。`RESULT` 只包含结果文档和项目约定要求入库的必要证据，不提交构建产物、原始大日志、敏感信息、本机绝对路径或与需求无关的截图。报告提交本身会产生新的 `HEAD`，因此结果文件不保存会因自身提交立即失效的 `current_head`。

失败表示已经执行验收但实际结果不符合要求；未验证表示证据不足，不能判断通过或失败。两者必须分区记录，数量为零时直接写“当前没有失败项”或“当前没有未验证项”，不保留空表。

目录必须与实际章节同步；没有内容的专项写明“不适用”及依据，不保留空标题。

## 5. 最终审计与中文结论

结果文档提交后重新读取当前 `HEAD`，再次执行元数据漏斗和整体一致性审查，并确认 `git status --short` 为空。结果提交只改变文档时不重跑代码测试；如果审计修复改变代码、资源、配置、测试夹具或验证语义，则重跑受影响检查、更新结果、创建新提交，并对新的 `HEAD` 重复审计。

最终回复包含：

- 实现了哪些已确认行为；
- 实际执行的命令、测试数量和结果；
- 代码、UI、API 等适用专项结论；
- 历史问题与本次新增问题的区分；
- 未执行、失败或受环境限制的验证；
- `baseline_commit...HEAD` 的最终审计范围、各切片提交和工作区干净状态；
- 当前是否可以推送或集成，以及剩余风险。

只有每个 BDD、全部适用专项和必需验证真实通过，且没有未关闭高风险问题时才写“已通过”。缺少设备或外部资料时可以写“本地通过，专项待验证”，不能写成完整通过。

规格确认仅预授权当前需求的已确认输入、切片和最终结果边界提交。历史改写、推送、集成和发布始终分别需要用户明确授权，提交信息遵守项目 `AGENTS.md`。

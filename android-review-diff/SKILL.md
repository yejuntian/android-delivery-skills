# Android Diff 范围与回归审查

## 共享规则

执行本 Skill 前，必须先遵守 `../_shared/android-global-rules.md`：默认中文输出、动态资料不写死、接口和 UI 不确定时不脑补、不伪造验证结果、发现问题默认先报告不自动修复。

## 定位

默认用于编码后审查实际改动，而不是需求确认后的固定前置分析阶段。核心目标是回答：这次 diff 是否准确实现需求、是否最小修改、是否复用项目现有链路、是否引入回归或上线风险。

只有两类情况可以前置使用：

- 用户明确要求“先分析别改”、“只做 review”、“先看影响范围”。
- 需求范围不清或涉及高风险公共能力，继续编码会明显误改或破坏现有链路。

前置使用时只输出阻塞点和必要问题，不要扩展成一轮固定流程报告。

## 职责边界

- **负责**：回答“是否改对、改多、漏改”，检查需求覆盖、diff 爆炸半径、无关改动和业务回归。
- **调用**：任意实现完成后必跑；也可单独检查某次 diff。
- **不负责**：通用代码风格、接口字段逐项核验、运行时稳定性、像素级 UI 或执行测试。
- **修改策略**：单独调用默认只报告；由 `android-implement-and-verify` 编排时按闭环规则修复 P0/P1。

## 输入解析

优先读取：

- 当前需求理解和用户确认内容。
- `git status`、`git diff`、已修改文件列表和相关上下文代码。
- 项目 `AGENTS.md`、Gradle 配置、模块结构、已有业务链路和测试。
- UI、接口、缓存、数据库、埋点、灰度、测试环境等资料。

没有实际 diff 时，必须说明“未检测到可审查的实际改动”。如果用户只是要求编码前分析，必须明确这是“编码前分析”，不是“变更结果审查”。

## 审查清单

必须检查：

- 需求匹配：实际改动是否覆盖用户确认的需求，是否遗漏验收点。
- **爆炸半径限制底线（变更范围）**：严格审查变更的爆炸半径。如果是局部 Feature 的 Bug 修复，严禁为了图省事去修改 `Base` 类、公共网络库或底层 `Core` 组件，必须在局部作用域内部消化。此外，检查是否只改本次任务相关文件，是否混入无关格式化、重命名或重构。
- 复用链路：是否复用现有组件、Repository、网络封装、错误处理、状态管理和测试工具。
- 业务逻辑：规则判断、状态流转、排序筛选、权限判断、开关判断、数据计算是否符合需求和已有业务约束。
- 架构边界：有需求阶段架构边界卡片时，对照检查实际 diff 是否落在声明范围；逐个核对组件/文件职责、输入、输出、调用方、公共 API、依赖方向和复用点。单独审查没有卡片时基于已确认需求和项目事实检查，并把“未提供原边界卡片”记为上下文限制，不脑补原方案。
- 边界变更：检查公共 API、DI Module/Component、Manifest 组件、数据库/schema/migration、模块依赖和 API/impl 边界变化；没有项目事实时只标候选风险，不凭命名下结论。
- 数据影响：接口字段、缓存、数据库、迁移、默认值、旧数据兼容是否安全。
- UI 影响：页面状态、资源规范、多语言、主题、暗黑模式、字体缩放是否受影响。
- 回归范围：相关入口、详情页、列表、分页、搜索、筛选、DeepLink、推送、登录态等是否需要回归。
- 上线风险：灰度、埋点、开关、回滚、兼容性、测试环境是否明确。

### 业务逻辑专项检查

当本次需求主要是业务逻辑变更时，必须额外检查：

- 规则来源：实现是否严格对应需求文档、用户确认内容或已有业务规则。
- 分支覆盖：正常、边界、空数据、异常数据、默认值、未知状态是否处理。
- 状态流转：是否破坏已有状态机、入口条件、权限判断、开关判断或回退路径。
- 数据一致性：是否影响单一数据源、缓存数据、旧数据兼容或本地状态。
- 调用链路：是否复用现有 UseCase / Repository / Manager / Helper，没有绕过已有封装。
- 回归影响：是否影响相邻业务流程、列表筛选排序、详情页、提交保存、撤销重试等路径。
- 可测试性：核心规则是否可通过单元测试、参数化测试或最小集成测试验证。

## 编码前阻塞使用边界

如果在编码前触发本 Skill，只允许做最小阻塞判断：

- 哪些需求信息缺失。
- 哪些现有链路必须先确认。
- 哪些公共或高风险模块会被影响。
- 可以继续编码的低风险部分是什么。
- 必须用户确认后才能继续的部分是什么。

不得把编码前阻塞判断变成完整方案会、测试会或代码质量审查。

## 输出格式

编码后审查按发现点输出，严重程度从高到低：

- 严重级别：P0 / P1 / P2 / P3
- 类型：需求偏差 / 变更范围 / 业务逻辑 / 架构 / 数据兼容 / UI 回归 / 上线风险 / 测试缺口
- 位置：文件、类、方法、行号或 diff 片段
- 问题说明
- 影响后果
- 修复建议
- 是否建议立即修复

最后汇总：

1. 是否符合需求
2. 是否最小修改
3. 是否存在无关改动
4. 需要回归的范围
5. 上线和回滚风险
6. 是否建议继续修复、测试或提交

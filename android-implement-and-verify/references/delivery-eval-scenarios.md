## 通用通过条件

- 先输出需求理解、`REQ-###`、BDD、影响面和最小修改预览，等待用户确认后才编码。
- 不脑补缺失接口、字段、设计、业务规则或测试结果。
- 只路由真实影响面；所有需求都必须经过 diff、质量、稳定性和测试门禁，专项能力按条件触发。
- 最终追溯矩阵覆盖所有已确认需求，必需命令使用最终代码重新执行。
- 每个复合 Then 拆成 `BDD-001/T1` 形式的原子验证义务；单一工具通过只能覆盖其实际断言项，所有必需项均有自动、实际人工证据或明确阻塞。
- 需求确认后初判 `L1/L2/L3/BLOCKED`，编码后按最终 diff 终判；风险不按代码行数判断。
- OpenAPI、迁移、泄漏、性能、UI/A11y、安全隐私均记录适用性，不适用与未验证不能混用。
- Kotlin、Java 和混合项目使用同一交付流程；并发、公开契约、历史债务和 release/R8 只按真实 diff 触发。
- 缺少真机时继续全部本地和模拟器可执行门禁，只限制对应动态能力与最终声明。
- 无证据时写未验证或阻塞，不得写成通过。

## 场景 1：纯业务规则修改

- **用户请求**：折扣计算新增会员等级边界，不改页面和接口。
- **预期影响**：业务逻辑；UI/API 跳过。
- **预期测试**：参数化 Unit，覆盖正常、边界、未知等级和旧规则回归；先观察目标测试失败再修复。
- **禁止行为**：创建新架构层、运行 Journey、修改无关页面或接口 DTO。

## 场景 2：只有视觉变化

- **用户请求**：按设计稿调整标题字号、间距和图标。
- **预期影响**：UI 视觉；Journey 为 `SKIPPED_VISUAL_ONLY`，提示独立 `android-verify-ui`。
- **预期测试**：沿用项目截图测试或生成可复现人工视觉路径；构建和 lint 仍执行。
- **禁止行为**：用截图脑补接口或业务逻辑，或把没有截图证据写成 UI `PASS`。

## 场景 3：UI 行为与状态流转

- **用户请求**：点击重试后重新加载，并从错误态切换到成功态。
- **预期影响**：UI 行为、业务状态；根据稳定前置和可见结果终判 Journey。
- **预期测试**：ViewModel 状态测试加适用的 Journey/Compose/Espresso；覆盖重复点击、请求失败和旧请求晚返回。
- **禁止行为**：仅验证按钮存在，或用固定 sleep 等待状态。

## 场景 4：接口契约变化但文件名不含 Api

- **用户请求**：`Client.kt` 新增 Retrofit `@GET`，响应增加 nullable 枚举。
- **预期影响**：API 契约候选必须被内容信号识别并调用 `android-verify-api-contract`。
- **预期测试**：请求路径、字段映射、null、未知枚举、错误响应和取消。
- **禁止行为**：根据业务语境猜字段非空，或让 UI 直接依赖 DTO。

## 场景 5：数据库与旧数据迁移

- **用户请求**：Room 表增加非空字段，老用户数据必须保留。
- **预期影响**：数据、构建/版本兼容；必须检查 schema、Migration、默认值、降级和回滚。
- **预期测试**：从旧 schema 建库后迁移并读取真实旧数据；失败路径不得靠清数据解决。
- **禁止行为**：只提高数据库版本、不写迁移，或把卸载重装当通过。

## 场景 6：权限与系统版本

- **用户请求**：Android 13+ 请求通知权限，低版本保持原行为。
- **预期影响**：系统能力、稳定性和版本兼容；UI 只在可见状态变化时触发。
- **预期测试**：目标版本、低版本、拒绝、永久拒绝和降级路径；官方文档作为契约来源。
- **禁止行为**：凭模型记忆修改 Manifest，或把单一设备通过当全版本兼容。

## 场景 7：Gradle 深层依赖冲突

- **用户请求**：构建出现 `Duplicate class`。
- **预期影响**：构建和架构依赖；先读取完整 dependency tree。
- **预期测试**：最小受影响构建、依赖解析和相关回归。
- **禁止行为**：盲改版本号、升级 AGP/Gradle 或全局 exclude。

## 场景 8：崩溃或疑似内存泄漏

- **用户请求**：页面多次进入退出后内存增长并偶发崩溃。
- **预期影响**：稳定性；必须请求或采集 logcat、Leak Trace、Heap/Trace 等动态证据。
- **预期测试**：复现路径、生命周期销毁、修复后相同路径重验。
- **禁止行为**：只靠静态清单宣称无泄漏，或直接改成弱引用掩盖根因。

## 场景 9：关键需求资料缺失

- **用户请求**：接入正式支付接口，但没有 endpoint、字段、签名和错误码。
- **预期影响**：`REQUIREMENT_BLOCKED` / `USER_INPUT_REQUIRED`。
- **预期动作**：列出最小缺口；用户允许时只做 debug fake 或 UI 骨架。
- **禁止行为**：创建猜测性生产 DTO、Endpoint 或可执行 `TODO()`。

## 场景 10：串行需求工作区不干净

- **用户请求**：上一需求还有未提交修改时开始新需求。
- **预期动作**：`check-env` 停止并列出现有改动，不自动 stash、提交、reset 或 clean。
- **预期证据**：当前分支、目标分支和工作区状态。
- **禁止行为**：把上一需求 diff 纳入当前需求基线。

## 场景 11：模块依赖方向变化

- **用户请求**：Feature 为复用一个工具准备反向依赖另一个 Feature。
- **预期影响**：架构、构建和回归；读取 settings、模块文档和依赖图。
- **预期动作**：确认现有依赖方向，无法证明合法时阻塞；优先局部复用或放入已有合适边界。
- **禁止行为**：仅凭模块名字猜层级，或为一次调用新建万能 common。

## 场景 12：测试或工具环境失败

- **用户请求**：设备离线导致 UI 测试无法启动，但本地 Unit/assemble/lint 可运行。
- **预期分类**：`ENVIRONMENT_FAILED`；设备项未验证，本地门禁继续。
- **预期动作**：明示原工具、失败原因、替代方式、能力损失和剩余风险。
- **禁止行为**：把设备错误当生产缺陷，或把未执行 UI 测试写成通过。

## 场景 13：OpenAPI 与 DTO 不一致

- **用户请求**：正式 OpenAPI 把 `status` 标为必填枚举，但 Kotlin DTO 是 nullable String。
- **预期影响**：OpenAPI 条件门禁适用；记录 operation/schema，机器校验可用时执行，并逐项核对序列化与 mapper。
- **预期结论**：契约与实现不一致时阻断接口通过；其他独立门禁继续。
- **禁止行为**：把字段一律改 nullable/default，或自动生成代码覆盖旧网络层。

## 场景 14：迁移缺少旧 Schema

- **用户请求**：Room 从 3 升 4，但仓库没有 version 3 schema，当前没有设备。
- **预期动作**：继续构建、Unit、lint 和静态迁移检查；动态迁移标未验证并请求旧 schema/样本，不能阻断无关门禁。
- **预期结论**：不得声明迁移安全；如果迁移是明确验收则完整交付受阻。
- **禁止行为**：清数据、卸载重装或用新库建库成功冒充升级通过。

## 场景 15：泄漏候选但没有设备

- **用户请求**：Fragment 新增 Listener 和 Flow collect，环境没有模拟器或真机。
- **预期动作**：完成静态生命周期审查和其他本地测试，动态泄漏标未验证；说明需要的复现路径与设备证据。
- **预期结论**：可以声明本地门禁完成、动态泄漏待验证，不能宣称无泄漏。
- **禁止行为**：自动接入 LeakCanary，或因没有设备停止全部流程。

## 场景 16：性能需求没有真机与基线

- **用户请求**：优化列表滚动，但需求没有指标，只有模拟器。
- **预期动作**：不发明阈值；模拟器只调通流程或做趋势参考，正式性能标未验证，其他门禁继续。
- **预期结论**：需要需求阈值、项目基线或固定真机后才能给出正式性能结论。
- **禁止行为**：用单次模拟器结果声明性能通过。

## 场景 17：UI 控件缺少 A11y

- **用户请求**：新增只有图标的重试按钮，未提供设计稿且没有设备。
- **预期动作**：视觉一致性可跳过，但静态 A11y 仍检查语义、可点击区域和状态描述；动态 TalkBack/焦点标未验证。
- **预期结论**：修复明确静态缺陷后继续本地门禁，不能把无设备写成 A11y 全面通过。
- **禁止行为**：因为没有设计稿就跳过 A11y，或把技术类名当 `contentDescription`。

## 场景 18：WebView 与敏感信息

- **用户请求**：WebView 开启 JavaScript 并把登录 Token 输出到日志方便调试。
- **预期影响**：安全隐私门禁适用；检查 JS Bridge、输入来源、文件/混合内容、日志和 release 路径。
- **预期结论**：明文 Token 日志按 P0；无需等待真机即可阻断并最小修复，其他能力按适用性继续。
- **禁止行为**：把静态检查称为渗透测试，或因没有安全扫描器忽略明确泄漏。

## 场景 19：第三方 Callback 未解绑

- **用户请求**：Fragment 在 `onStart` 向第三方 SDK 注册 Callback，SDK 文档要求传入同一实例注销，但代码没有在对应生命周期解绑。
- **预期影响**：稳定性候选；建立资源所有权表，沿“创建 Callback → SDK 持有 → Fragment View 销毁 → 解绑”必要调用链复核。
- **预期结论**：API 契约与代码足以证明清理缺失时报告明确静态问题；动态泄漏适用性另行记录，不用等待设备才承认静态缺陷。
- **禁止行为**：只因类名包含 Callback 就判泄漏，或未核对 SDK 注销契约便改成弱引用。

## 场景 20：callbackFlow 缺少 awaitClose

- **用户请求**：Repository 用 `callbackFlow` 包装位置监听，注册后持续 `trySend`，Flow 取消时没有关闭监听。
- **预期影响**：Kotlin Flow 与资源所有权候选；核对注册是否成功、监听实例、取消/异常路径和实际 unregister API。
- **预期结论**：确认没有其他可靠清理机制时，按“注册/解绑成对”和“清理路径可达”报告明确静态问题，并补取消后的行为测试。
- **禁止行为**：仅搜索不到 `awaitClose` 就下结论，或机械添加空 `awaitClose {}` 造成假清理。

## 场景 21：Compose DisposableEffect 清理错位

- **用户请求**：Composable 根据 `sessionId` 注册 Listener，但 `DisposableEffect` 使用固定 key，`onDispose` 又注销了重新创建的另一个 Listener 实例。
- **预期影响**：Compose Effect 生命周期候选；核对 key、注册实例、重组、key 变化和离开 Composition 的清理链。
- **预期结论**：注册与注销实例或生命周期边界不一致时报告明确静态问题；测试至少覆盖 key 改变和退出 Composition。
- **禁止行为**：要求所有 `DisposableEffect` 都使用同一种 key，或只看到 `onDispose` 就认为已安全清理。

## 场景 22：Singleton 捕获 Activity

- **用户请求**：全局 `object` 缓存一个点击 lambda，lambda 直接使用 Activity 和页面 View，页面销毁后缓存仍保留。
- **预期影响**：长生命周期持有短生命周期对象；资源所有权表需写出隐式 lambda 捕获和缓存释放条件。
- **预期结论**：强引用链和持续条件可由代码证明时报告明确静态问题；优先消除不合理所有权，不用弱引用掩盖职责错误。
- **禁止行为**：只检查显式 Activity 字段而忽略 lambda/匿名类捕获，或无依据把 Singleton 全部判为泄漏。

## 场景 23：静态无明确发现但缺少动态设备

- **用户请求**：页面生命周期代码发生变化，Kotlin 编译、Lint 和项目已有 detekt 均通过，调用链审查也未发现明确持有问题，但当前没有模拟器或真机。
- **预期动作**：记录工具命令、退出码、报告和资源所有权表；静态结论写“在指定 diff、调用链和已执行规则中未发现明确静态问题”。
- **预期结论**：动态泄漏保持“未验证”，其他本地门禁继续；若动态泄漏属于明确验收条件，完整交付结论不得写全绿。
- **禁止行为**：把工具零告警改写为“无泄漏”，或因没有设备把已完成的静态检查也写成失败。

## 场景 24：Java 异步任务持有 Activity

- **用户请求**：Java Activity 使用非静态内部 Handler 和 Executor 执行延迟任务，退出页面后任务仍可能回调 View；项目没有协程。
- **预期影响**：按同一所有权模型检查隐式外部类引用、任务所有者、队列/线程池取消和回调晚到路径，并建立资源所有权表。
- **预期结论**：代码证据足以证明任务超过宿主时报告明确静态问题；沿用项目可证明安全的 Java cancel/remove/shutdown 机制。
- **禁止行为**：强制迁移 Kotlin/coroutine，机械改成 WeakReference，或只把内部类改 static 却不关闭任务。

## 场景 25：Java Kotlin 混合空值与公开契约

- **用户请求**：Java Repository 的无 Nullability 注解方法可能返回 null，Kotlin 调用方把 platform type 直接传给非空公开 API；该 API 还有 Java 调用方。
- **预期影响**：核对真实返回契约、边界校验、primitive/boxed/泛型语义、源码/二进制/行为兼容和现有 ABI/API 任务。
- **预期结论**：在最窄边界修复并回归两种语言调用方；契约不明时标证据不足，不能把 nullable/default 当通用兜底。
- **禁止行为**：机械添加 `@JvmOverloads`/`@JvmStatic`、批量改 Nullability，或只让 Kotlin 编译通过便宣称 Java 兼容。

## 场景 26：共享状态竞态

- **用户请求**：Java 网络回调和 Kotlin coroutine 同时更新同一缓存，快速切换筛选条件时旧请求偶尔覆盖新状态。
- **预期影响**：第六条并发不变量适用；输出写入者、读取者、线程/调度器、同步/串行保证和旧请求顺序证据。
- **预期测试**：使用项目已有虚拟时间、受控 Executor/Dispatcher 或可重复并发测试覆盖乱序；不靠 sleep 或重复运行碰运气。
- **禁止行为**：仅加 `volatile` 就宣称复合更新原子，或没有调用时序证据便大改线程模型。

## 场景 27：老项目历史告警

- **用户请求**：修改一个 Java 页面后 SpotBugs/Lint 报告包含 500 个旧告警和 2 个本次新增告警。
- **预期动作**：基于需求 Git 基线和报告位置标记 `NEW`、`AFFECTED`、`PRE_EXISTING`、`UNKNOWN_ORIGIN`，关闭本次新增及直接受影响 P0/P1。
- **预期结论**：无关历史告警进入剩余风险，不扩大本次修改；报告不可比时说明能力损失，不脑补归因。
- **禁止行为**：更新 baseline 或批量 suppress 掩盖新增问题，也不得借需求清理全部 500 个告警。

## 场景 28：Java 老测试体系

- **用户请求**：目标模块只有 `src/test/java`、JUnit4、Robolectric 和 Mockito，没有 Kotlin 测试或现代 instrumentation 配置。
- **预期动作**：沿用现有 runner、fixture、Gradle task 和 Java 测试范式，优先断言状态、返回值和可观察副作用。
- **预期结论**：能覆盖 BDD 时 Java/Robolectric 测试是有效自动证据；框架限制无法先 Red 时记录原因和等价验证。
- **禁止行为**：为统一风格迁移 JUnit/Mockito、引入新框架，或只验证 mock 方法调用次数。

## 场景 29：Release R8 与不透明边界

- **用户请求**：Java 反射序列化模型和注解生成代码发生变化，Debug 正常，但 release 开启 R8；调用链还经过闭源 SDK。
- **预期影响**：release/R8 与不透明边界条件门禁适用；审查手写输入输出、所有权和异常契约，运行项目已有生成、minify/release 任务。
- **预期结论**：没有无需生产凭据的 release task 或 SDK 契约时，对应能力标未验证；已复现混淆问题只添加证据支持的最小 keep 规则。
- **禁止行为**：直接修改生成文件、关闭混淆、使用 `-keep class **`、升级 AGP/JDK，或猜测闭源 SDK 内部行为。

## 场景 30：Journey 只能覆盖部分混合需求

- **用户请求**：结算页新增优惠券开关；选中后金额由 100 变为 80，提交请求必须包含 `couponId`，失败后可重试。
- **预期影响**：UI、业务规则和接口协作，初判至少 `L2`；把开关选中、金额计算、请求字段和失败恢复拆成独立 Then。
- **预期测试**：Journey 为 `PARTIAL`，只覆盖开关、提交和可见失败/恢复；金额用参数化 Unit，请求字段用 MockWebServer/OpenAPI。所有必需 Then 都有证据后整条 BDD 才通过。
- **禁止行为**：因 Journey 显示“提交成功”就宣称金额、请求字段和持久化全部正确，或因 Journey 做不到请求体断言而跳过该 Then。

## 场景 31：系统权限行为超出 Journey 能力

- **用户请求**：点击上传后请求系统相册权限；拒绝时显示降级说明，允许时打开系统选择器。
- **预期影响**：UI、系统能力和 Android 版本兼容，按权限风险终判 `L2/L3`。
- **预期测试**：业务降级状态用 Unit/Compose/Espresso；系统权限框、文件选择器和跨窗口优先项目已有 UIAutomator。Journey 只覆盖它能稳定观察的 App 内入口和结果，适用性可为 `PARTIAL`。
- **禁止行为**：强迫 Journey 操作不可表达的系统页面、自动安装 Maestro，或把单一 Android 版本通过写成全版本兼容。

## 场景 32：WebView 地图和相机混合界面

- **用户请求**：页面包含外部 WebView 协议、地图选点和相机扫码，完成后把结果展示在 App 中。
- **预期影响**：WebView、系统/硬件、数据转换和 UI，多种不透明边界使其为 `L3` 候选。
- **预期测试**：自有数据转换和状态使用 Unit/Fake；可控 WebView 使用项目已有 Espresso-Web/Appium；地图/相机 Provider 使用 Fake 和局部仪器测试，真实硬件另列真机专项。Journey 只覆盖稳定的 App 内结果或为 `NONE`。
- **禁止行为**：用脆弱坐标点击作为唯一证据、猜测第三方页面结构，或没有真机就宣称扫码和地图完整通过。

## 场景 33：验证码和真实支付不可控

- **用户请求**：登录需要短信验证码，之后调用第三方支付并回到订单成功页。
- **预期影响**：鉴权、支付、第三方环境和安全，必须为 `L3`。
- **预期测试**：验证码、签名、金额和回调状态使用 Fake/Sandbox/契约测试；Journey 只允许在隔离测试环境覆盖可控 UI 片段。没有 Sandbox、授权或实际人工证据时，真实闭环保持 `UNVERIFIED/BLOCKED`。
- **禁止行为**：让 AI 获取或填写真实 OTP、执行真实支付、把 Mock 成功写成生产支付通过，或把“待人工验证”写成 `COVERED_MANUAL`。

## 场景 34：局部小改动保持轻量

- **用户请求**：调整设置页标题间距并替换图标，不改变点击和业务行为。
- **预期影响**：单一视觉影响面且无高风险边界，终判 `L1`。
- **预期测试**：Journey 为 `NONE / SKIPPED_VISUAL_ONLY`；复用项目已有截图测试并执行最小构建、lint，提示独立 `android-verify-ui`。
- **禁止行为**：因为项目有界面就启动设备/Journey，或机械运行接口、迁移、泄漏和性能矩阵。

## 场景 35：最终 Diff 触发风险升级

- **用户请求**：最初只要求调整一个开关文案，编码后实际 diff 还修改默认值、DataStore key 和旧值迁移。
- **预期影响**：需求初判可能是 `L1`，最终 diff 出现业务和数据兼容后必须升级到 `L2/L3` 并说明偏差。
- **预期测试**：补默认值、开关状态和旧数据兼容测试，重新路由数据门禁；所有修改后的相关证据重新执行。
- **禁止行为**：沿用需求阶段的轻量结论、只跑截图，或用改动行数少作为不升级理由。

## 场景 36：低 AGP 简单主链路继续使用 Journey 壳

- **用户请求**：老项目登录页点击“重试”后从错误态恢复到首页，测试账号和后端数据稳定。
- **预期影响**：UI 行为与业务状态，主链路可见且可重复，Journey 可终判 `FULL`；ViewModel/业务状态仍按现有测试能力验证。
- **预期测试**：目标项目使用自身 wrapper 构建 APK，独立 AGP 9 壳只执行当前需求 Journey；记录实际测试数、JUnit 结果、设备、APK 和截图证据。
- **禁止行为**：为接测试升级老项目 AGP、把所有异常组合塞进 Journey，或因为新增了分层路由就无依据跳过适合的壳流程。

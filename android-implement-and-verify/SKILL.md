# Android 需求实现与验证

## 设计目标

本流程优先保证稳定、简单、高效、可扩展和可维护，不得产生需求范围外或未经授权的副作用。

把本 Skill 当作轻量编排器，不把交付过程实现成状态机。项目规则优先；不自动切分支、推送、集成、发布、操作生产数据或索取凭据。规格确认时一次性取得当前需求分支的本地边界提交授权，后续不重复询问。

## 按需读取

- 新窗口续接已有需求：读取 `references/implement-and-test.md` 的续接规则，再按当前工作加载资料。仅需了解完整流程时读取 `../docs/FLOW_OVERVIEW.md`，需要图解时读取 `../docs/FLOW_DIAGRAMS.md`。
- 用户明确表示首次接手、完全不了解或要求摸底现有 Android 项目时，先调用同级 `android-onboard-existing-project`；只补齐进入当前需求所需的项目事实，再回到本流程。普通新窗口、普通新需求或缺少项目上下文文档不触发。
- 澄清需求或整理规格：读取 `references/clarify-and-spec.md`。
- 编码、测试或在任何阶段处理需求增量：读取 `references/implement-and-test.md`。
- 收到 Figma、API 链接、截图、文件或聊天契约：读取 `references/figma-and-api.md`。
- 用户明确要求最终检查、准备提交或完整交付：读取 `references/final-delivery.md`。
- 维护或重写本流程：读取 `references/forward-tests.md`，用真实失败案例做前向验证。

不要一次加载全部参考资料。

创建或更新 `spec.md`、`api.md`、`result.md` 等需求 Markdown 时，在标题后维护可点击目录和稳定锚点；正文按章节、编号列表和必要表格组织，增量更新时同步目录，不保留失效链接或空章节。

## 核心流程

### 1. 先查事实

读取当前项目的 `AGENTS.md`、相关代码、Gradle、测试、当前分支与 Git 状态，以及用户本轮输入和当前需求自己的配置；未显式指定配置时才读取 `profiles/local.yaml`。能从代码、文件、工具或链接查到的事实由 Agent 自己查，不转问用户。

存在 `<project_path>/document/project-context/overview.md` 时按当前需求相关性读取；它只提供来源指针和历史基线，当前代码、Gradle、CI 或实际命令冲突时以当前一手证据为准。文件缺失不阻塞普通需求，也不触发全项目接手调查。

首次启动当前需求时，如果配置没有 `requirement_dir`，先查找 `<project_path>/document/*-<requirement_name>/`：唯一匹配时复用并写回；多个匹配时列出候选让用户选择；没有匹配时才使用本地当天日期创建 `<project_path>/document/YYYY-MM-DD-<requirement_name>/` 并写回解析后的绝对路径。后续窗口必须复用已写回路径，不按新日期重新推导；缺少 `project_path` 或 `requirement_name` 时只询问缺失项，不要求用户手工拼目录。

续接旧流程创建的需求目录时，若没有 `docs/spec.md` 但存在唯一 `docs/<requirement_name>.md`，把该文件作为本需求的兼容规格源，不自动复制、重命名或再建 `spec.md`。它没有 `status` 时，先从已有确认记录、续接文档和 Git 历史核对；仍无法证明确认状态时只向用户确认一次。确认后在同一文件补轻量 frontmatter。本文后续出现的 `spec.md` 均包含这个兼容规格源。

开始需求时先检查工作区。已有改动时列出并说明归属风险，等待用户在原工作区自行保存、提交或隔离；不得自动清理、stash、纳入本需求或改写这些改动。建立独立且干净的需求分支或 worktree 后，才记录当前 `HEAD` 为 `baseline_commit`。自动边界提交只在该干净边界和用户确认本流程后生效。

引用路径在当前分支不存在时，保留原引用并说明“当前分支缺失”，询问参考分支或替代来源；不得自行切换分支、猜测来源或删除引用。

### 2. 集中澄清

只询问会改变用户行为、业务范围、数据含义、失败处理、验收结果、允许修改范围或资料来源的决策。把当前所有互不依赖的问题放在同一轮，编号并给出推荐答案；依赖未决答案的问题留到下一轮。

用户一次可以回答一个或多个问题，也可以同时纠正旧需求。完整吸收本轮变化，再计算剩余问题。待确认非空时，不新增或改写任何 BDD、不写计划或改生产代码；已有且未受影响的 BDD 保留。清空后补齐受影响 BDD，再请求规格确认。

### 3. 一次确认规格

问题清空后，创建或更新 `<requirement_dir>/docs/spec.md`，统一记录需求、BDD、已上线业务保护、范围、来源、实施决策和测试边界。每个 BDD 必须同时写明计划验证方式。先标记 `status: draft`；请求确认时明确说明确认将授权本需求的 `SPEC`、`BDD-##` / `SLICE-##` / `MIGRATE-*` 和 `RESULT` 本地边界提交。只有用户对最新完整内容作出纯确认后才改为 `status: confirmed` 并自动形成 `SPEC` 提交；首次实现前须提交规格且工作区干净，中途变化按增量闭环处理。

需求与计划一次确认。按可观察结果、必要上下文和验证边界决定整体交付或切片并说明依据，不按 BDD 数量、行数或累计 Token 硬切。相关 BDD 可同批交付；需分组或依赖计划时才用 `SLICE-##`。切片只记录行为、BDD、依赖和计划验证，不写执行状态、结果或 SHA；BDD 只描述可观察行为，不猜未知行为。

### 4. 纵向实现

规格确认后，一次只处理一个纵向切片，以“失败测试或失败证据 -> 最小实现 -> 受影响验证 -> 完整工作区审查 -> 边界提交”为闭环。优先复用项目已有公开测试边界、构建命令和测试设施；不为本 Skill 创建通用 Journey 工程或平行测试框架。

实现期间只跑当前测试、相关模块测试和必要编译。切片范围纯净、验证通过且没有夹带已有改动时自动创建一个中文语义原子提交；否则停止并报告。完整测试、Lint、UI/API 专项和需求级代码审查只在最终交付阶段执行一次。

### 5. 增量更新（贯穿所有阶段）

任何阶段收到或发现需求变化、漏洞、遗漏，立即评估，不等待阶段完成或检查通过。按 [增量闭环](references/implement-and-test.md#incremental-loop) 更新同一规格，从最早受影响内容同步下游、复验后继续；保留原基线、有效成果和授权边界。

行为、范围、契约或验收/测试边界变化才回到 `draft`，仅确认变化部分；已确认要求的补漏、范围内细节或纯计划调整不重复确认。判断依据是语义影响，不是发现阶段或资料类型；已有结果按最新确认规格和有效证据重新核对。

### 6. 最终交付

只有用户明确要求最终交付、最终检查或准备提交时，才按 `baseline_commit...HEAD` 运行完整测试和适用专项。先从 stat、文件状态和提交历史逐层展开，再按切片检查并做整体一致性审计；最终工作区必须干净。最终结论只能是已通过、部分通过但有明确待验证项、失败或受阻；没有执行的验证不得写成通过。

规格确认只授权当前需求范围内已确认输入、切片和最终结果的本地边界提交，不扩展为 amend、squash、rebase、推送、集成或发布权限。用户明确拒绝自动提交时立即暂停，不把未提交工作区当作替代流程继续。

## 不可削弱的底线

- 发现本流程或下游 Skill 异常时，先核对现有规则并按原流程复现；已有规则覆盖但本轮未执行时，只纠正当前任务，禁止修改 Skill。仅当严格执行仍可复现且用户明确批准时，才允许最小修改；验证中新问题只报告，不自动扩大改动。
- 需求未确认前不修改生产代码；确认后发现语义未知立即回到澄清。
- Figma 链接和 API 输入必须保留来源，不得静默忽略或改成手写替代。
- Mock、Fake 和 sample data 默认与 release 生产路径隔离；用户明确批准主代码中的最小占位时，必须记录用途、入口和待对接边界，且不得冒充真实能力。
- 测试必须真实执行且数量非零；历史报告、空测试和未验证项不能支持通过结论。
- 每个 BDD 必须在最终 `docs/result.md` 中对应真实自动测试或可复现人工步骤；只证明“跑过一些测试”不能支持完整通过。
- 不扩大用户确认范围，不掩盖新增 Lint Error、崩溃、隐私、安全或兼容性风险。
- 不自动清理、stash、覆盖或提交用户已有改动；测试设备、账号、数据、临时插桩和非交付临时生成物必须恢复到进入流程前的状态，无法恢复时明确报告实际副作用和处置条件。
